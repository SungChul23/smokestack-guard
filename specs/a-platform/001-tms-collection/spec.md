# Feature Specification: TMS 원본 수집 인프라

**Feature Branch**: `infra/tms-collection-terraform`

**Created**: 2026-11-03

**Status**: Implemented (사후 문서화)

**Input**: User description: "사후 문서화: 이미 infra/tms-collection-terraform 브랜치에 구현된 TMS 수집 인프라의 spec. CleanSYS 공개 API를 10분마다 전체 스냅샷으로 받아 SHA-256 변경 시에만 S3에 gzip 원문+메타 저장, 실행 시각은 매번 상태 파일에 기록해 갱신 없음과 수집 중단을 구분, 실패 시 Errors 알람→SNS 메일. 이슈 #4."

**관련 이슈**: #4

> 이 spec은 개인 계정 콘솔에서 검증한 수집 구성을 팀 계정에 코드로 옮긴 뒤 작성한 **사후 문서**다. 무엇을 왜 보장하는지 기록해, 이후 변경(예: 002 누락률 리포트)이 이 보장을 깨지 않는지 리뷰할 기준으로 쓴다.

## 배경

한국환경공단 굴뚝자동측정기기(CleanSYS) 공개 API는 **현재 시점의 측정값만** 준다. 과거 조회 기능이 없으므로 수집하지 못한 시점의 데이터는 영구히 잃는다. 이후 모든 단계(Silver 정제, 분석, AI 경고)는 이 원본에서 시작한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 원본이 사람 개입 없이 계속 쌓인다 (Priority: P1)

데이터 담당자(B, C, E)는 아무도 손대지 않아도 공개 API의 전체 측정 결과가 10분마다 확인되고, 내용이 바뀔 때마다 원문 그대로 보존되기를 원한다. 나중에 정제 방식이 바뀌어도 원문에서 다시 만들 수 있어야 한다.

**Why this priority**: 놓친 데이터는 다시 받을 수 없으므로 수집 연속성이 모든 기능의 전제다.

**Independent Test**: 배포 후 1시간 동안 아무 조작 없이 두고, 원본 저장소에 원문·메타가 쌓이고 상태 파일의 마지막 확인 시각이 10분마다 바뀌는지 본다.

**Acceptance Scenarios**:

1. **Given** 배포가 끝난 상태, **When** 매시 00·10·20·30·40·50분(한국 시각)이 되면, **Then** API 전체 스냅샷을 한 번 받는다.
2. **Given** 이번 응답이 직전에 저장한 응답과 내용이 다를 때, **When** 수집이 끝나면, **Then** 원문(압축)과 메타 정보가 실행 시각 기준 경로에 새로 저장된다.
3. **Given** 이번 응답이 직전 응답과 같을 때, **When** 수집이 끝나면, **Then** 원문은 저장하지 않고 "마지막 확인 시각"만 갱신된다.
4. **Given** 원문을 저장한 뒤, **When** 데이터 담당자가 원문을 열면, **Then** API가 준 바이트와 완전히 같은 내용이 나온다.

---

### User Story 2 - "갱신 없음"과 "수집 중단"을 구분한다 (Priority: P1)

운영 담당자(A, B)는 원문이 한동안 새로 생기지 않을 때, 그것이 API 값이 안 바뀐 정상 상태인지 수집이 멈춘 장애인지 바로 구분하고 싶다.

**Why this priority**: 둘을 구분하지 못하면 장애를 정상으로 오인해 수집 공백이 길어진다.

**Independent Test**: 상태 파일 하나만 보고 마지막 확인 시각과 마지막 변경 시각을 비교해 판단할 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** API 값이 1시간째 그대로일 때, **When** 상태 파일을 보면, **Then** 마지막 확인 시각은 최근 10분 이내이고 마지막 변경 시각만 오래되어 있다.
2. **Given** 수집이 멈췄을 때, **When** 상태 파일을 보면, **Then** 마지막 확인 시각 자체가 멈춰 있다.

---

### User Story 3 - 실패하거나 멈추면 사람에게 알린다 (Priority: P2)

운영 담당자는 수집이 실패하거나 아예 실행되지 않으면 이메일로 알림을 받아, 공백이 길어지기 전에 대응하고 싶다.

**Why this priority**: 자동 수집의 안전장치다. 다만 알림이 와도 이미 놓친 회차는 복구할 수 없으므로 P1보다 낮다.

**Independent Test**: 수집을 일부러 실패시키고(예: 잘못된 키) 15분 안에 메일이 오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 수집이 오류로 끝났을 때, **When** 15분 평가 구간이 지나면, **Then** 등록된 메일로 경보가 온다.
2. **Given** 스케줄이 멈춰 수집이 한 번도 실행되지 않을 때, **When** 15분 평가 구간이 지나면, **Then** 경보가 온다.
3. **Given** 경보 후 수집이 정상화되면, **When** 다음 평가 구간이 지나면, **Then** 정상 복귀 메일이 온다.
4. **Given** 응답 구조가 이상하거나 전체 건수와 실제 건수가 다를 때, **When** 수집이 끝나면, **Then** 원문은 보존되고, 실패로 집계되어 경보가 오며, 상태 파일은 마지막 정상 응답을 유지한다.

---

### User Story 4 - 누구나 같은 구성을 재현한다 (Priority: P2)

팀원 누구든 저장소를 받아 초기화만 하면 같은 구성을 확인·재배포할 수 있어야 하고, 파일을 따로 주고받지 않아야 한다.

**Why this priority**: 장애 복구와 팀 협업의 전제다(원칙 III).

**Independent Test**: 새 작업 환경에서 저장소를 받아 초기화와 변경 미리보기를 실행했을 때, 추가 파일 없이 실제 구성과 차이가 없다고 나오는지 본다.

**Acceptance Scenarios**:

1. **Given** 새로 받은 저장소, **When** 초기화와 미리보기를 실행하면, **Then** 공유 상태 저장소에 자동 연결되고 변경 사항이 없다고 나온다.
2. **Given** 두 사람이 동시에 변경을 적용하려 할 때, **When** 한쪽이 먼저 시작하면, **Then** 다른 쪽은 잠금 때문에 대기하거나 실패한다.

### Edge Cases

- **일시적 API 오류(과부하, 서버 오류, 네트워크 끊김)**: 한 회차 안에서 짧은 간격으로 최대 3회 시도한다. 그래도 실패하면 그 회차를 실패로 기록하고 자동 재실행에 맡긴다.
- **인증 오류 등 재시도해도 소용없는 오류**: 즉시 실패로 끝내 경보로 알린다.
- **같은 회차의 자동 재실행**: 같은 예정 시각을 받아 같은 경로에 저장한다. 회차가 중복으로 생기지 않는다.
- **첫 실행(상태 파일 없음)**: 비교 대상이 없는 것으로 보고 원문을 저장한다.
- **실행이 겹쳐 상태 파일이 어긋남**: 스냅샷이 한 번 더 저장될 수는 있지만 원문이 사라지지는 않는다.
- **재시도까지 모두 실패**: 그 회차는 복구할 수 없다. 경보로만 알 수 있다(알려진 한계).
- **API 키 교체**: 저장소의 값만 바꾸면 된다. 실행 환경이 캐시한 이전 키가 잠시 쓰일 수 있다.

## Requirements *(mandatory)*

### Functional Requirements

**수집**

- **FR-001**: 시스템은 한국 시각 기준 매시 00분부터 10분 간격으로 API 전체 측정 결과를 한 번에 받아야 한다. 실행 시각을 임의로 늦추는 유연 시간 창은 쓰지 않는다.
- **FR-002**: 시스템은 일시적 오류에 대해 한 회차 안에서 최대 3회 시도하고, 재시도해도 소용없는 오류는 즉시 실패해야 한다.
- **FR-003**: 회차의 저장 위치는 실제 실행 시각이 아니라 **예정 시각을 10분 단위로 내린 시각**으로 정해, 같은 회차를 재실행해도 같은 위치에 저장되어야 한다.

**보존**

- **FR-004**: 시스템은 응답 내용이 직전 저장분과 다를 때만 원문을 저장하고, 원문은 API가 준 바이트를 바꾸지 않고 압축만 해야 한다.
- **FR-005**: 원문마다 메타 정보(예정 시각, 요청·저장 시각, 응답 상태, 소요 시간, 시도 횟수, 원문·압축 크기, 내용 해시, 점검 결과)를 함께 저장해야 한다.
- **FR-006**: 저장 경로는 UTC 기준 `수집 날짜 / 시 / 실행 시각` 계층을 따라야 한다(`tms_cleansys/ingest_date=YYYY-MM-DD/hour=HH/run_ts=YYYYMMDDTHHMMSSZ/`).
- **FR-007**: 원본 저장소는 객체 삭제와 저장소 자체의 삭제를 막고, 덮어써도 이전 버전이 남아야 하며, 외부 공개를 차단하고 저장 시 암호화해야 한다. 자동 만료(수명 주기) 규칙은 두지 않는다.

**상태와 점검**

- **FR-008**: 시스템은 매 실행마다 상태 파일의 마지막 확인 시각을 갱신해야 한다. 상태 파일에는 마지막 내용 해시, 마지막 변경 시각, 마지막 확인 시각, 마지막 원문 위치를 둔다.
- **FR-009**: 시스템은 응답의 결과 코드가 정상이고 전체 건수와 실제 건수가 같은지 점검해야 한다. 점검에 실패하면 원문은 보존하되 상태를 갱신하지 않고 실패로 끝내야 한다.
- **FR-010**: 상태 파일은 원문과 메타 저장이 모두 끝난 뒤 마지막에 갱신해야 한다.

**알림·운영**

- **FR-011**: 15분 동안 실패가 1회 이상이거나 실행 기록이 아예 없으면 등록된 이메일로 경보를 보내고, 정상화되면 복귀 알림을 보내야 한다.
- **FR-012**: 실행 기록은 요약(건수, 변경 여부, 저장 위치, 소요 시간)만 남기고, 응답 본문과 키는 남기지 않아야 하며, 14일 보관해야 한다.

**보안·재현성**

- **FR-013**: API 키는 사람이 암호화 저장소에 직접 등록하고, 코드와 구성 정의는 그 **이름**만 참조해야 한다. 이메일 주소도 저장소 파일에 쓰지 않는다.
- **FR-014**: 수집기는 기능에 필요한 최소 권한만 가져야 한다(로그 쓰기, 원본 저장소 읽기·쓰기, 키 하나 읽기·복호화). 실행을 호출하는 주체도 그 수집기 하나만 호출할 수 있어야 한다.
- **FR-015**: 모든 구성은 코드로 정의하고, 상태는 공유 저장소에 잠금과 함께 보관해야 하며, 저장소를 받아 초기화만 하면 재현할 수 있어야 한다. 적용은 사람이 한다.

### Key Entities

- **스냅샷(원문)**: 한 회차에 받은 API 응답 전체. 압축해서 보관하며 한 번 저장하면 바꾸지 않는다.
- **메타 정보**: 스냅샷 하나에 붙는 수집 이력·크기·해시·점검 결과.
- **상태 파일**: 저장소 전체에 하나. 직전 해시와 마지막 변경·확인 시각, 마지막 원문 위치를 가진다. 매 실행 갱신된다.
- **회차(run_ts)**: 10분 단위 예정 시각. 저장 위치와 재실행 중복 방지의 기준이다.
- **경보**: 15분 구간의 실패 또는 실행 없음 여부. 이메일 구독자에게 전달된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 정상 운영 중 하루 144회 예정 회차 모두 마지막 확인 시각이 갱신된다. 상태 파일의 마지막 확인 시각이 10분 이상 멈춰 있는 구간이 없다.
- **SC-002**: API 값이 바뀐 회차는 100% 원문이 저장되고, 바뀌지 않은 회차는 원문이 추가로 생기지 않는다.
- **SC-003**: 수집 실패나 실행 중단이 생기면 15분 안에 담당자에게 메일이 도착한다.
- **SC-004**: 새 팀원이 추가 파일 없이 저장소만으로 구성을 확인할 수 있고, 미리보기 결과가 "변경 없음"이다.
- **SC-005**: 저장소, 상태 파일, 실행 기록 어디에서도 API 키와 개인 이메일이 발견되지 않는다.

## Assumptions

- API는 호출당 전체 측정 결과를 한 번에 주며, 측정값은 대략 30분 단위로 갱신된다. 10분 호출은 갱신을 놓치지 않기 위한 여유분이다.
- 계정의 동시 실행 한도가 낮아 수집기 동시 실행을 1로 고정하지 못했다. 한도를 올린 뒤 1로 고정한다(알려진 한계).
- 회차가 재시도까지 모두 실패하면 별도 보관 대기열 없이 경보로만 안다. 하루 단위 누락 확인은 002(누락률 리포트)에서 보강한다.
- 상태 저장소(bootstrap)는 최초 1회 사람이 만들고, 이후 모든 구성은 그 저장소를 공유한다.

## Out of Scope

- 정제(Silver)와 데이터 계약: C 담당
- 하루 단위 슬롯 누락률 계산과 알림: `002-missing-rate-report`
- 실시간 신선도 경보(마지막 변경 시각 정체 감지): 후속 과제
