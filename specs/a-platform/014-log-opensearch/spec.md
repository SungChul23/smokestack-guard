# Feature Specification: 서비스 로그 수집·분석 (CloudWatch → Firehose → OpenSearch)

**Feature Branch**: `65-a-서비스-로그-수집분석-cloudwatch-firehose-opensearch`

**Created**: 2026-11-20

**Status**: Draft

**Input**: User description: "서비스 로그를 CloudWatch로 모아 Data Firehose로 OpenSearch에 보내 검색·통계·모니터링 대시보드로 본다. 비용을 먼저 확인하고 개발 단계는 비용 효율적으로. 약 28일 상시 운영 후 지운다. 법령 RAG는 같은 도메인을 쓸 수 있게만 열어 두고 문서가 준비된 뒤 별도 이슈로."

## 배경

요구사항: CloudWatch로 애플리케이션·시스템 로그를 수집하고, Data Firehose로 전달하고, OpenSearch로 검색·통계·모니터링 대시보드를 만든다. **AWS 서비스별 예상 비용을 미리 확인하고, 개발 단계에서는 비용 효율적으로 구성한다.**

지금 로그는 서비스마다 CloudWatch 로그 그룹에 흩어져 있다(서버 컨테이너 2개, 수집·적재·누락률·합성·계약 검사 Lambda 등). 문제가 생기면 그룹을 하나씩 열어 봐야 하고, "어제 오류가 몇 번, 어느 서비스에서" 같은 통계를 한눈에 볼 수 없다.

**법령 RAG(후순위)**: 같은 검색 엔진에는 한국어 형태소 분석기가 기본으로 있어, 나중에 법령 근거 검색(형태소 키워드 + 벡터)에 쓸 수 있다. 원본 문서가 준비된 뒤 별도 이슈로 하고, 이 기능에서는 도메인을 그 용도로도 쓸 수 있게 크기·권한 설계만 막지 않는다.

```
[로그]  서비스 로그 그룹 → 구독 → 전달 스트림 → 검색 엔진 로그 인덱스(14일) → 대시보드·오류 알림
                                          └→ 전달 실패분은 S3에 보관
```

**비용 (서울 리전 공식 가격, 28일)**

| 항목 | 단가 | 28일 |
|---|---|---|
| 검색 엔진 인스턴스 1대(가장 작은 범용, 메모리 2GB) | $0.056/시간 | $37.6 |
| 디스크 10GB | $0.1391/GB-월 | $1.3 |
| 전달 스트림 | $0.036/GB | 약 $0.1 (로그 약 3GB 가정) |
| CloudWatch 로그 추가 수집 | $0.76/GB | 약 $1~2 |
| **합계** | | **약 $41** |

- 검색 엔진을 사설망(VPC) 안에 두면 전달 비용이 28일 약 $9 늘고, 팀원이 대시보드를 보려면 터널이 필요하다. 그래서 공개 주소 + 로그인으로 둔다.
- 서버리스 검색 엔진은 최소 사용량 요금 때문에 월 $170 이상이라 쓰지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 흩어진 서비스 로그를 한곳에서 검색한다 (Priority: P1)

팀원이 로그 대시보드에 로그인해 "지난 1시간 오류"를 검색하면, 서버·Lambda 어디에서 나왔든 한 화면에 시간순으로 나온다. 서비스 이름, 수준(오류·경고), 기간으로 거를 수 있다.

**Why this priority**: 요구사항의 핵심(수집 → 전달 → 검색)이고, 대시보드·알림(US2)은 로그가 들어와야 만들 수 있다.

**Independent Test**: 서버와 Lambda에서 로그를 하나씩 남긴 뒤 5분 안에 대시보드 검색에 두 줄이 모두 나오고, 서비스 이름으로 거르면 한 줄만 남는다.

**Acceptance Scenarios**:

1. **Given** 대상 로그 그룹에 새 로그가 남는다, **When** 5분이 지난다, **Then** 대시보드 검색에서 그 로그가 서비스 이름·시각·본문과 함께 보인다.
2. **Given** 로그인한 팀원, **When** 수준이 "오류"인 로그를 지난 24시간으로 검색한다, **Then** 모든 대상 서비스의 오류가 한 목록에 나온다.
3. **Given** 전달 중 일시 오류, **When** 검색 엔진이 로그를 받지 못한다, **Then** 그 로그는 사라지지 않고 S3에 보관된다.
4. **Given** 14일이 지난 로그, **When** 보관 기간이 지난다, **Then** 검색 엔진에서 자동으로 지워진다(원본은 CloudWatch에 기존 보관 기간대로 남음).
5. **Given** 로그인하지 않았거나 초대 코드를 통과하지 않은 사람, **When** 대시보드 주소를 연다, **Then** 들어올 수 없다.

---

### User Story 2 - 운영 대시보드와 오류 알림 (Priority: P1)

팀원은 대시보드 한 화면에서 서비스별 로그 양, 오류 추이, 수집 Lambda의 실행 상태를 본다. 짧은 시간에 오류가 몰리면 운영 메일이 온다.

**Why this priority**: 요구사항의 "통계 분석 및 모니터링 대시보드"이고, 발표에서 보여 줄 결과물이다.

**Independent Test**: 저장된 대시보드를 열면 그래프가 채워져 있고, 오류 로그를 일부러 여러 번 남기면 정해진 시간 안에 알림 메일이 온다.

**Acceptance Scenarios**:

1. **Given** 로그가 들어오는 중, **When** 저장된 운영 대시보드를 연다, **Then** 서비스별 로그 수, 시간대별 오류 수, 최근 오류 목록이 보인다.
2. **Given** 5분 안에 오류가 기준 횟수 이상 남는다, **When** 알림 조건이 확인된다, **Then** 기존 운영 알림 메일로 한 번 알린다.
3. **Given** 대시보드와 알림 설정, **When** 검색 엔진을 지웠다가 다시 만든다, **Then** 저장소에 있는 정의로 같은 대시보드·알림을 다시 만들 수 있다.

---

### User Story 3 - 사용 현황 (Priority: P2)

팀원은 대시보드에서 하루 접속자 수, 초대 코드 통과·실패·차단 수, 즐겨찾기 추가·삭제, 에이전트 질문 수를 본다. 운영 로그와 섞이지 않게 따로 모으고, 개인 정보(이메일, 질문 원문)는 남기지 않는다.

**Why this priority**: 서비스가 실제로 쓰이는지 보여 주는 지표로 발표에 쓴다. 운영 로그(US1·US2)가 먼저.

**Independent Test**: 로그인과 초대 코드 통과, 에이전트 질문을 한 번씩 한 뒤 5분 안에 사용 현황 대시보드의 숫자가 늘고, 남은 기록에 회원 id만 있고 이메일·질문 본문은 없다.

**Acceptance Scenarios**:

1. **Given** 회원이 로그인·초대 코드 통과·에이전트 질문을 한다, **When** 5분이 지난다, **Then** 사용 현황에 각 사건이 회원 id·시각·종류로 집계된다.
2. **Given** 사용 기록, **When** 내용을 본다, **Then** 이메일, 이름, 입력한 초대 코드, 질문 원문이 없다. (2026-11-25 017 변경: 에이전트 가드에 걸린 질문만 개인정보를 가린 앞 300자로 남는다)
3. **Given** 사용 기록, **When** 28일이 지난다, **Then** 자동으로 지워진다(운영 로그 14일과 따로).

### Edge Cases

- 로그 한 줄이 JSON이 아니면 본문 문자열로 그대로 넣는다(버리지 않음).
- CloudWatch가 묶어 보내는 압축 레코드를 풀어 줄 단위로 나눈다. 풀지 못하면 S3 보관.
- 검색 엔진 디스크가 차면 오래된 로그 인덱스부터 지운다(보관 정책).
- 검색 엔진 메모리가 모자라면(힙 사용률이 계속 높음) 한 단계 큰 인스턴스로 바꾼다. 데이터는 유지된다.
- 수집 Lambda 로그는 10분마다 나오지만 요약만 남기므로 양이 작다. 로그에 원문·비밀이 들어가지 않는 기존 규칙을 그대로 따른다.
- 검색 엔진을 지운 동안에도 서비스와 수집은 영향이 없다. 로그는 CloudWatch에 계속 쌓이고, 전달 실패분은 S3에 남는다.

## Requirements *(mandatory)*

### Functional Requirements

**로그 수집·전달 (US1)**

- **FR-001**: 대상 로그 그룹(서버 컨테이너 2개, 수집·누락률·대시보드 적재·합성 적재·계약 검사·학습 스냅샷 알림 Lambda)과 Step Functions 실행 결과(성공·실패·시간 초과), Glue 잡 로그의 오류 줄의 새 로그를 검색 엔진으로 보내야 한다. 대상 목록은 설정 한 곳에서 더하고 뺄 수 있어야 한다.
- **FR-002**: 로그는 남은 뒤 5분 안에 검색되어야 한다.
- **FR-003**: 각 로그에 서비스 이름(로그 그룹), 시각, 본문이 있어야 하고, JSON 로그는 필드로 나뉘어야 한다. 수준(오류·경고·정보)으로 거를 수 있어야 한다.
- **FR-004**: 전달에 실패한 로그는 S3에 보관해야 한다.
- **FR-005**: 검색 엔진의 로그는 14일 뒤 자동으로 지워야 한다. CloudWatch의 기존 보관 기간은 바꾸지 않는다.
- **FR-006**: 로그 수집 경로를 더해도 수집 Lambda의 실행·스케줄·저장에 영향이 없어야 한다.

- **FR-019**: 로그는 세 묶음으로 나눠 모아야 한다: 서버 로그(요청 기록 포함), 데이터 파이프라인(Lambda) 로그, 사용자 활동. 묶음마다 보관 기간을 따로 둔다(운영 14일, 활동 28일).
- **FR-020**: API·에이전트 서버는 요청마다 경로·상태·응답 시간·회원 id를 구조화된 한 줄로 남겨야 한다. 상태 확인 요청은 남기지 않는다.

**대시보드·알림 (US2)**

- **FR-007**: 운영 대시보드 하나를 저장해 두어야 한다: 서비스별 로그 수, 시간대별 오류 수, 최근 오류 목록, 수집 Lambda 실행 요약, 상태 머신 실행 결과(매일 갱신·30분 적재의 성공·실패).
- **FR-008**: 5분 안에 오류가 기준 횟수(기본 10) 이상이면 기존 운영 알림 메일로 알려야 한다.
- **FR-009**: 대시보드·알림·인덱스 설정은 저장소에 정의로 두어 검색 엔진을 다시 만들어도 복구할 수 있어야 한다.

**접근·보안**

- **FR-010**: 대시보드는 로그인한 `members`(013 초대 코드 통과) 회원만 볼 수 있어야 한다(팀원 전용 그룹으로 더 좁히지 않음, 2026-11-20 결정).
- **FR-021**: 사용자 활동 기록에는 회원 id·시각·사건 종류만 남기고 이메일·이름·초대 코드 입력값·질문 원문을 남기지 않아야 한다. **예외(2026-11-25, [017](../017-agent-guardrail/spec.md) FR-023)**: 1차 정규식·2차 가드레일에 걸린 질문(`event = agent_guard`)은 개인정보를 가린 앞 300자를 활동 보관 기간(28일) 동안 남긴다. 라우터가 저장 전에 한 번 더 가린다. 걸리지 않은 질문은 여전히 남기지 않는다.
- **FR-011**: 전달 스트림, 에이전트 서버, 색인 주체는 각자 필요한 인덱스·동작에만 IAM 역할로 접근해야 한다. 비밀번호를 쓰지 않는다.
- **FR-012**: 검색 엔진 주소가 공개되어 있어도 인증 없는 요청은 거부해야 한다.

**비용·운영**

- **FR-017**: 검색 엔진 전체를 스위치 하나로 만들고 지울 수 있어야 한다. 지워도 서비스·수집·RDS에는 영향이 없다.
- **FR-018**: 서비스별 예상 비용과 실제 비용 확인 방법을 문서에 남겨야 한다.

### Key Entities

- **로그 문서**: 서비스 이름, 시각, 수준, 본문(또는 JSON 필드), 로그 그룹·스트림. 서버 로그·파이프라인 로그 묶음으로 날짜별로 쌓이고 14일 뒤 지운다.
- **사용 기록**: 회원 id, 시각, 사건 종류(`session`, `invite_ok`·`invite_fail`·`invite_limited`, `favorite_add`·`favorite_remove`, `agent_question`). 28일 뒤 지운다.
- **운영 대시보드·알림 정의**: 저장소에 있는 설정 파일.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 대상 서비스에서 남긴 로그의 99% 이상이 5분 안에 검색된다.
- **SC-002**: 팀원이 "지난 24시간 오류"를 서비스 상관없이 한 번의 검색으로 10초 안에 찾는다.
- **SC-003**: 운영 대시보드 한 화면에서 서비스별 로그 수와 오류 추이를 본다(따로 그룹을 열 필요 없음).
- **SC-004**: 오류가 몰리면 10분 안에 알림 메일이 온다.
- **SC-006**: 28일 운영 비용이 $50 이하다.
- **SC-009**: 사용 현황에서 하루 접속자·질문 수를 한 화면에서 보고, 기록에서 개인 정보 검색 결과가 0건이다(가드 기록의 질문 문장 포함 — 017 SC-007).
- **SC-007**: 검색 엔진을 지웠다 다시 만들어도 1시간 안에 대시보드·알림이 복구된다.
- **SC-008**: 로그 수집 경로 추가 전후로 수집 누락률이 변하지 않는다.

## Assumptions

- 대상 로그는 하루 수 MB다(2026-11-21 로그 그룹 크기로 확인, plan research R7).
- 검색 엔진은 약 28일(시연까지) 상시 운영하고 시연 뒤 지운다.
- 가장 작은 인스턴스(메모리 2GB)로 로그는 충분하다. 나중에 법령 RAG를 더해도 수천 조각은 들어간다. 부족하면 한 단계 올린다.
- 대시보드 로그인은 013의 Cognito(Google + `members`)를 그대로 쓴다.
- RDS `rag.doc_chunk`는 이 기능에서 지우지 않는다(D와 확정 뒤).
- 범위 밖: 법령 RAG 인덱스·원본 문서 경로·임베딩(문서 준비 뒤 별도 이슈), GA4, 서비스 대시보드(React), 사용자별 에이전트 호출 제한.
