## 배경

요구사항: Google 계정으로 로그인·로그아웃하고, 사용자 인증은 AWS Cognito와 연계한다.

지금(009)은 Cognito 관리형 로그인에서 이메일·비밀번호로만 들어오고, 계정은 A가 한 사람씩 만들어 임시 비밀번호를 전달한다. 화면은 로그인이 안 됐으면 바로 로그인 페이지로 보내고, API·에이전트 서버는 Cognito가 발급한 토큰만 받는다.

Google 로그인을 열면 Google 계정이 있는 누구나 회원이 된다. 대시보드와 에이전트는 우리 팀과 시연자만 써야 하고, 특히 에이전트는 호출할 때마다 Bedrock 비용이 든다. 그래서 **로그인은 누구나 되지만, 초대 코드를 한 번 입력한 회원만 서비스를 쓴다.**

```
[로그인]   화면 → (Cognito 화면을 건너뛰고) Google 본인 확인 → Cognito가 회원을 만들거나 찾음 → Cognito 토큰
[처음 한 번] 초대 코드가 없는 회원 → 화면: "초대 코드 입력" → 서버가 코드 확인 → 회원을 members 그룹에 추가
              → 토큰을 새로 받아 바로 대시보드
[매 요청]  서버: Cognito 토큰 검증(지금과 같음) + members 그룹인지 확인 → 아니면 거부
```

- **회원 정보는 Cognito가 관리하고 Google은 본인 확인만 한다.** 서버는 지금처럼 Cognito 토큰만 믿는다. 토큰을 주는 곳이 바뀌지 않으므로 서버 검증 방식은 그대로다.
- **초대 코드를 로그인 뒤에 받는 이유**: Google 로그인 화면에는 우리 입력칸을 넣을 수 없다.
- **비밀값을 사람이 넣는 이유**: Google 연결을 Terraform으로 만들면 클라이언트 시크릿이 상태 파일에 평문으로 남는다(AGENTS.md 비밀값 규칙). 수집 API 키와 같이 사람이 등록하고 Terraform은 이름만 안다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Google 계정으로 로그인·로그아웃 (Priority: P1)

팀원이 대시보드 주소에 들어가면 서비스 첫 화면이 나오고, "Google 계정으로 로그인"을 누르면 바로 Google 계정 선택 화면으로 갔다가 대시보드로 돌아온다. 비밀번호를 따로 만들거나 기억할 필요가 없다. 로그아웃하면 다시 로그인해야 들어온다.

**Why this priority**: 요구사항의 핵심이고, 초대 코드(US2)는 로그인이 된 뒤에야 의미가 있다.

**Independent Test**: 초대 코드 검사를 켜기 전, 팀원 한 명이 Google 계정으로 로그인 → 화면의 이메일이 Google 이메일과 같은지 → 서버 인증 확인 → 로그아웃 뒤 다시 들어가면 로그인 요구.

**Acceptance Scenarios**:

1. **Given** 로그인하지 않은 사용자, **When** 대시보드 주소를 연다, **Then** 서비스 소개와 Google 로그인 버튼이 있는 첫 화면이 나오고, 버튼을 누르면 이메일·비밀번호 입력 화면을 거치지 않고 Google 계정 선택 화면으로 간다.
2. **Given** Google 본인 확인을 마친 처음 온 사용자, **When** 대시보드로 돌아온다, **Then** 회원이 하나 생기고 이메일·이름이 Google 계정 값으로 채워진다.
3. **Given** 같은 사용자가 다시 로그인한다, **When** 로그인을 마친다, **Then** 새 회원이 생기지 않고 같은 회원으로 들어온다.
4. **Given** 로그인한 사용자, **When** 로그아웃한다, **Then** 서비스 세션이 끝나고 첫 화면으로 돌아온다(자동으로 Google로 넘어가지 않음).
5. **Given** 이메일·비밀번호 로그인, **When** 누군가 시도한다, **Then** 그 방식으로는 들어올 수 없다.

### User Story 2 - 초대 코드를 한 번 입력해야 서비스를 쓴다 (Priority: P1)

Google로 처음 들어온 사람에게는 대시보드 대신 "초대 코드 입력" 화면이 나온다. 팀이나 발표 준비 쪽에서 받은 코드를 넣으면 바로 대시보드가 열리고, 다음부터는 묻지 않는다. 코드가 틀리면 다시 입력할 수 있지만 몇 번 이상 틀리면 잠시 막힌다.

**Why this priority**: 이것 없이 Google 로그인을 열면 아무나 대시보드와 에이전트(유료 호출)를 쓴다. US1과 함께 배포해야 한다.

**Independent Test**: 새 Google 계정으로 로그인 → 초대 코드 화면 → 틀린 코드 거부 → 맞는 코드 → 다시 로그인 없이 대시보드 → 로그아웃·재로그인 때 코드를 다시 묻지 않음. 코드 없이 서버를 직접 부르면 거부.

**Acceptance Scenarios**:

1. **Given** 초대 코드를 아직 입력하지 않은 회원, **When** 로그인한다, **Then** 대시보드 대신 초대 코드 입력 화면이 나온다.
2. **Given** 그 회원, **When** 맞는 코드를 넣는다, **Then** 다시 로그인하지 않고 바로 대시보드를 쓴다.
3. **Given** 그 회원, **When** 틀린 코드를 넣는다, **Then** "코드가 맞지 않는다"고 알리고 통과시키지 않는다.
4. **Given** 짧은 시간에 틀린 코드를 정해진 횟수 넘게 넣는다, **When** 다시 시도한다, **Then** 일정 시간 동안 코드 확인을 받지 않는다.
5. **Given** 코드를 통과한 회원, **When** 나중에 다시 로그인한다, **Then** 코드를 다시 묻지 않는다.
6. **Given** 코드를 통과하지 않은 회원의 로그인 토큰, **When** 대시보드 API나 에이전트를 직접 부른다, **Then** 서버가 거부한다(상태 확인 경로는 예외).

---

### User Story 3 - 운영자가 코드와 회원을 관리한다 (Priority: P2)

A는 초대 코드를 바꿀 수 있고(예: 시연이 끝난 뒤), 회원을 조회하거나 서비스 자격을 뺄 수 있다. Google 연결 정보가 바뀌거나 사라져도 백업으로 다시 등록할 수 있다.

**Why this priority**: 운영 중 필요하지만 첫 로그인 흐름이 돌아가는 데는 필요 없다.

**Independent Test**: 코드를 바꾼 뒤 옛 코드가 거부되고 새 코드가 통과, 이미 통과한 회원은 그대로 쓸 수 있음. 한 회원의 자격을 빼면 그 회원은 다음 토큰 갱신부터 거부.

**Acceptance Scenarios**:

1. **Given** 운영자가 초대 코드를 새 값으로 바꾼다, **When** 새 회원이 옛 코드를 넣는다, **Then** 거부되고 새 코드는 통과한다. 이미 통과한 회원은 영향이 없다.
2. **Given** 운영자가 한 회원의 서비스 자격을 뺀다, **When** 그 회원의 토큰이 갱신된다, **Then** 서버가 거부하고 화면은 다시 초대 코드를 묻는다.
3. **Given** 기존 이메일·비밀번호 계정, **When** 전환을 마친다, **Then** 모두 삭제되어 있고 팀원은 Google로 다시 들어온다.

### Edge Cases

- Google 계정에 이메일이 없거나 확인되지 않은 경우: 회원을 만들지 않거나 서비스 자격을 주지 않는다(Google 계정은 확인된 이메일을 준다고 가정).
- 같은 사람이 다른 Google 계정으로 들어오면 다른 회원이다. 코드를 다시 넣어야 한다.
- 코드를 통과한 직후 이전 토큰(자격 없음)으로 요청이 오면 거부된다. 화면은 통과 직후 새 토큰을 받아서 쓴다.
- 서버가 여러 대일 때 틀린 시도 제한이 서버마다 따로 세어질 수 있다. 코드는 우리 팀과 시연자에게만 알리고, 노출되면 바로 교체한다(FR-013).
- 초대 코드 값이 등록되지 않았거나 읽을 수 없으면 모든 코드 확인이 실패한다(통과시키지 않는다).
- Google 연결 등록 전에 로그인 설정을 "Google만"으로 바꾸면 반영이 실패한다. 사람이 연결을 먼저 등록한다.
- 로컬 개발(인증 끔)에서는 그룹 확인도 건너뛴다. 운영 서버에는 인증 끔을 넣지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

**로그인 (US1)**

- **FR-001**: 로그인 수단은 Google 계정 하나여야 한다. 이메일·비밀번호 로그인은 막혀야 한다.
- **FR-002**: 로그인하지 않은 사용자에게는 서비스 첫 화면(소개 + Google 로그인 버튼)을 보여야 한다. 자동으로 로그인 화면으로 보내지 않는다. 버튼을 누르면 중간 로그인 화면 없이 바로 Google 본인 확인으로 가야 한다(2026-11-20 UX 결정).
- **FR-003**: 처음 로그인한 사용자는 Cognito 회원이 되고, 이메일·이름은 Google 계정 값으로 채워져야 한다. 같은 Google 계정으로 다시 들어오면 같은 회원이어야 한다.
- **FR-004**: 서버(API·에이전트)는 지금처럼 Cognito가 발급한 토큰만 받아야 한다. Google 토큰을 직접 받지 않는다.
- **FR-005**: 로그아웃하면 서비스 세션이 끝나야 한다(지금과 같은 동작).

**초대 코드 (US2)**

- **FR-006**: 서비스 자격(members)이 없는 회원은 로그인 뒤 초대 코드 입력 화면을 봐야 한다.
- **FR-007**: 코드는 서버가 확인해야 한다. 맞으면 그 회원을 members에 넣고, 화면은 다시 로그인 없이 새 토큰을 받아 바로 대시보드를 보여야 한다.
- **FR-008**: 틀린 코드는 거부하고, 한 회원이 10분에 5번 넘게 틀리면 일정 시간 확인을 받지 않아야 한다.
- **FR-009**: 대시보드 API와 에이전트는 members가 아닌 토큰의 요청을 거부해야 한다. 상태 확인 경로와 초대 코드 확인 경로는 예외다.
- **FR-010**: 초대 코드는 운영자가 정한 문구다(한글 가능, 예: 짧은 인사말). 길이 제한은 두지 않고, 틀린 시도 제한(FR-008)과 코드 교체(FR-013)로 막는다. 한글은 입력 환경에 따라 자모가 나뉘어 올 수 있어 같은 글자로 맞춰(NFC) 비교한다.

**비밀값·운영 (US3)**

- **FR-011**: Google 클라이언트 시크릿과 초대 코드는 저장소·Terraform 상태·로그·채팅 어디에도 평문으로 남지 않아야 한다. 사람이 등록하고 Terraform은 이름만 참조한다.
- **FR-012**: Google 연결 정보는 다시 등록할 수 있도록 안전한 곳에 백업되어야 한다.
- **FR-013**: 운영자는 초대 코드를 바꿀 수 있어야 하고, 바꿔도 이미 통과한 회원은 그대로여야 한다.
- **FR-014**: 운영자는 회원의 서비스 자격을 뺄 수 있어야 한다.
- **FR-015**: 전환 때 기존 이메일·비밀번호 회원은 모두 삭제하고 팀원에게 새 로그인 방법을 알린다.
- **FR-016**: 서버 로그에는 코드 확인 성공·실패와 회원 식별자만 남기고 입력한 코드 값은 남기지 않아야 한다.

### Key Entities

- **회원**: Cognito가 관리하는 사용자. 식별자(sub), 이메일, 이름, 로그인 공급자(Google). 서비스 자격 여부는 그룹으로 표시한다.
- **members 그룹**: 초대 코드를 통과한 회원의 묶음. 토큰에 그룹 이름이 실려 서버가 매 요청 확인한다.
- **초대 코드**: 하나의 공유 비밀 값. 사람이 등록하고 바꾼다.
- **Google 연결**: Cognito에 등록한 Google 로그인 공급자(클라이언트 ID·시크릿). 사람이 등록·백업한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 팀원이 대시보드 주소를 열고 Google 계정을 고른 뒤 30초 안에 화면에 들어온다(이미 통과한 회원).
- **SC-002**: 새 회원이 초대 코드를 넣고 1분 안에 대시보드를 쓴다. 다시 로그인하지 않는다.
- **SC-003**: 코드를 통과하지 않은 회원의 토큰으로 API·에이전트를 부르면 100% 거부된다.
- **SC-004**: 이메일·비밀번호로는 로그인할 수 없다(시도 100% 실패).
- **SC-005**: 저장소·Terraform 상태 파일·서버 로그를 검색해 Google 시크릿과 초대 코드 값이 0건 나온다.
- **SC-006**: 초대 코드를 바꾼 뒤 옛 코드는 100% 거부되고, 기존 회원은 계속 쓴다.
- **SC-007**: 추가 비용이 없다(Cognito 무료 범위, 새 유료 자원 없음).

## Assumptions

- 팀원과 시연자는 모두 Google 계정이 있다.
- Google 동의 화면은 기본 범위(openid, email, profile)만 쓰므로 Google 검수 없이 공개 상태로 쓸 수 있다. 시험 상태로 두면 등록한 시험 사용자만 로그인된다.
- Cognito의 "관리자만 계정 생성" 설정은 Google로 들어오는 회원 생성을 막지 않는다(plan에서 확인).
- 토큰을 갱신하면 바뀐 그룹이 새 토큰에 반영된다(plan에서 확인).
- 대시보드 앱과 에이전트에 아직 회원별 데이터가 없어 기존 회원 삭제로 잃는 것이 없다.
- 초대 코드 입력 화면은 지금의 최소 화면에 A가 붙이고, D가 대시보드를 만들 때 디자인을 맞춘다.
