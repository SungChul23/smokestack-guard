# Feature Specification: 합성 데이터 v2 전환·재수집과 학습 스냅샷 알림

**Feature Branch**: `73-a-합성-데이터-v2-전환재수집1030silver-재계산학습-스냅샷-알림`

**Created**: 2026-11-20

**Status**: 운영 중 (2026-11-20 v2 전환·다시 채우기·Silver 재계산 완료, 알림 2026-11-21 05:00부터). 확인: SC-001·SC-002·SC-003(`OTHER` 0개), 양성 1:1(tasks 확인 결과). 남음: SC-004(첫 메일)

**Input**: User description: "B의 합성 생성기 v2(PR #72, OTHER 세분화·양성 1:1·경로 tms_synthetic_train_v2/)로 AWS 합성 적재를 바꾸고, 10/30부터 다시 채워 Bronze에 쌓고, Silver 합성 표를 재계산한다. E가 매번 찾던 학습용 스냅샷 ID(Silver·ML-ready 2개)를 실측·합성 모두 매일 메일로 알려 준다."

**관련 이슈**: #73 · **관련**: [011-synthetic-train-s3-ingest](../011-synthetic-train-s3-ingest/spec.md) (합성 적재) · [008-ktms-silver-pipeline](../008-ktms-silver-pipeline/spec.md) (매일 Silver·ML-ready) · [010](../010-ktms-ml-ready-contract-check/spec.md) (계약 검사) · B PR #72 (생성기 v2)

## 배경

B가 학습용 합성 생성기를 v2로 바꿨다(PR #72, 2026-11-20 머지).

| | v1 (지금 AWS에서 운영) | v2 |
|---|---|---|
| 모양 | 6종, 그중 `OTHER`가 가장 많음 | `OTHER`를 진입 전 2시간 곡선으로 4종(하강·근접 유지·불규칙 상승·진동)으로 나눔, `NEAR_MISS`(80~89.9%, 기본 0) 추가 → 10종 |
| 하루 양 | 에피소드 NOx 218·SOx 57, 양성이 설계보다 1.5~1.8배 | 에피소드 약 158, 양성 행이 실측 적격 양성과 1:1(NOx 약 254, SOx 약 82) |
| 원본 경로 | `tms_synthetic_train/` | `tms_synthetic_train_v2/` (v1 경로에는 쓰지 않음) |

AWS의 합성 적재(011)와 Silver 합성 표(`tms_silver2.ktms_synth`, `ktms_synth_ml_ready`)는 아직 v1이다. 학습에 v2를 쓰려면 적재를 v2로 바꾸고, 합성 기간 처음(10/30)부터 다시 채우고, Silver를 다시 계산해야 한다.

또 E는 학습할 때 "계약 검사를 통과한 최신 스냅샷 ID"를 Silver·ML-ready 표마다 Athena로 찾는다. 매일 같은 일을 반복하므로, 매일 아침 실측·합성의 쓸 수 있는 스냅샷을 메일로 받게 한다.

```
[수집]   30분마다 합성 적재 → tms_synthetic_train_v2/          (v1 경로·데이터는 그대로 보존)
[다시 채우기] 10/30 ~ 오늘 v2 원본
[Silver] 합성 표를 10/30부터 v2로 다시 계산(같은 표, 새 버전) → 계약 검사
[알림]   매일 아침: 실측·합성 각각 최근 통과 실행의 스냅샷 2개 + 확정 범위 → E 메일
```

**같은 표를 다시 계산하는 이유**: 합성 표는 버전(스냅샷)을 쌓는 형식이라, 다시 계산하면 새 버전이 생기고 v1은 이전 버전으로 남는다. 표 이름을 바꾸면 카탈로그·권한·계약 검사·E의 읽기 코드가 모두 바뀐다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 합성 적재가 v2로 30분마다 쌓인다 (Priority: P1)

전환 뒤 30분마다 v2 생성기로 만든 합성 스냅샷이 v2 경로에 쌓인다. v1 경로에는 더 쓰지 않고, 이미 쌓인 v1 원본은 그대로 남는다.

**Why this priority**: 이후 모든 단계(다시 채우기, Silver)의 원본이다.

**Independent Test**: 전환 뒤 다음 두 번의 정기 실행에서 v2 경로에 완성 표시가 있는 스냅샷이 생기고, 메타에 `gen-train-v2`가 있고, v1 경로의 객체 수가 늘지 않는다.

**Acceptance Scenarios**:

1. **Given** 전환 완료, **When** 정기 실행 시각이 된다, **Then** v2 경로에 그 슬롯의 스냅샷·메타·manifest·완성 표시가 생기고 생성기 버전이 `gen-train-v2`다.
2. **Given** 전환 완료, **When** 실행이 끝난다, **Then** v1 경로에는 새 객체가 없다.
3. **Given** v2 참조 통계가 없거나 버전이 다르다, **When** 실행한다, **Then** 아무것도 쓰지 않고 실패해 운영 알림이 온다(기존 규칙).
4. **Given** 하루 점검(06:00), **When** 전날 v2 슬롯 48개를 확인한다, **Then** 모자라면 알린다.

---

### User Story 2 - 10/30부터 다시 채우고 Silver 합성 표를 다시 계산한다 (Priority: P1)

운영자가 10/30부터 오늘까지 v2 원본을 다시 채우고, Silver·ML-ready 합성 표를 그 범위로 다시 계산한다. 계약 검사를 통과한 새 버전에는 v1 데이터가 섞이지 않는다.

**Why this priority**: E가 v2로 학습하려면 전 기간이 v2여야 한다.

**Independent Test**: 다시 채운 뒤 날짜마다 v2 슬롯 48개, 다시 계산한 Silver 최신 버전에서 v1에만 있는 모양(`OTHER`) 굴뚝 0개, 계약 검사 통과.

**Acceptance Scenarios**:

1. **Given** v2 적재가 돈다, **When** 10/30~오늘을 다시 채운다, **Then** 날짜마다 슬롯 48개가 v2 경로에 있다(이미 있는 슬롯은 건너뜀).
2. **Given** v2 원본, **When** 합성 Silver·ML-ready를 10/30부터 다시 계산한다, **Then** 최신 버전의 굴뚝 모양이 v2 10종 안에만 있고 `OTHER`는 0개다.
3. **Given** 다시 계산한 버전, **When** 계약 검사를 한다, **Then** 통과하고 그 스냅샷이 학습용으로 알려진다.
4. **Given** 다시 계산 뒤, **When** v1 버전 스냅샷 ID로 읽는다, **Then** v1 데이터가 그대로 보인다(지우지 않음).
5. **Given** 매일 03:30 합성 갱신, **When** 다음 날 돈다, **Then** v2 원본으로 최근 이틀을 다시 계산한다.

---

### User Story 3 - 매일 아침 학습 스냅샷 메일 (Priority: P2)

E는 매일 아침 메일 한 통으로 실측·합성 각각의 "계약 검사를 통과한 최신 스냅샷"(Silver 표 하나, ML-ready 표 하나)과 확정 범위(D−2까지), 그리고 전날·전전날 스냅샷을 받는다. 메일에는 바로 붙여 쓸 수 있는 읽기 예시가 있다.

**Why this priority**: 반복 수작업을 없애는 편의 기능이다. v2 데이터(US1·US2)가 먼저.

**Independent Test**: 다음 날 아침 메일이 오고, 메일의 스냅샷 ID로 표를 읽으면 행이 나오며, 그 ID가 그날 계약 검사 통과 기록과 같다.

**Acceptance Scenarios**:

1. **Given** 그날 실측·합성 갱신과 계약 검사가 모두 통과, **When** 알림 시각이 된다, **Then** 메일에 출처별(실측·합성) 최근 3회 실행의 날짜·Silver 스냅샷·ML-ready 스냅샷·확정 범위가 있고 맨 위가 최신이다.
2. **Given** 그날 한 출처의 검사가 실패했거나 실행이 없다, **When** 알림을 보낸다, **Then** 그 출처는 "오늘 새 스냅샷 없음(사유)"으로 표시하고 마지막으로 통과한 스냅샷을 최신으로 보여 준다.
3. **Given** 메일, **When** 받는 사람이 본다, **Then** 표 이름과 스냅샷 ID로 읽는 예시 한 줄이 있다.
4. **Given** 수신 주소, **When** 저장소를 본다, **Then** 이메일 주소가 어디에도 없다.

### Edge Cases

- 전환 순간과 다시 계산 사이에는 Silver가 아직 v1이다. 그 사이 알림의 합성 스냅샷은 v1이므로, 전환 공지 전까지 E는 새 합성 스냅샷을 쓰지 않는다(운영 안내).
- 다시 채우기가 한 번에 끝나지 않으면 기간을 나눠 실행한다. 이미 쓴 슬롯은 건너뛰므로 다시 실행해도 안전하다.
- v2 생성기는 하루 양이 v1보다 적다. 합성 Silver 행 수가 줄어드는 것은 정상이다.
- 실측 표 스냅샷은 이 기능에서 바뀌지 않는다(알림만 한다).
- 알림 시각에 03:30 합성 갱신이 아직 안 끝났으면, 합성은 전날 통과분이 최신으로 나온다.
- v1 원본·이전 스냅샷은 지우지 않는다(원본 버킷 규칙).

## Requirements *(mandatory)*

### Functional Requirements

**v2 적재 (US1)**

- **FR-001**: 합성 적재는 B의 v2 생성기를 수정 없이 쓰고, v2 경로(`tms_synthetic_train_v2/`)에만 써야 한다. v1 경로에는 쓰지 않는다.
- **FR-002**: 적재 역할의 쓰기 권한은 v2 경로로 바꿔야 한다(v1 경로 쓰기 권한 없음).
- **FR-003**: v2 참조 통계는 사람이 v2 경로 아래 참조 통계 위치에 올린다(실제 굴뚝명 포함, 저장소에 넣지 않음).
- **FR-004**: 정기 실행·다시 채우기·하루 점검의 동작(슬롯 계산, 완성 표시, 건너뛰기, 알림)은 그대로여야 한다.

**다시 채우기·재계산 (US2)**

- **FR-005**: 10/30~오늘의 v2 원본을 다시 채울 수 있어야 한다(기존 다시 채우기 명령, 31일 이내 단위).
- **FR-006**: 합성 Silver·ML-ready는 v2 원본을 읽어야 하고, 10/30~D−2를 한 번에 다시 계산해 새 버전을 만들어야 한다. 표 이름은 그대로다.
- **FR-007**: 다시 계산한 최신 버전에는 v1 모양(`OTHER`) 굴뚝이 없어야 하고 계약 검사를 통과해야 한다.
- **FR-008**: v1 원본과 이전 버전은 지우지 않는다.

**학습 스냅샷 알림 (US3)**

- **FR-009**: 매일 정해진 시각(실측 03:00·합성 03:30 갱신과 검사가 끝난 뒤)에 메일을 한 통 보내야 한다.
- **FR-010**: 메일에는 실측·합성 각각 최근 3회 실행의 날짜, Silver 스냅샷 ID, ML-ready 스냅샷 ID, 확정 범위(첫날 ~ D−2), 계약 검사 결과가 있어야 한다. 최신이 맨 위다.
- **FR-011**: 스냅샷 ID는 계약 검사를 통과한 실행의 기록에서 가져와야 한다(통과하지 않은 실행은 "최신"으로 쓰지 않음).
- **FR-012**: 메일에는 스냅샷 ID로 표를 읽는 예시가 있어야 한다.
- **FR-013**: 수신 주소는 배포할 때 사람이 넣고 저장소·설정 파일·로그에 남기지 않는다. 받는 사람이 구독을 확인해야 받는다.
- **FR-014**: 알림을 손으로 다시 보낼 수 있어야 한다(같은 내용).

### Key Entities

- **합성 원본(v2)**: `tms_synthetic_train_v2/` 아래 30분 슬롯 스냅샷, manifest, 참조 통계.
- **실행 기록**: 매일 Silver·ML-ready·계약 검사가 남기는 기록. 범위·결과·스냅샷 ID를 담는다.
- **학습 스냅샷 알림**: 출처(실측·합성)별 최근 3회의 (실행 날짜, Silver 스냅샷, ML-ready 스냅샷, 확정 범위, 검사 결과).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 전환 뒤 정기 실행의 100%가 v2 경로에 쓰고, v1 경로 객체 수는 늘지 않는다.
- **SC-002**: 10/30~오늘 모든 날짜에 v2 슬롯 48개가 있다.
- **SC-003**: 다시 계산한 합성 ML-ready 최신 버전에서 `OTHER` 굴뚝 0개, 계약 검사 통과.
- **SC-004**: 전환 다음 날부터 매일 아침 메일이 오고, 메일의 스냅샷 ID가 그날 통과 기록과 100% 같다.
- **SC-005**: E가 학습용 스냅샷을 찾는 데 Athena 조회가 필요 없다(메일 한 통으로 충분).
- **SC-006**: 저장소에서 수신 이메일 주소 검색 결과 0건.
- **SC-007**: 실측 수집·실측 Silver·대시보드 적재에 영향 없음(누락률·실측 스냅샷 변화 없음).

## Assumptions

- B의 v2 생성기(PR #72)는 머지됐고 그대로 쓴다. 참조 통계 버전(`ref-1030-1110`)과 seed는 v1과 같다.
- 합성 기간은 10/30부터다(v1과 같음).
- 알림 수신자는 E이고, 주소는 사람이 배포 때 넣는다. 필요하면 수신자를 더할 수 있다.
- 확정 범위는 매일 최근 이틀을 다시 계산하는 규칙(008)에 따라 D−2까지다.
- 다시 채우기·재계산 명령은 기존 011·008 명령을 쓴다(A가 실행).
- 범위 밖: v1 원본·옛 스냅샷 삭제, 생성량·모양 비중·NEAR_MISS 조정(B·E), RECONTACT 시나리오, 학습 코드 변경(E).
