# Feature Specification: 대시보드용 K-TMS 관측 RDS 적재

**Feature Branch**: `62-a-대시보드용-k-tms-관측-rds-적재-파이프라인-30분-매일-정정`

**Created**: 2026-11-19

**Status**: Draft

**Input**: User description: "D의 대시보드(지도·시계열)와 에이전트가 읽을 K-TMS 관측값을 RDS PostgreSQL에 적재한다(A 담당, D는 적재하지 않음). 30분마다 최근 원본에 C의 Silver 규칙을 그대로 적용해 덮어쓰고(늦게 온 정정 포함), 매일은 RDS 안에서 일일 요약과 매핑 점검을 한다. 추론과 분리한 별도 파이프라인. 상태 행 값은 null, 굴뚝 키는 원본 조합, site_id는 ref에서 연결. 범위 밖: 추론·예측 테이블, 에이전트 도구·RAG 색인, Silver 계약 변경."

**관련 이슈**: #62 · **관련**: [008-ktms-silver-pipeline](../008-ktms-silver-pipeline/spec.md) (매일 갱신, Silver 규칙) · [009-service-infra](../009-service-infra/spec.md) (RDS·VPC·베스천) · [007-ktms-bronze-success-marker](../007-ktms-bronze-success-marker/spec.md) (`_SUCCESS`) · D의 서비스용 RDS 테이블 제안(2026-11-18)과 A 회신(2026-11-19)

## 배경

D의 대시보드는 전국 굴뚝 지도(최근 24시간)와 굴뚝별 시계열을 보여 주고, 에이전트는 "전국에서 가장 높았던 굴뚝", "어제 평균", "그래프가 왜 비었나" 같은 질문에 답한다. 둘 다 K-TMS 관측값을 빠르게, 조회마다 과금 없이 읽어야 한다.

정본 Silver(`tms_silver2.ktms`)는 매일 03:00에 한 번 만들고 **진행 중인 오늘의 행을 넣지 않는다**(008). 그대로 복사하면 지도는 항상 어제까지만 보인다. 조회마다 S3를 Athena로 읽으면 몇 초가 걸리고 스캔한 만큼 과금된다.

그래서 서비스용 복사본을 RDS에 두고 채운다. 정본은 계속 S3 Silver이고, 이 기능은 학습용 Silver 파이프라인(008)과 별개로 돌며 Silver를 읽지 않는다.

```
[30분마다]  Bronze 최근 몇 시간 (_SUCCESS만) → C의 Silver 규칙 그대로 → 적재용 정리 → RDS 관측 표 (키 기준 덮어쓰기)
[매일]      RDS 안에서 최근 2일 일일 요약 계산 → 매핑 점검 → (처음 본 사업장 이름이면) 운영 메일
[필요할 때] 날짜를 지정해 원본에서 다시 채우기 (30분 경로와 같은 방식, 하루 단위)
[처음 한 번] D의 사업장 목록 → 기준 정보 표(사업장·이름 이력·굴뚝·상태 코드)
[읽을 때]   화면·에이전트 서버가 관측 표와 기준 정보 표를 이어서 사업장 코드·좌표·화면 id를 붙인다
```

**추론과 분리하는 이유**: 추론은 E(모델 형식·입력 열·임계값)와 D(경고 단계)의 결정을 기다려야 하지만 관측 적재는 지금 만들 수 있다. 모델 호출이 실패해도 지도에는 측정값이 계속 나와야 한다. 추론은 나중에 이 적재 결과를 입력으로 쓸 수 있다.

**매일 다시 계산하지 않는 이유**: API는 굴뚝마다 "지금 보여 줄 최신 측정"만 주므로, 과거 칸의 변화(상태 문구 변경, 확인 중이던 값 채움)도 반드시 새 스냅샷으로 들어온다. 30분 경로가 새로 받은 스냅샷을 측정 시각과 상관없이 모두 반영하면 관측 표는 그대로 최신이 된다. 빠진 실행은 범위를 겹쳐 읽어 다음 실행이 메우고, 긴 공백은 사람이 다시 채운다.

**Silver 규칙을 그대로 쓰는 이유**: API는 같은 30분 측정값을 10분마다 반복해서 주고, 큰 값에 천 단위 쉼표가 있고, 숫자 대신 상태 문구(미수신, 보수중 등)가 오고, 같은 조합이 한 스냅샷에 두 번 오기도 한다. C의 규칙이 이 모두를 처리한다. 새로 짜면 규칙이 두 벌이 되어 학습 데이터·에이전트 답과 값이 어긋날 수 있다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 지도와 시계열이 오늘 값까지 30분 안에 보인다 (Priority: P1)

D의 화면이 RDS 관측 표를 읽으면, 가장 최근에 확정된 30분 측정값까지 들어 있다. 같은 시각의 값이 나중에 바뀌어 오면(상태 문구가 바뀌거나 확인 중이던 값이 채워짐) 다음 적재에서 바뀐 값으로 덮인다.

**Why this priority**: 이 기능의 목적이다. 오늘 값이 없으면 지도와 시계열을 만들 수 없다.

**Independent Test**: RDS를 켠 상태에서 30분 적재를 한 번 실행하고, 가장 최근 `_SUCCESS` 스냅샷의 측정 시각이 관측 표에 있는지, 행 수가 같은 범위를 C의 규칙으로 직접 변환한 결과와 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 10:40 KST에 측정 10:00 슬롯이 담긴 스냅샷이 확정됨, **When** 그다음 30분 적재가 돌면, **Then** 관측 표에 측정 10:00 행(NOx·SOx)이 생긴다.
2. **Given** 같은 범위로 적재를 두 번 실행, **When** 표를 비교하면, **Then** 행 수와 값이 같다(중복 행 없음).
3. **Given** 사흘 전 측정 시각의 상태가 "미수신"에서 "기기점검"으로 바뀐 스냅샷이 새로 들어옴, **When** 30분 적재가 돌면, **Then** 그 행의 상태가 "기기점검"으로 바뀐다.
4. **Given** 어떤 굴뚝의 NOx 칸에 "보수중"이 옴, **When** 적재하면, **Then** 그 행의 측정값은 비어 있고(0이 아님) 상태는 보수중이다.
5. **Given** 쓰다 만 스냅샷 폴더(`_SUCCESS` 없음), **When** 적재하면, **Then** 그 폴더는 읽지 않는다.

---

### User Story 2 - 매일 일일 요약이 생기고 관측이 정본과 같게 유지된다 (Priority: P1)

매일 새벽, 최근 2일의 굴뚝·물질별과 전국 일일 요약이 관측 표로 계산된다. 에이전트는 기간 질문을 요약 표로 답한다. 30분 경로가 빠지지 않았다면 확정된 날의 관측은 정본 Silver와 같다.

**Why this priority**: 기간 질문용 요약이 있어야 에이전트가 S3를 훑지 않는다. 정본과 같아야 화면 값과 학습 데이터가 어긋나지 않는다.

**Independent Test**: 매일 단계를 실행한 뒤 요약 값이 관측 표로 직접 계산한 값과 같은지, 확정된 날의 관측이 Silver와 행 단위로 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 30분 경로가 빠짐없이 돈 날, **When** 그날이 확정된 뒤(D−2) Silver와 비교하면, **Then** 관측 행(NOx·SOx)이 Silver와 같다.
2. **Given** 매일 단계 실행, **When** 관측 표를 보면, **Then** 관측 행은 하나도 바뀌지 않는다(요약과 점검 기록만 쓴다).
3. **Given** 어떤 굴뚝의 하루 48칸 중 40칸이 정상, 5칸이 미수신, 3칸이 행 없음, **When** 요약하면, **Then** 정상 40칸으로 평균·최댓값을 내고, 상태별 칸 수와 행 없는 칸 수를 따로 센다.
4. **Given** 03:00 Silver 갱신이 실패함, **When** 매일 단계가 돌면, **Then** 영향 없이 요약이 계산된다(Silver와 독립).

---

### User Story 3 - 화면이 굴뚝을 사업장 코드·좌표와 연결해 보여 준다 (Priority: P1)

D의 화면은 CleanSYS 사업장 코드와 좌표로 지도를 그린다. 관측 데이터에는 이름(지역·사업장·굴뚝 번호)만 있으므로, 기준 정보 표가 둘을 잇는다. 연결이 안 된 굴뚝도 관측은 남고, 사업장 이름이 바뀌면 사람이 한 줄 추가해 과거 이력까지 이어진다.

**Why this priority**: 연결이 없으면 관측값을 지도에 찍을 수 없다.

**Independent Test**: D의 사업장 목록으로 기준 정보를 채운 뒤, 관측 표에 나온 (지역, 사업장) 중 연결된 비율과 연결되지 않은 목록을 확인한다. 이름 변경 사례를 하나 추가하고, 옛 이름과 새 이름의 관측이 같은 사업장 코드로 함께 조회되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** D의 목록 909개 사업장, **When** 기준 정보를 채우고 관측과 이으면, **Then** D가 확인한 대로 대부분(904개)이 자동으로 연결되고, 나머지는 연결 안 됨으로 남는다.
2. **Given** 기준 정보에 없는 새 (지역, 사업장)이 관측에 나타남, **When** 매일 단계가 돌면, **Then** 운영 메일로 그 이름이 한 번 알려지고 관측은 그대로 저장된다.
3. **Given** 사람이 이름 이력에 한 줄을 추가함, **When** 그 사업장을 조회하면, **Then** 관측 표를 다시 쓰지 않고도 옛 이름과 새 이름의 기록이 함께 나온다.

---

### User Story 4 - RDS를 껐다 켜도 명령 하나로 다시 채운다 (Priority: P2)

RDS는 비용 때문에 평소 꺼 둔다. 처음 만들 때나 껐다 켤 때 운영자가 날짜 범위를 지정한 명령 하나로 관측 표와 요약을 10/30부터 다시 채운다. 몇 번 실행해도 결과가 같다.

**Why this priority**: RDS는 정본이 아니라 언제든 다시 만들 수 있는 복사본이어야 한다. 그래야 끄고 켜는 운영이 안전하다.

**Independent Test**: 빈 RDS에 다시 채우기를 실행한 뒤 날짜별 관측 행 수가 Silver(확정 날짜)와 같은지 확인한다. 같은 명령을 한 번 더 실행해 결과가 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 빈 RDS, **When** 10/30부터 오늘까지 다시 채우면, **Then** 날짜마다 원본에 Silver 규칙을 적용해 채워지고, 확정된 날(D−2까지)은 Silver와 행 수가 같다.
2. **Given** RDS가 꺼져 있음, **When** 30분 적재나 매일 단계가 돌면, **Then** 실패 알림 없이 건너뛰었다는 기록만 남긴다.
3. **Given** 다시 채우기를 같은 범위로 두 번 실행, **When** 비교하면, **Then** 결과가 같다.

---

### User Story 5 - D 앱이 쓸 공간과 계정이 준비된다 (Priority: P3)

D 앱은 사용자·대화(`app`)와 법령 문서 벡터(`rag`)를 같은 DB에 쓴다. A가 이 공간과 앱 전용 계정을 만들어 두면 D는 채우기만 한다. 앱 계정은 관측과 기준 정보는 읽기만, 사용자·대화 공간에만 쓴다.

**Why this priority**: D의 앱 작업이 시작되려면 필요하지만, 관측 적재(P1)와는 독립이다.

**Independent Test**: 앱 계정으로 관측 표 쓰기를 시도해 거부되는지, 사용자·대화 공간 쓰기는 되는지, 문서 벡터 공간에서 벡터 검색 확장을 쓸 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 앱 계정, **When** 관측 표나 기준 정보 표에 쓰면, **Then** 거부된다.
2. **Given** 앱 계정, **When** 사용자·대화 공간에 쓰면, **Then** 된다.

---

### Edge Cases

- **RDS가 꺼져 있음:** 두 경로 모두 건너뛰고 기록만 남긴다. 켤 때 다시 채우기로 복구한다.
- **원본 폴더에 `_SUCCESS`가 없음:** 읽지 않는다(007). 다음 실행에서 확정되면 들어온다.
- **수집 공백:** 원본이 없는 30분 칸은 행이 없다. 요약에서 "행 없음" 칸 수로 센다.
- **같은 (지역, 사업장, 굴뚝 번호)가 한 스냅샷에 두 번, 값이 다름:** C의 규칙대로 그 물질은 `ambiguous`(값 없음)다. 한국주강 같은 동명 사업장은 사람이 기준 정보에서 따로 다룬다.
- **허용기준이 하루 중 바뀜:** 요약에 그날 기준값 범위(최소·최대)를 남긴다.
- **원래 측정하지 않는 물질(`not_monitored`):** 결측이 아니라 미측정으로 센다.
- **5종 외 새 상태 문구:** C의 규칙대로 `other`로 남는다. 원문은 Silver에 없어 복원하지 않는다.
- **03:00 Silver 갱신이 실패하거나 늦음:** 이 기능은 Silver를 읽지 않으므로 영향이 없다. 매일 단계는 같은 날 두 번 돌아도 결과가 같다.
- **30분 실행이 몇 번 빠짐:** 다음 실행이 겹친 범위(최근 4시간)로 메운다. 그보다 긴 공백은 사람이 그 날짜를 다시 채운다.
- **30분 적재와 다시 채우기가 겹침:** 두 실행이 같은 행을 쓰더라도 같은 규칙으로 덮어쓰므로 결과가 같다. 매일 단계는 관측 행을 쓰지 않는다.
- **이름이 바뀐 사업장:** 새 이름은 연결 안 됨으로 저장되고 알림이 간다. 사람이 이력에 추가하면 이어진다.

## Requirements *(mandatory)*

### Functional Requirements

**30분 경로**

- **FR-001**: 시스템은 30분마다 K-TMS 원본의 최근 몇 시간(최소 3시간)을 읽어 관측 표에 반영해야 한다. 읽는 범위는 수집 시각 기준이며, `_SUCCESS`가 있는 폴더만 읽는다.
- **FR-002**: 변환은 C의 Silver 규칙(원본 읽기·정제 함수)을 **수정 없이** 호출해야 한다. 이 기능은 규칙을 새로 구현하지 않는다.
- **FR-003**: 적재용 정리는 다음만 한다. (a) 굴뚝 키 = `지역|사업장|굴뚝번호`(ML-ready의 `stack_code`와 같은 규칙), (b) 상태 문자열 → 상태 번호, (c) NOx·SOx만 남김. 측정값이 없으면 비워 두고(null) 0으로 채우지 않는다.
- **FR-004**: 관측 표는 (굴뚝 키, 물질, 측정 시각)이 키이고, 적재는 키 기준으로 없으면 넣고 있으면 덮어써야 한다.
- **FR-005**: 30분 경로는 측정 시각으로 행을 거르지 않아야 한다. 새 스냅샷에 들어온 며칠 전 시각의 정정도 반영된다.
- **FR-006**: RDS가 꺼져 있으면 30분 경로는 실패 없이 건너뛰고 건너뛴 사실을 기록해야 한다.

**매일 경로**

- **FR-007**: 매일 단계는 하루 한 번 새벽(전날 마지막 값의 지연이 끝난 뒤, 03:00 갱신과 같은 기준)에 실행되어야 한다. 원본도 Silver도 읽지 않고 RDS의 관측 표만으로 계산한다.
- **FR-008**: 매일 단계는 관측 행을 바꾸지 않아야 한다. 정정은 30분 경로(FR-005)와 다시 채우기(FR-015)만 한다.
- **FR-009**: 매일 단계는 굴뚝·물질·일별 요약과 전국·물질·일별 요약을 다시 계산해야 한다. 대상 날짜는 최근 2일과, 직전 매일 단계 이후 관측 행이 바뀐 날짜(늦게 온 정정이 들어온 과거 날짜)다.
  - 평균·최댓값·최솟값과 그 시각, 90% 이상·100% 이상·100% 초과 칸 수는 정상(`ok`) 행만으로 계산한다. 측정값 0은 포함한다.
  - 상태별 칸 수, 미측정 칸 수, 행 없음 칸 수(하루 48칸 기준), 그날 허용기준 범위를 함께 남긴다.
- **FR-010**: 매일 단계는 그날 관측에 나타났지만 기준 정보에 없는 (지역, 사업장)을 찾아, 처음 나타난 이름만 운영 알림으로 보내야 한다. 같은 이름을 매일 반복해 보내지 않는다. 이미 아는 사업장에 새 굴뚝이 나타나면 굴뚝 목록에 자동으로 추가하고 점검 기록에만 남긴다(메일 없음).
- **FR-011**: RDS가 꺼져 있으면 매일 단계도 실패 없이 건너뛰어야 한다. 이 기능은 기존 03:00 Silver 갱신에 아무 영향을 주지 않아야 한다.

**기준 정보와 연결**

- **FR-012**: 기준 정보는 사업장(사업장 코드, 표기, 지역, 주소, 좌표), 이름 이력(지역·사업장 이름 → 사업장 코드, 유효 기간), 굴뚝(굴뚝 키 → 사업장 코드·굴뚝 번호·화면 id), 상태 코드표(번호, 상태, 원문, 화면 표시, 설명, 평균 포함 여부)를 담아야 한다.
- **FR-013**: 관측 표와 요약 표에는 사업장 코드나 화면 id를 저장하지 않는다. 연결은 읽을 때 기준 정보로 한다.
- **FR-014**: 기준 정보 초기 적재는 D가 준 사업장 목록으로 사람이 실행하는 명령 하나로 해야 하고, 다시 실행해도 결과가 같아야 한다.

**다시 채우기**

- **FR-015**: 운영자는 날짜 범위를 지정해 관측 표와 요약을 다시 채울 수 있어야 한다. 날짜마다 30분 경로와 같은 방식(원본 → C의 규칙 → 키 기준 덮어쓰기)으로 그 하루를 채우며, 확정된 날짜는 Silver와 같은 결과가 나온다.
- **FR-016**: 다시 채우기는 같은 범위로 여러 번 실행해도 결과가 같아야 한다.

**DB 구조와 계정**

- **FR-017**: DB 구조(스키마, 표, 인덱스, 벡터 검색 확장)는 저장소의 마이그레이션 파일로 만들고, 같은 파일로 빈 DB를 다시 만들 수 있어야 한다. 사용자·대화(`app`)와 문서 벡터(`rag`) 공간은 구조만 만들고 채우지 않는다.
- **FR-018**: 앱 전용 계정은 관측·기준 정보·문서 벡터를 읽기만 하고, 사용자·대화 공간에만 쓸 수 있어야 한다. 적재 작업은 별도 권한으로 실행한다.
- **FR-019**: 적재 작업의 권한은 최소 범위여야 한다. 원본 경로는 읽기만 하고, 원본 버킷에 쓰지 않는다.
- **FR-020**: 비밀번호나 접속 정보 값은 코드·설정·문서·로그에 쓰지 않는다.

**운영**

- **FR-021**: 30분 경로와 매일 단계가 실패하면 운영 알림이 가야 한다. 실행마다 읽은 범위, 반영한 행 수, 소요 시간, 건너뜀 여부를 요약으로 남긴다.
- **FR-022**: 이 기능은 수집 경로(수집 함수, 스케줄, 원본 쓰기)를 바꾸지 않는다.

### Key Entities

- **관측(30분)**: 굴뚝 키 × 물질(NOx·SOx) × 측정 시각 한 칸. 측정값(없으면 비움), 허용기준, 기준 대비 비율, 상태 번호, 적재 출처(30분 경로 / 다시 채우기)와 적재 시각.
- **굴뚝·일 요약**: 굴뚝 키 × 물질 × KST 날짜. 정상 행 통계, 상태별·미측정·행 없음 칸 수, 기준값 범위, 계산 시각.
- **전국·일 요약**: 물질 × KST 날짜. 전국 최고값과 그 굴뚝·시각, 평균, 보고한 굴뚝 수, 90% 이상·100% 초과 굴뚝 수.
- **사업장**: CleanSYS 사업장 코드, 표기, 지역, 주소, 좌표, 연결 상태.
- **이름 이력**: (지역, 사업장 이름) → 사업장 코드, 유효 기간, 확인한 사람, 메모.
- **굴뚝**: 굴뚝 키 → 사업장 코드, 굴뚝 번호, 화면 id(`KS-…`), 충돌 표시.
- **상태 코드**: 번호, 상태(`ok`, `stopped`, `checking`, `no_signal`, `maintenance`, `inspection`, `not_monitored`, `ambiguous`, `other`), 원문, 화면 표시, 설명, 평균 포함 여부.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: RDS가 켜져 있는 동안 새 측정 슬롯이 확정되고 **40분 안에** 관측 표에 나타난다(30분 주기 + 실행 시간).
- **SC-002**: 같은 범위를 두 번 적재하면 결과가 100% 같다. 30분 경로, 매일 단계, 다시 채우기 모두 해당한다.
- **SC-003**: 30분 경로가 빠짐없이 돈 날과 다시 채운 날은, 확정(D−2) 뒤 관측(NOx·SOx)이 Silver와 행 단위로 100% 일치한다. 매일 단계 전후로 관측 행 변화는 0건이다.
- **SC-004**: 일일 요약 값이 관측 표로 직접 계산한 값과 같다(표본 굴뚝·날짜 10개 이상).
- **SC-005**: 상태 문구가 온 칸의 측정값이 0으로 저장된 경우가 0건이다.
- **SC-006**: 빈 DB에 10/30부터 다시 채우기를 마치는 데 1시간이 걸리지 않고, 날짜별 행 수가 Silver(확정 날짜)와 같다.
- **SC-007**: 관측에 나타난 (지역, 사업장) 중 기준 정보로 연결된 비율이 D의 확인 결과와 같은 수준(909개 중 904개 이상)이고, 연결 안 된 이름은 모두 운영 알림이나 점검 기록에 나온다.
- **SC-008**: 앱 계정으로 관측·기준 정보에 쓰기를 시도하면 100% 거부된다.
- **SC-009**: 화면이 한 굴뚝의 하루 시계열(NOx·SOx, 96칸)과 연결 정보를 1초 안에 받는다.

## Assumptions

- **RDS는 009에서 만든 것을 쓴다.** PostgreSQL 16, 벡터 검색 확장 사용 가능, 프라이빗 서브넷, 평소 꺼 둠. 켜면 베스천이 같이 켜진다. 개발 중에는 단일 AZ로 둔다.
- **NAT 없이 접속한다.** 적재 작업은 VPC 안에서 실행하고, 평소 꺼 둔 NAT에 의존하지 않는다. 접속 인증 방식은 plan에서 정한다(DB IAM 인증 또는 비밀 저장소 엔드포인트).
- **C의 규칙 함수는 그대로 쓸 수 있다.** 원본 읽기 함수는 날짜와 경로를 인자로 받는다(`6c3c408`). 매일 갱신과 같은 패키지를 쓴다.
- **Silver를 읽지 않는다.** 다시 채우기도 원본에서 같은 함수로 계산한다. Silver는 같은 함수를 같은 원본에 돌린 결과라 값이 같다. NAT 없이 실행하면 S3 외의 AWS API(카탈로그·조회 서비스)를 부를 수 없다(plan research).
- **보관 정책은 두지 않는다.** NOx·SOx는 하루 약 18만~20만 행이고, 12월 중순까지 약 1,000만 행(2~2.5GB)으로 저장 공간 20GB 안이다. 장기 운영 시 월 단위 분할을 추가한다.
- **D의 사업장 목록**은 실제 사업장 이름과 좌표가 있어 저장소에 넣지 않는다. S3 비공개 운영 경로에 두고 초기 적재 명령이 읽는다(011의 참조 통계와 같은 방식).
- **D와 C가 정할 것(이 기능은 기다리지 않음)**
  - 상태 5종의 정확한 의미와 설명 문구: 처음엔 설명을 비워 둔다.
  - 측정 시각이 30분 구간의 시작인지 끝인지: 처음엔 Silver의 값을 그대로 쓴다.
  - 평균 정의(0 포함, 상태 제외): 이 spec의 정의로 시작하고 C의 답에 맞춘다.
  - 첫 화면 지도의 캐시 방식: 범위 밖.
- **범위 밖**
  - 추론 파이프라인과 예측 표(다음 이슈)
  - 에이전트 조회 함수, 문서 색인, 대화 저장(D)
  - C의 Silver 규칙·계약 변경
  - 합성 데이터(`ktms_synth`): 서비스 화면에 섞지 않는다.
  - 지도용 JSON 파일 캐시
