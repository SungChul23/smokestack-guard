## 배경

008 파이프라인은 매일 03:00(KST)에 최근 2일을 다시 계산해 `tms_silver2.ktms`(Silver)와 `tms_silver2.ktms_ml_ready`(ML-ready)를 갱신한다. 지금은 **잡이 실패할 때만** 알림이 간다. 잡은 성공했는데 결과가 계약을 어긴 경우는 아무도 모른 채 학습(E)에 쓰일 수 있다.

- 예: 컬럼이 빠지거나 순서가 바뀜, 버전 값이 다름, 같은 행이 두 번 들어감, Feature·라벨 계산이 규칙과 다름, 합성과 실데이터가 섞임
- C가 이를 판정하는 규칙을 만들었다(PR #52, `ml_ready_check`): 형식 → 규칙 → 재계산 세 가지.
- 이 기능은 그 규칙을 **수정 없이** 파이프라인 마지막 단계로 붙이고, 결과를 운영자가 바로 읽을 수 있게 알린다.

```
03:00  Silver ─▶ ML-ready ─▶ 계약 검사 (새 단계)
                                 ├ 통과 ─▶ 통과 기록 (snapshot_id)
                                 ├ 위반 ─▶ 위반 알림 (무엇이, 몇 행, 첫 행) + 전체 목록 기록
                                 └ 검사 자체 실패 ─▶ 실행 실패 알림
```

**가장자리 오탐**: Feature는 과거 150분, 라벨은 미래 60분을 본다. 검사 범위의 행만 읽어 다시 계산하면 범위 첫 행의 과거 값, 마지막 행의 미래 값이 없어 데이터가 멀쩡해도 "불일치"가 나온다. 이를 가짜 위반으로 보고하지 않아야 한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 계약을 어긴 갱신이 그날 아침 알려진다 (Priority: P1)

매일 갱신이 끝나면 같은 날짜 범위의 ML-ready를 계약에 맞춰 검사한다. 위반이 있으면 운영자(A)는 메일 제목만 보고 "계약 위반"임을 알고, 본문에서 어느 검사(형식·규칙·재계산)의 어느 항목이 몇 행 어겼는지, 첫 위반 행이 무엇인지, 전체 목록이 어디 있는지, 다시 실행하려면 무엇을 치는지 바로 읽는다.

**Why this priority**: 이 기능의 목적이다. 위반을 모르면 깨진 데이터로 학습한다.

**Independent Test**: 위반이 있는 표본과 없는 표본으로 검사를 돌려, 위반 표본만 위반 알림 내용(항목, 행 수, 첫 행 키)을 만들고 정상 표본은 통과하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 갱신이 계약을 지킨 결과를 냄, **When** 검사 단계가 끝나면, **Then** 통과로 기록되고 알림은 가지 않는다.
2. **Given** 대상 범위의 한 행 라벨이 규칙과 다름, **When** 검사하면, **Then** "재계산 불일치 `label_entry_60m`: 1행 (첫 행 …)"이 위반 알림 본문에 나온다.
3. **Given** 위반이 50가지, **When** 알림을 보내면, **Then** 메일에는 상위 몇 건과 "외 N건"만 나오고 전체 목록은 실행 기록 위치에 있다.
4. **Given** 테이블을 읽는 중 조회가 실패함, **When** 검사가 끝나지 못하면, **Then** 제목이 위반 알림과 다른 "검사 실행 실패" 알림이 오류 종류·메시지와 함께 간다.
5. **Given** 대상 범위 첫날 00:00 행, **When** 데이터가 정상이면, **Then** 과거 값을 못 봐서 생기는 불일치는 위반으로 보고하지 않는다.
6. **Given** 매일 실행 직후 마지막 날 끝 1시간의 라벨이 비어 있음(다음 날 채워짐), **When** 검사하면, **Then** 위반이 아니다.

---

### User Story 2 - 운영 데이터와 운영 알림에 영향 없이 시험한다 (Priority: P1)

운영자는 검사 단계를 만들고 고치는 동안 운영 테이블을 바꾸거나 팀원에게 가짜 알림을 보내지 않고 시험한다. 이미 있는 테이블에 검사만 따로 돌리고, 알림 없이 결과만 남기고, 일부러 만든 위반은 운영 테이블이 아닌 표본으로 확인한다. 처음 배포 뒤 며칠은 위반이 나와도 파이프라인을 실패로 만들지 않고 알림만 보내다가, 오탐이 없음을 확인하면 설정 하나로 "위반이면 실패"로 바꾼다.

**Why this priority**: 사용자가 정한 필수 조건이다. 검사가 잘못돼 운영 파이프라인을 실패시키거나 데이터를 건드리면 안 된다.

**Independent Test**: 검사만 실행(갱신 잡 없이) + 알림 끔으로 운영 테이블에 돌린 뒤, 테이블의 최신 스냅샷이 실행 전과 같고 알림이 오지 않았고 결과 기록만 생겼는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 검사만 실행하도록 지정, **When** 실행하면, **Then** Silver·ML-ready 갱신 잡은 돌지 않고 검사만 돈다.
2. **Given** 알림 끔으로 실행, **When** 위반이 있어도, **Then** 알림은 가지 않고 결과는 실행 기록에 남는다.
3. **Given** 어떤 실행이든, **When** 끝나면, **Then** ML-ready·Silver 테이블의 최신 스냅샷과 원본 경로는 바뀌지 않는다.
4. **Given** 관찰 모드(기본), **When** 위반이 나오면, **Then** 위반 알림은 가지만 파이프라인 실행은 성공으로 끝난다.
5. **Given** 위반 시 실패 모드, **When** 위반이 나오면, **Then** 위반 알림이 가고 파이프라인 실행은 실패로 끝난다.

---

### User Story 3 - 학습하는 사람이 믿을 수 있는 버전을 고른다 (Priority: P2)

검사를 통과한 ML-ready 스냅샷이 기록되어, E는 "마지막으로 통과한 스냅샷"을 골라 학습한다. 위반이 난 날의 데이터로 학습하지 않을 수 있다.

**Why this priority**: 검사는 갱신이 커밋된 뒤에 돌아 위반 데이터를 되돌리지 못한다. 대신 통과 여부를 남겨 쓰는 쪽이 피할 수 있게 한다.

**Independent Test**: 통과한 실행 기록에 그 시점 ML-ready 스냅샷 식별자가 있고, 안내 문서의 방법으로 그 스냅샷을 읽을 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 검사 통과, **When** 실행 기록을 보면, **Then** 검사한 테이블의 스냅샷 식별자와 범위, 통과가 적혀 있다.
2. **Given** 오늘 위반·어제 통과, **When** E가 안내대로 마지막 통과 스냅샷을 찾으면, **Then** 어제 스냅샷이 나온다.

---

### User Story 4 - 같은 검사를 합성 테이블에도 쓴다 (Priority: P3)

합성 데이터 ML-ready가 생기면 같은 검사 단계를 출처 기대값(`ktms_synth`)과 "실데이터와 굴뚝 키가 겹치지 않음" 조건을 더해 돌린다.

**Why this priority**: 합성 통합(다음 작업)에서 필요하지만 지금 합성 테이블은 없다. 입구만 열어 둔다.

**Independent Test**: 출처 기대값과 실데이터 비교 대상을 지정해 표본으로 돌렸을 때 출처가 다르거나 굴뚝 키가 겹치면 위반으로 나오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 출처 기대값 `ktms_synth`, **When** 테이블 출처가 `ktms`이면, **Then** `data_source` 위반이다.
2. **Given** 실데이터 비교 대상 지정, **When** 굴뚝 키가 겹치면, **Then** "실데이터와 굴뚝 키가 겹친다" 위반이다.

### Edge Cases

- **대상 범위에 행이 0개**(수집 중단 등): 위반이 아니라 "검사할 행 없음" 경고로 알린다. 누락 자체는 누락률 리포트가 맡는다.
- **날짜 범위 "auto"**: 검사는 같은 실행의 ML-ready가 처리한 날짜 범위와 정확히 같은 범위를 본다. 어긋나면 가짜 위반이나 검사 누락이 생긴다.
- **ML-ready 단계가 실패**: 검사는 돌지 않는다(기존 실패 알림만).
- **검사 단계가 재시도 뒤에도 실패**: 검사 실행 실패 알림을 보낸다. 관찰 모드에서도 이건 알린다.
- **알림 본문이 지나치게 김**: 위반 항목 수에 상관없이 메일 길이를 제한하고 나머지는 기록 위치로 안내한다.
- **같은 범위를 다시 검사**: 결과가 같아야 한다. 실행 기록은 실행마다 따로 남는다.
- **원본 열 값이 비어 있는 행**: C 규칙의 동작을 그대로 따른다(이 기능은 판정 규칙을 바꾸지 않는다).

## Requirements *(mandatory)*

### Functional Requirements

**검사 실행**

- **FR-001**: 매일 갱신 파이프라인은 ML-ready 단계가 성공한 뒤 계약 검사 단계를 실행해야 한다.
- **FR-002**: 검사는 C의 계약 검사 규칙(형식·규칙·재계산, PR #52)을 수정 없이 사용해야 한다. 판정 규칙을 이 기능에서 바꾸지 않는다.
- **FR-003**: 검사 범위는 같은 실행의 ML-ready 단계가 처리한 날짜 범위와 같아야 한다("auto" 포함).
- **FR-004**: 재계산 비교는 ML-ready 잡과 같은 여유 구간(대상 범위 앞 150분, 마지막 날 다음날 00:30까지 = 마지막 칸 +60분)을 함께 읽어 계산하고, 비교와 보고는 대상 범위 행만 해야 한다(가장자리 오탐 방지).
- **FR-005**: 매일 실행 직후 범위 마지막 날 끝 1시간의 라벨 빈 값은 위반으로 보지 않아야 한다.
- **FR-006**: 검사 결과는 통과 / 위반 / 검사할 행 없음 / 검사 실행 실패 네 가지로 구분해야 한다.

**알림 (가독성)**

- **FR-007**: 위반 알림과 검사 실행 실패 알림은 메일 제목부터 달라야 한다. 기존 갱신 잡 실패 알림과도 구분되어야 한다. 제목은 메일 제약상 영문, 본문은 한국어다.
- **FR-008**: 위반 알림 본문에는 범위, 검사한 스냅샷 식별자, 위반 항목별 한 줄(검사 종류, 항목, 행 수, 첫 위반 행 키), 전체 목록 위치, 다시 실행 방법, 읽는 법 문서 위치가 있어야 한다.
- **FR-009**: 메일에는 위반 항목을 최대 10건까지만 싣고 나머지는 "외 N건"으로 줄여야 한다. 전체 목록은 실행 기록에 남긴다.
- **FR-010**: 검사 실행 실패 알림에는 오류 종류, 메시지, 실행 이름, 로그 위치가 있어야 한다.
- **FR-011**: 알림은 기존 운영 알림 수신처(운영 SNS)로 보내야 한다.

**시험 가능성 (운영 무영향)**

- **FR-012**: 검사 단계는 읽기 전용이어야 한다. 테이블·원본 경로에 쓸 수 없고, 자기 실행 기록 경로에만 쓸 수 있다.
- **FR-013**: 운영자는 파이프라인 입력으로 "검사만" 실행할 수 있어야 한다(갱신 잡 없이, 범위 지정 가능).
- **FR-014**: 운영자는 실행 입력으로 알림을 끌 수 있어야 한다. 이때도 실행 기록은 남는다.
- **FR-015**: 위반 시 동작은 설정 하나로 "관찰"(알림만, 실행 성공)과 "차단"(알림 + 실행 실패) 중 고를 수 있어야 하고, 처음 배포 기본값은 관찰이다.
- **FR-016**: 위반을 일부러 만든 시험은 운영 테이블이 아니라 표본 데이터로 할 수 있어야 한다(자동 테스트 포함).

**기록·재사용**

- **FR-017**: 실행마다 결과(범위, 스냅샷 식별자, 결과 구분, 행 수, 위반 전체 목록, 소요 시간)를 `silver2/_runs/ktms_ml_ready_check/`에 남겨야 한다.
- **FR-018**: 검사를 통과한 스냅샷을 찾는 방법을 학습 담당(E)이 읽는 문서에 적어야 한다.
- **FR-019**: 검사 단계는 대상 테이블, 출처 기대값, 실데이터 비교 대상을 입력으로 받아 합성 테이블에도 쓸 수 있어야 한다.
- **FR-020**: 저장소 루트의 규칙 테스트(`tests/`)가 CI에서 실행되어야 한다.

### Key Entities

- **검사 실행 기록**: 한 번의 검사 결과. 범위, 대상 테이블, 스냅샷 식별자, 결과 구분, 대상 행 수, 위반 목록(검사 종류·항목·행 수·첫 행 키), 실행 이름, 시작·종료 시각, 모드(관찰·차단), 알림 여부.
- **위반 항목**: C 규칙이 돌려주는 한 줄. 검사 종류(형식·규칙·재계산), 항목, 행 수, 첫 위반 행 키.
- **실행 입력**: 단계 선택(전체·Silver·ML-ready·검사만), 날짜 범위, 알림 여부, (합성용) 대상 테이블·출처 기대값·실데이터 비교 대상.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 계약을 지킨 최근 2일 데이터에 검사를 7번 돌려 가짜 위반이 0건이다(가장자리 포함).
- **SC-002**: 위반을 넣은 표본 5종(컬럼 누락, 출처 섞임, 키 중복, 라벨 변조, Feature 변조)을 모두 위반으로 잡는다.
- **SC-003**: 위반 알림을 받은 사람이 다른 자료를 열지 않고 "어느 항목이 몇 행, 첫 행이 무엇인지"를 메일만으로 말할 수 있다.
- **SC-004**: 검사만·알림 끔 실행 뒤 ML-ready·Silver 최신 스냅샷이 실행 전과 같고 운영 알림은 0건이다.
- **SC-005**: 검사 단계가 매일 파이프라인 전체 시간을 5분 넘게 늘리지 않는다.
- **SC-006**: E가 문서만 보고 마지막 통과 스냅샷을 찾아 읽을 수 있다.

## Assumptions

- PR #52(`ml_ready_check`)는 main에 머지되어 #46 브랜치에 들어와 있다(2026-11-17).
- 매일 스케줄은 이미 켜져 있다(2026-11-13, `ktms_schedule_enabled` 기본값 true). 그래서 이 단계를 배포하는 순간 매일 실행에 들어간다. 첫 배포는 반드시 관찰 모드여야 하고, 수동 "검사만" 실행으로 먼저 확인한다.
- 하루 갱신 범위(2일)의 K-TMS ML-ready는 수만 행 수준이라 가벼운 실행 단위로 충분하다.
- 위반이 나도 이미 커밋된 ML-ready를 되돌리지 않는다. 되돌리기 대신 통과 스냅샷 기록으로 대응한다.
- 알림 수신처는 기존 운영 SNS 토픽(이메일)이다. 새 토픽은 만들지 않는다.
- 범위 밖: 추론 파이프라인, Athena 지표 뷰(시맨틱 레이어), 대만 CEMS 테이블 검사, 합성 데이터 생성·업로드.
