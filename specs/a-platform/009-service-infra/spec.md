## 배경

대시보드(D)와 에이전트(D·E)가 올라갈 서비스 계층이 아직 없다. 합성 데이터(B)가 들어오기 전까지 데이터 쪽 작업이 멈춰 있어, 이 기간에 서비스 인프라의 골격을 먼저 만든다.

2026-11-15~16에 정한 구성은 다음과 같다.

```
사용자 ─① 주소 조회─▶ Route 53 (smokestack-guard.store, 카페24에서 NS 위임)
사용자 ─② smokestack-guard.store ─▶ CloudFront ─▶ S3 (React 화면, 비공개)
사용자 ─③ 로그인 ─▶ Cognito (관리자가 만든 계정만)
사용자 ─④ api.smokestack-guard.store ─▶ IGW ─▶ ALB (두 AZ 퍼블릭 서브넷)
        ─▶ /api/* API 서버 · /agent/* 에이전트 서버 (두 AZ 프라이빗 서브넷, 각 2대)
        ─▶ RDS PostgreSQL + pgvector (프라이빗 DB 서브넷, 시연 때 Multi-AZ)
서버 ─⑤ 외부 호출 (Bedrock, ECR, SSM, Secrets, Athena) ─▶ 같은 AZ의 NAT ─▶ IGW
```

모두 켜면 월 약 $220(LLM 호출 제외)으로 크레딧($200)을 넘는다. 그래서 **시간당 요금이 붙는 자원은 만들 수 있게만 해 두고 기본은 꺼 둔다.** 개발·시험 때는 최소 구성(NAT 1개, 단일 AZ DB, 서버 각 1대)으로 잠깐 켜고, 완전 이중화는 시연 기간에만 켠다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 자기 도메인 https 주소로 화면이 열린다 (Priority: P1)

방문자가 브라우저에 `smokestack-guard.store`(또는 `www.smokestack-guard.store`)를 입력하면 https로 화면이 열린다. 지금은 빈 React 페이지지만, 나중에 D의 대시보드가 같은 주소에 올라간다.

**Why this priority**: 도메인 위임과 인증서 발급은 몇 시간에서 하루가 걸리고, 다른 모든 주소(`api.`)와 로그인 설정이 이것에 기댄다. 가장 먼저 끝나야 한다.

**Independent Test**: 카페24 네임서버를 바꾼 뒤 브라우저로 루트 주소와 `www` 주소를 열어 인증서 경고 없이 같은 페이지가 나오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 도메인 위임과 인증서 발급이 끝난 상태, **When** `https://smokestack-guard.store`를 열면, **Then** 경고 없이 빈 React 페이지가 보인다.
2. **Given** 같은 상태, **When** `https://www.smokestack-guard.store` 또는 `http://smokestack-guard.store`를 열면, **Then** `https://smokestack-guard.store`의 같은 페이지로 간다.
3. **Given** 화면 파일이 든 저장소, **When** 누군가 저장소 주소로 직접 접근하면, **Then** 거부된다(화면은 배포 경로로만 보인다).

### User Story 2 - 꺼 둔 상태로 비용이 거의 들지 않고, 변수만 바꿔 켜고 끌 수 있다 (Priority: P1)

A가 기본값으로 적용하면 시간당 요금이 붙는 자원(NAT, ALB, DB와 배스천, 서버)은 하나도 만들어지지 않는다. 개발·시험이나 시연 때는 켜는 변수만 바꿔 적용하면 해당 자원이 생기고, 다시 끄면 사라진다. 예상치 못한 비용은 알림으로 먼저 알 수 있다.

**Why this priority**: 크레딧이 $200뿐이라, 켜고 끄는 구조와 비용 알림이 없으면 나머지 기능을 안전하게 시험할 수 없다.

**Independent Test**: 기본값으로 적용한 뒤 시간당 요금 자원이 0개인지 확인한다. 개발 구성으로 켜서 `api.` 주소 → 서버 → DB 연결을 한 번 확인하고, 다시 기본값으로 적용해 자원이 사라졌는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 모든 켜는 변수가 기본값, **When** 적용하면, **Then** NAT·ALB·DB·배스천·서버가 하나도 없고, 꺼 둔 상태의 월 예상 비용이 $5 이하다.
2. **Given** 개발 구성(NAT 1개, ALB, 단일 AZ DB, 서버 각 1대), **When** 적용하면, **Then** `https://api.smokestack-guard.store`의 상태 확인 경로가 API 서버와 에이전트 서버에서 각각 응답하고, 각 서버가 DB에 연결된다.
3. **Given** 시연 구성(NAT 2개, Multi-AZ DB, 서버 각 2대), **When** 적용하면, **Then** 서버와 NAT가 AZ마다 하나씩 놓이고, 한쪽 AZ의 서버를 멈춰도 `api.` 주소가 계속 응답한다.
4. **Given** 켜 둔 상태, **When** 다시 기본값으로 적용하면, **Then** 시간당 요금 자원이 모두 사라지고, 도메인·인증서·화면·로그인·이미지 저장소는 그대로 남는다.
5. **Given** 월 비용이 정한 기준(예: $50, $100, $150)을 넘을 때, **When** 기준을 넘으면, **Then** A에게 이메일 알림이 간다.

### User Story 3 - 로그인하고 들어온다, 계정은 관리자만 만든다 (Priority: P2)

화면에 들어오면 로그인부터 한다(로그인 전에는 대시보드가 보이지 않는다). A(관리자)가 만들어 준 계정으로만 로그인할 수 있고 아무나 가입할 수는 없다. 서버는 로그인 토큰을 확인해 로그인한 사용자 요청만 받는다(운영 확인용 경로만 공개). 2026-11-16 범위 확장: 화면 로그인 강제와 서버 토큰 검증을 최소 앱에 넣어 D가 이어 쓴다.

**Why this priority**: 에이전트는 LLM 호출 비용이 들어 외부인이 마음대로 쓰면 안 된다. 다만 화면과 서버 앱(D)이 나오기 전까지는 로그인 화면만 확인할 수 있어 P2다.

**Independent Test**: 관리자가 계정을 하나 만들고, 그 계정으로 로그인 화면에서 로그인해 토큰을 받는지 확인한다. 가입 화면이나 셀프 가입 요청이 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 관리자가 만든 계정, **When** 처음 로그인하면, **Then** 비밀번호를 바꾸라는 요청을 받고, 바꾼 뒤 로그인된다.
2. **Given** 계정이 없는 사람, **When** 스스로 가입하려 하면, **Then** 거부된다.
3. **Given** 로그인이 끝난 사용자, **When** 화면으로 돌아오면, **Then** 화면 주소(루트)로 돌아오고 토큰을 받는다.
4. **Given** 로그인하지 않은 방문자, **When** 화면 주소를 열면, **Then** 바로 로그인 페이지로 이동한다.
5. **Given** 토큰이 없거나 다른 앱·만료된 토큰, **When** 서버의 보호된 경로(`/api/me` 등)를 부르면, **Then** 401이다. `/health`, `/api/health`, `/agent/health`는 토큰 없이 응답한다.
6. **Given** 로그인한 사용자, **When** 1시간이 지나도, **Then** 다시 로그인하지 않고 토큰이 조용히 갱신된다(30일까지).

### User Story 4 - D가 자기 폴더를 main에 머지하면 그 앱만 배포된다 (Priority: P2)

D가 `services/dashboard-api/`, `services/dashboard-agent/`, `services/dashboard-web/` 중 하나를 고쳐 PR을 올리면 테스트만 돌고, main에 머지되면 그 앱만 배포된다. 서버가 꺼져 있어도 배포 기록은 남고, 나중에 서버를 켜면 마지막으로 배포된 버전으로 뜬다.

**Why this priority**: D가 앱을 만들기 시작하기 전에 배포 길이 있어야 D가 인프라를 몰라도 작업할 수 있다. 앱 코드가 없는 지금은 빈 앱으로만 확인할 수 있어 P2다.

**Independent Test**: 각 폴더에 최소 앱을 두고, 한 폴더만 고친 커밋을 main에 머지해 그 앱의 배포만 실행되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** `dashboard-api` 폴더만 바꾼 PR, **When** PR을 올리면, **Then** 그 앱의 테스트·빌드만 돌고 배포는 하지 않는다.
2. **Given** 같은 변경, **When** main에 머지되면, **Then** api 이미지만 새 버전(커밋 기준 태그)으로 올라가고 "현재 api 버전" 기록이 바뀐다. 켜져 있는 API 서버는 새 버전으로 바뀌고, 에이전트 서버와 화면은 그대로다.
3. **Given** `dashboard-web` 폴더 변경이 main에 머지, **When** 배포가 끝나면, **Then** 화면 주소에서 새 화면이 보인다(옛 화면이 캐시에 남지 않는다).
4. **Given** 서버가 꺼져 있을 때(대수 0) 머지, **When** 배포가 돌면, **Then** 실패하지 않고 "현재 버전" 기록만 바뀌며, 나중에 서버를 켜면 그 버전으로 뜬다.
5. **Given** main이 아닌 브랜치, **When** 배포 권한을 쓰려 하면, **Then** 거부된다.

### User Story 5 - 팀원 누구나 DB GUI 도구로 DB에 접속한다 (Priority: P3)

DB가 켜져 있으면 배스천(관리용 인스턴스)도 함께 켜져 있다. 팀원(A~E)과 멘토는 A가 나눠 준 공용 키 파일(.pem) 하나로, DBeaver의 SSH 터널 설정에 배스천 주소를 넣고 DB(PostgreSQL)에 관리자 계정으로 접속한다. 별도 명령이나 AWS CLI는 필요 없다. DB는 인터넷에서 들어오는 포트가 없고, 배스천은 키 인증 SSH만 받는다.

**Why this priority**: D(화면·RAG)와 E(판정·모델)가 스키마와 데이터를 직접 확인해야 하지만, DB를 켜는 개발 단계부터 필요하므로 P3다.

**Independent Test**: 개발 구성으로 DB를 켜고, A가 아닌 팀원 한 명이 안내 문서대로 DBeaver에 SSH 터널(배스천 주소, 키 파일)과 DB 연결값을 넣어 접속하고 테이블을 조회할 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** DB가 켜진 상태(배스천도 함께 켜짐), **When** 팀원이 DBeaver에서 SSH 터널로 배스천 주소와 공용 키 파일을, DB 연결로 DB 주소와 관리자 계정을 넣고 접속하면, **Then** 로그인된다.
2. **Given** 같은 상태, **When** 키 파일 없이(비밀번호로) 배스천에 SSH 접속하면, **Then** 거부된다.
3. **Given** 같은 상태, **When** 인터넷에서 DB 포트로 직접 접속하면, **Then** 거부된다.
4. **Given** NAT가 꺼진 상태, **When** DB를 켜면, **Then** 배스천을 거친 접속이 여전히 된다(배스천은 NAT에 기대지 않는다).
5. **Given** DB를 껐다 다시 켜 배스천이 새로 만들어진 상태, **When** 팀원이 저장해 둔 DBeaver 설정으로 접속하면, **Then** 설정을 고치지 않아도 접속된다(배스천 주소가 고정 이름이다).

### Edge Cases

- **도메인 위임 전 적용**: 카페24 네임서버를 아직 안 바꿨거나 전파 중이면 인증서 검증이 끝나지 않는다. 호스팅 영역을 먼저 만들고 위임이 확인된 뒤 인증서·화면·`api.`을 적용한다. 순서를 어기면 적용이 인증서 검증을 기다리다 멈출 수 있다.
- **호스팅 영역을 지웠다 다시 만들기**: 네임서버 4개가 바뀌어 카페24 설정을 다시 해야 하고, 그동안 모든 주소가 끊긴다. 그래서 호스팅 영역은 다른 자원과 따로 두고 지우지 않는다.
- **NAT를 끄고 서버만 켜기**: 프라이빗 서버가 이미지 저장소·SSM에 닿지 못해 뜨지 못한다. 서버를 켜는 구성은 NAT를 1개 이상 함께 켠다. 켜는 변수가 이 조합을 막거나 경고해야 한다.
- **DB 끄기**: 끄면 DB 인스턴스와 배스천이 함께 사라진다(다시 켜면 배스천 IP가 바뀌지만 고정 이름이 새 IP를 가리킨다). 지우기 전에 마지막 스냅샷을 남기고, 다시 켤 때 스냅샷에서 되살릴 수 있게 한다. 개발 단계의 DB 데이터는 다시 만들 수 있는 것만 둔다(Assumptions).
- **서버 대수 0에서 배포**: 배포 대상이 없어도 실패로 끝나지 않고 "현재 버전"만 기록한다.
- **화면 캐시**: 새 화면을 배포했는데 옛 진입 파일이 캐시에 남으면 옛 화면이 보인다. 진입 파일은 캐시하지 않고, 이름에 해시가 붙은 파일만 오래 캐시한다.
- **한쪽 AZ 장애(시연 구성)**: ALB는 남은 AZ의 서버로만 보내고, 서버는 같은 AZ의 NAT를 써서 영향을 받지 않으며, DB는 대기 인스턴스로 넘어간다(1~2분 끊김 가능).
- **공용 키 유출**: 키 파일은 팀이 공유하므로 새 나갈 수 있다. 새 나가면 A가 새 키를 만들고 배스천을 다시 만들어 옛 키를 무효로 한다. 키만으로는 DB에 들어갈 수 없다(DB 비밀번호가 따로 필요).
- **팀원 IP가 바뀜**: SSH 허용 주소를 팀원 IP로 좁히면 집·학원을 옮길 때마다 막힌다. 그래서 허용 주소는 전체 허용 + 키 인증만으로 운영하고, 필요하면 변수로 좁힌다(Assumptions).
- **비밀번호 교체**: 관리자 비밀번호는 30일마다 바뀐다. 접속이 거부되면 새 비밀번호를 읽어 DBeaver에 다시 넣는다(안내 문서에 적는다).
- **잘못된 비용**: 켜 둔 것을 잊으면 하루 약 $7씩 나간다. 비용 알림이 이것을 잡는다.

## Requirements *(mandatory)*

### Functional Requirements

**도메인·인증서**

- **FR-001**: `smokestack-guard.store`의 DNS를 AWS에서 관리하고, 그 네임서버 4개를 출력해 사람이 카페24에 입력할 수 있어야 한다. 이 DNS 영역은 다른 자원을 지우고 다시 만들어도 바뀌지 않도록 따로 관리한다.
- **FR-002**: 화면용(루트, `www`)과 서버용(`api.`) https 인증서를 DNS 검증으로 자동 발급·갱신해야 한다.

**네트워크**

- **FR-003**: AZ 2개에 각각 퍼블릭·앱·DB 서브넷을 두는 전용 네트워크를 만들어야 한다. 앱·DB 서브넷은 인터넷에서 직접 들어올 수 없어야 한다.
- **FR-004**: 앱 서브넷의 외부 호출은 같은 AZ의 NAT로 나가야 하며, NAT 개수는 0(기본), 1, 2 중에서 변수로 정한다. NAT가 1개면 두 AZ가 그 하나를 같이 쓴다.
- **FR-005**: S3 접근은 NAT를 거치지 않는 무료 경로로 가야 한다.
- **FR-006**: 접근 규칙은 "인터넷 → ALB 443", "ALB → 서버 앱 포트", "허용 주소 → 배스천 SSH 22", "서버·배스천 → DB 5432"만 허용해야 한다. 서버와 DB에는 인터넷에서 들어오는 규칙이 없어야 한다.

**화면**

- **FR-007**: 화면 파일은 비공개 저장소에 두고, 배포 경로(CloudFront)로만 읽을 수 있어야 한다. 루트와 `www`, `http`는 모두 `https://smokestack-guard.store`로 가야 한다.
- **FR-008**: 화면의 진입 파일은 캐시하지 않고, 이름에 해시가 붙은 정적 파일만 길게 캐시해야 한다. 화면 안의 다른 경로(예: `/stacks/123`)로 새로고침해도 화면이 열려야 한다.

**로그인**

- **FR-009**: 관리자만 계정을 만들 수 있는 사용자 풀과, 화면이 쓸 앱 클라이언트를 만들어야 한다. 로그인 뒤 돌아갈 주소는 화면 주소(운영)와 로컬 개발 주소로 한정한다.
- **FR-027**: 화면은 로그인 전에는 대시보드를 보여 주지 않고 로그인 페이지로 보내야 하며, 로그인 상태는 탭을 닫아도 유지되고(Refresh 토큰 기간) 로그아웃할 수 있어야 한다.
- **FR-028**: API·에이전트 서버는 운영 확인용 경로를 뺀 모든 경로에서 Cognito Access 토큰(서명, 만료, 발급자, token_use, 앱 클라이언트)을 검증해야 한다.
- **FR-010**: 서버가 로그인 토큰을 검증할 때 필요한 값(사용자 풀 ID, 앱 클라이언트 ID, 리전)을 서버와 화면 빌드가 읽을 수 있는 곳에 이름으로 남겨야 한다. 비밀값은 아니다.

**서버·배포**

- **FR-011**: API·에이전트 앱 이미지를 보관하는 저장소 2개를 만들어야 하고, 오래된 이미지는 일정 개수만 남기고 지워야 한다.
- **FR-012**: API 서버 그룹과 에이전트 서버 그룹을 각각 두 AZ의 앱 서브넷에 걸쳐 만들어야 한다. 대수는 0(기본), 1, 2 중 변수로 정하고, 서버가 멈추면 같은 대수로 다시 채워야 한다.
- **FR-013**: 서버는 뜰 때 "현재 버전" 기록을 읽어 그 이미지를 받아 실행해야 한다. 서버에는 SSH 키를 두지 않고, 접속은 세션 관리자로만 한다.
- **FR-014**: ALB(변수, 기본 꺼짐)는 `/api/*`를 API 서버 그룹으로, `/agent/*`를 에이전트 서버 그룹으로 보내고, 상태 확인 경로로 건강한 서버에만 보내야 한다. ALB를 켜면 `api.` 주소가 ALB를 가리키고, 끄면 그 주소도 사라진다.
- **FR-015**: 배포 권한은 이 저장소의 main 브랜치에서 돈 작업만 얻을 수 있어야 하며, 권한 범위는 이미지 올리기, 화면 파일 올리기, 캐시 비우기, "현재 버전" 기록 쓰기, 서버에 새 버전 받으라고 명령하기로 한정한다.
- **FR-016**: 배포 작업은 앱 폴더(`services/dashboard-api/`, `services/dashboard-agent/`, `services/dashboard-web/`)별로 따로 돌아야 한다. PR에서는 테스트·빌드만, main 머지에서는 배포까지 한다.

**DB**

- **FR-017**: DB(변수, 기본 꺼짐)는 PostgreSQL에 pgvector를 쓸 수 있는 버전으로 DB 서브넷에 만들고, 단일 AZ(개발)와 Multi-AZ(시연)를 변수로 고른다.
- **FR-018**: DB 관리자 비밀번호는 AWS가 만들어 비밀 저장소에 두고, 저장소와 Terraform 상태 어디에도 평문으로 남지 않아야 한다. 서버는 비밀 저장소에서 읽는다.
- **FR-019**: DB를 끌 때 마지막 스냅샷을 남기고, 다시 켤 때 원하면 그 스냅샷에서 되살릴 수 있어야 한다.

**관리 접속**

- **FR-020**: 배스천(관리용 인스턴스 1대)은 DB와 함께 켜지고 꺼져야 한다. 퍼블릭 서브넷에 두고, 허용 주소(변수)에서 오는 SSH만 키 인증으로 받아야 하며 비밀번호 로그인은 꺼야 한다. 배스천에서는 DB 포트로의 터널만 쓰고, NAT가 꺼져 있어도 동작해야 한다. A가 관리 작업을 할 수 있도록 세션 관리자 접속도 함께 켜 둔다.
- **FR-024**: 배스천 SSH 키는 팀 공용 1개다. 키 쌍은 A가 콘솔에서 만들고 키 파일(.pem)은 A가 팀원에게 직접 전달하며, Terraform은 키 **이름**만 참조해 키 내용이 저장소·상태에 남지 않아야 한다.
- **FR-025**: 배스천에 고정 이름(예: `bastion.smokestack-guard.store`)을 붙여, 배스천이 새로 만들어져 IP가 바뀌어도 DBeaver 설정을 고치지 않게 해야 한다. 팀원용 접속 안내(DBeaver SSH 터널 설정값, DB 주소·포트, 비밀번호 읽는 법, 비밀번호 교체 시 할 일)를 제공해야 한다.
- **FR-026**: 팀원은 모두 DB 관리자 계정으로 접속한다(2026-11-16 결정). 관리자 비밀번호는 비밀 저장소에 두고 **30일마다** 자동 교체하며, 팀원 IAM 사용자 그룹은 이 비밀 하나만 읽을 수 있어야 한다.

**비용·운영**

- **FR-021**: 월 비용 기준(예: $50, $100, $150)을 넘으면 A에게 이메일 알림을 보내야 한다. 이메일 주소는 저장소에 쓰지 않는다.
- **FR-022**: 서버 로그를 모으는 로그 그룹을 만들고 보존 기간을 정해야 한다.
- **FR-023**: 모든 자원은 기존 규칙(태그, 상태 저장 위치, 이름 규칙)을 따르고, 기존 수집·Silver 스택은 건드리지 않아야 한다.

### Key Entities

- **켜는 변수**: NAT 개수, ALB 켜기, DB 켜기(배스천 포함)·Multi-AZ, API·에이전트 서버 대수·인스턴스 유형. 기본값은 모두 "꺼짐(0)".
- **운영 구성 3가지**: 꺼 둠(기본), 개발(NAT 1, ALB, 단일 AZ DB, 서버 각 1), 시연(NAT 2, ALB, Multi-AZ DB, 서버 각 2).
- **"현재 버전" 기록**: 앱(api, agent)별로 마지막으로 배포된 이미지 태그. 배포가 쓰고, 서버가 뜰 때 읽는다.
- **공개 설정값**: 사용자 풀 ID, 앱 클라이언트 ID, 화면 주소, `api.` 주소, 이미지 저장소 주소. 서버·화면 빌드·배포 작업이 읽는다. 비밀이 아니다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 도메인 위임이 끝난 뒤 루트·`www`·`http` 세 주소 모두 경고 없이 같은 https 화면으로 열린다.
- **SC-002**: 꺼 둔 상태(기본값)의 월 예상 비용이 $5 이하다.
- **SC-003**: 켜는 변수만 바꿔 적용하면, 꺼 둠 → 개발 구성 전환 뒤 30분 안에 `api.` 주소가 두 앱 모두에서 응답하고 DB에 연결된다. 다시 꺼 둠으로 돌리면 시간당 요금 자원이 0개가 된다.
- **SC-004**: 관리자가 만든 계정은 로그인되고, 셀프 가입은 100% 거부된다.
- **SC-005**: 앱 폴더 하나만 바꾼 머지는 그 앱만 배포하며, main 머지 뒤 15분 안에 켜져 있는 서버(또는 화면)가 새 버전으로 바뀐다.
- **SC-006**: 인터넷에서 서버·DB로 직접 들어갈 수 있는 포트가 0개이고, 배스천은 키 인증 SSH 하나만 받는다. 비밀번호·키가 저장소와 Terraform 상태에 평문으로 0건 남는다.
- **SC-007**: 시연 구성에서 한쪽 AZ의 서버를 멈춰도 `api.` 주소가 계속 응답한다.

## Assumptions

- **화면 주소**: 루트 `smokestack-guard.store`, `www`는 루트로. 서버 주소는 `api.smokestack-guard.store`(2026-11-16 결정).
- **도메인**: 카페24에서 산 도메인이고, 네임서버 변경은 사람이 카페24에서 한 번 한다. 카페24 계정 정보는 저장소·AI에게 주지 않는다.
- **스택 나누기**: `tms-foundation`(DNS 영역·비용 알림·GitHub OIDC 공급자, 지우지 않음), `tms-network`, `tms-serving`(인증서·CloudFront·Cognito), `tms-database`(DB·배스천), `tms-app`(이미지 저장소·서버 그룹·ALB·배포 권한). plan R1에서 확정.
- **크기·값 기본**: 서버 t3.small(API·에이전트 각각 변수, 에이전트는 메모리가 부족하면 t3.medium으로 올림, 스왑 2GB), DB db.t4g.micro, 배스천 t3.micro(새 무료 플랜에서는 nano를 못 쓸 수 있음), 앱 포트 8000, 상태 확인 경로 `/health`. plan에서 조정할 수 있다.
- **EC2 대수**: 모두 켜면 API 2 + 에이전트 2 + 배스천 1 = 5대. 배스천은 DB가 켜진 동안 계속 켜져 있다(월 약 $14, 공인 IPv4 포함).
- **팀원 IAM**: 팀원 5명과 멘토는 팀 계정에 각자 IAM 사용자가 있다(`de-ai-05`, `de-ai-08`, `de-ai-11`, `de-ai-14`, `de-ai-22`(A), `tms_mentor`). DB 비밀번호를 읽는 IAM 그룹은 Terraform이 만들고, 그룹 구성원(IAM 사용자 이름, 비밀 아님)은 변수로 받는다. 액세스 키는 어디에도 적지 않는다.
- **배스천 접속 방식**: SSM 포트 포워딩 대신 공용 키 SSH로 정했다(2026-11-16). 팀원이 AWS CLI 없이 DBeaver만으로 접속하기 위해서다. 대신 22번 포트가 열리고 키를 공유하는 위험을 받아들인다. SSH 허용 주소는 전체 허용(0.0.0.0/0) + 키 인증만으로 정했다(2026-11-16, 팀원이 장소를 옮겨도 접속되게). 변수로 두어 나중에 좁힐 수 있다.
- **에이전트 메모리**: 에이전트는 Bedrock을 API로 호출하고 서버 안에서 모델(로컬 임베딩 등)을 돌리지 않는다. 바뀌면 인스턴스 유형 변수만 올린다.
- **DB 데이터**: 배치 추론(미정)이 생기기 전까지 DB에는 다시 만들 수 있는 데이터(테스트, 벡터 색인)만 둔다. 그래서 끌 때 인스턴스를 지우고 스냅샷만 남기는 방식을 쓴다. 장기 보관이 필요한 데이터가 생기면 다시 정한다.
- **최소 앱**: 배포 길을 확인하기 위해 A가 세 폴더에 상태 확인만 응답하는 최소 앱(빈 React 페이지 포함)을 둔다. 실제 앱은 D가 같은 폴더에서 만든다.
- **Bedrock**: 모델 접근 신청은 콘솔에서 사람이 한다. 서버 역할에 호출 권한은 미리 넣되, 쓰는 모델은 D·E가 정한 뒤 좁힌다.
- **적용 주체**: Terraform `plan`·`apply`는 A가 PowerShell에서 한다(원칙 III). AI 에이전트는 `fmt`·`validate`까지 한다.
- **수집·Silver 영향 없음**: 새 스택만 추가하고 기존 원본 버킷·수집 스케줄·Silver 잡은 바꾸지 않는다(원칙 I).
