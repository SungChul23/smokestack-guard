# 복합 질문 처리 설계 (계획 모양과 단일/복합 판별)

[오케스트레이션 초안](orchestration.md) · [계약 초안](contracts-draft.md) · 상태: **초안 + 첫 구현 조각(2026-11-18)**

한 질문에 요청이 여럿인 "복합 질문"을 안전하게 다루는 방법이다. 결론부터: 맨 앞에서 단일/복합을 가르고, 복합은 부분 목록(계획)으로 나눠 부분별로 실행하며, 못 하는 부분은 **숨기지 않고 부분마다 상태와 이유를 돌려준다.**

## 1. 왜 필요한가 (측정)

복합 질문 정답 세트(검수 통과 830건 + 공격적 질문 209건, 모두 합성이고 Bedrock 없이 현재 시스템에 넣음):

- 시스템이 답을 낸 것은 830건 중 39건(4.7%)이었고 **39건 전부가 복합 질문이었는데 알림 없이 일부만 답했다.** 예: 3가지를 물었는데 1가지만 답, 예측을 물었는데 전국 순위를 답.
- 분류가 완벽하다고 가정하고 정답 칸을 그대로 넣어도 데이터 부분 1,322개 중 답변은 215(16%, 자료 없음 359 제외 시 22%). 막힌 곳은 기간 표현(지난주·새벽·지금: 16%), 사업장 없음/전체 굴뚝, 한 번에 한 조회만 담는 구조.
- 즉 첫 분류 LLM의 문제가 아니라 **구조(한 칸 모델)와 코드 지원 범위**의 문제다. LLM은 계획의 초안을 내는 역할이고 검증·실행은 코드가 한다.

## 2. 경로

| 경로 | 조건 | 처리 |
|---|---|---|
| 단일 조회 | 복합 단서가 없다 | 지금 흐름 그대로(정규식 → 카드 → 도구) |
| 복합 조회 | 집계·기간·굴뚝이 여럿, 비교·나열·정정 | 계획(부분 목록) → 부분별 실행 |
| 다른 에이전트 섞임 | 근거(법령)·예측·요약·화면 요청이 섞임 | 계획의 부분마다 에이전트가 다르다. 아직 없는 에이전트 부분은 `UNAVAILABLE`로 알린다 |
| 차단 | 위험한 요청 | 해로운 부분은 `blocked`(처리 안 함), 나머지는 정상 처리 |

예측·법령은 "채우는" 문제가 아니라 **그쪽 흐름을 따로 만들어야** 하는 일이다. 그때까지는 위 방식으로 정직하게 알린다.

## 3. 판별: 확실한 단일만 LLM을 건너뛴다

- 정규식 단서(`app/agent/router.py`)가 하나라도 걸리면 복합으로 본다. 단서: 집계 둘 이상, 기간 둘 이상, 굴뚝 번호 둘 이상, 다른 기능 단어(법·예측·지도·요약…), 비교·나열·정정(비교·그리고·말고·차이·전날…), 앞 결과를 잇는 말(그 굴뚝·걔·거기), 위험한 말.
- 복합이 단일로 새면 **틀린 답이 조용히 나가고**, 단일이 복합으로 가면 **LLM 호출만 늘어난다.** 그래서 정규식은 정밀도(확실한 단일)를 우선한다. 시험(위험한 복합 992건, 단일 901건): 놓친 복합 19.1%, 복합으로 잘못 본 단일 2.4%.
- 놓친 복합(주로 앞 결과를 잇는 연쇄, 정상 질문 사이에 끼운 위험한 요청, 다른 에이전트 요청의 완곡한 표현)은 정규식 단서로 못 잡는다. **LLM 분류가 연결되기 전까지는 이 구멍이 남는다.** 단일 흐름이 도구를 실행하기 전에 LLM이 단일/복합을 판정하는 단계(애매하면 LLM)를 두는 것이 정식 해결이다.
- 현재(계획기 미연결): 복합 단서가 있으면 일부만 답하지 않고 멈춰서 "하나씩 나눠 질문해 주세요"라고 알린다. 정상 세트 830건 중 답을 낸 것은 7건으로 줄었다(이전 39건). 공격 세트는 209건 중 1건.

## 4. 계획 모양

`Planner.plan(message, now, has_last)`가 돌려주는 JSON. 구현은 `app/agent/compound.py`.

```json
{"parts": [
  {"id": "p1", "agent": "data", "intent": "aggregate",
   "stack": {"business": "가나에너지", "code": "1"}, "pollutants": ["nox"],
   "time": {"kind": "yesterday"}, "operation": "mean", "metric": "value",
   "depends_on": null, "note": "NOx 평균"},
  {"id": "p2", "agent": "evidence", "intent": "law", "note": "법 기준"}
]}
```

| 필드 | 규칙 |
|---|---|
| `agent`/`intent` | data: aggregate·rank·freshness·gap / evidence: law / prediction: predict / report: report / ui: navigate / blocked: blocked. 맞지 않는 짝이면 계획을 버린다 |
| 부분 수 | 1~6개(`MAX_PARTS`). 넘으면 "나눠서 다시 입력"을 안내한다 |
| `depends_on` | **앞선** 부분의 id만 가능(자기 참조·순환 차단) |
| `stack.business` | 질문 원문에 실제로 있는 이름만 쓴다(지어낸 이름은 버림). 선택은 사업장 인식기가 한다. `code`는 숫자이거나 `all` |
| `pollutants` | nox·sox만(나머지는 버림) |
| `time` | yesterday·today·now·date·hours(1~72)·other. 형식이 틀리면 버림, `other`는 "지원 안 함"으로 남긴다 |
| `operation` | mean·max·min·sum. 그 밖은 버림 |

모델이 낸 값은 그대로 믿지 않고 코드가 다시 검증한다. 숫자는 도구가 계산한 값만 쓴다.

## 5. 부분 상태와 응답

부분마다 `Part.status`: `DONE`(처리됨) · `NEEDS_INPUT`(빠진 정보가 있음, 이유를 `notice`에 적음) · `UNAVAILABLE`(지원하지 않음: 없는 에이전트, 지원 밖 기간, 전체 굴뚝, 미등록 사업장, 차단) · `SKIPPED`(앞 부분이 끝나지 않아 건너뜀).

응답 `status`는 부분에서 계산한다: 모두 `DONE` → `ANSWERED`, 일부만 → `PARTIAL`, 없으면 `REFUSED`. 일부라도 못 한 부분이 있으면 `notices`에 "일부 부분은 처리하지 못했습니다"를 붙인다.

## 6. 구현 범위(2026-11-19 갱신)

흐름 전체가 끝까지 연결되어 있다: 가드 → 단일/복합 판별 → 계획(LLM) → 검증 → 모호한 칸은 카드 → 부분별 실행(데이터·근거·요약) → 부분별 상태. LLM 호출(해석기·계획기)은 `AGENT_LLM_BACKEND`로 고르고(`none`·`bedrock`·`local-agent`) 같은 코드 경로를 쓴다.

구현됨:
- 단일/복합 판별, 계획 검증(근거 확인·상한·의존), 모호하면 카드로 되묻기, 부분별 상태.
- **데이터 에이전트:** 집계·순위·기준 시각·결측 이유 + 파생 계산(허용기준 초과 횟수·연속 구간, 극값 시각, 두 값의 차이) + 굴뚝 전부(굴뚝별 나열) + 지역 안 순위 + 앞 순위의 1등 굴뚝 이어받기 + 최근 N일(3일까지는 72시간으로).
- **근거 에이전트:** 법령·공식 안내 조문 검색(아래).
- **요약 에이전트:** 전국 일일 요약(굴뚝 수·정상 수신율·초과가 있던 굴뚝 수·최댓값 상위). 도구 값만 조립한다.
- 로컬 에이전트 클라이언트(개발용), 서버 조립(환경 변수).

아직 없음(알려진 한계):
- **예측 에이전트:** E의 출력 형식이 정해지지 않았다. 지금은 "아직 지원하지 않습니다"로 알린다.
- **화면 조작(`ui`)**은 프런트 연결 단계의 일이다(지금은 안내만).
- 값 가공 계산(이상치 제외·보정·반올림), 지난주·한 달 같은 긴 기간, 지역 전체 평균(근거를 보이고 지역 안 순위·사업장 지정을 권한다).
- 카드의 자유 입력(이름 직접 입력, C6)은 계약 변경이라 미룬다.
- 데이터는 로컬 하루치, 대화 상태는 서버 메모리다(RDS·체크포인터 연결은 인프라 준비 뒤).
- 복합 응답 뒤 후속 질문 상속(`last_command`)은 갱신하지 않는다.

### 근거 에이전트 (`app/agent/evidence.py`)

- **조문 단위 검색:** 문서 전체를 모델에 던지지 않는다. 자료는 조문 청크 22개(법·시행령·시행규칙 14개 + 공식 안내 8개, `corpus/law-evidence-20261112.json`, 확인일 시행본)이고, 질문마다 상위 최대 3개 조문만 읽는다.
- **발췌는 원문 그대로:** 청크 원문의 연속 부분 문자열만 보여 준다(시험으로 검증). 출처 URL·법령명·조문 번호·확인일을 붙이고, 자료의 한계(미확보 별표 등)와 "위반·처분 여부를 판단하지 않는다"를 항상 붙인다.
- **지어내지 않는다:** 점수가 낮거나 질문의 핵심어 대부분이 문서에 없으면 "찾지 못했습니다"로 답한다. 일부 낱말만 없으면 그 낱말을 알린 뒤 겹치는 조문 후보를 보인다("설치비"가 없다 등).
- **벡터 DB를 염두에 둔 구조:** 검색기는 `Retriever.search(query, k)` 인터페이스다. 지금은 글자 조각 키워드 검색(`KeywordRetriever`, 제목 가중·동의어)이다. 벡터 DB(pgvector 등)를 붙일 때는 청크(`Chunk`)를 그대로 임베딩해 `VectorRetriever`를 같은 인터페이스로 넣고, 키워드 결과와 합치는 `HybridRetriever`로 확장한다. 청크가 조문 단위라서 인덱스를 바꿔도 발췌·출처 로직은 그대로 쓴다. 문서가 늘면 같은 JSON 형식을 추가한다.
- **질문 쪽:** 법령 질문만 있으면(측정값 조회 없음) 규칙으로 근거 에이전트 하나로 보내고, 데이터와 섞였으면 계획기가 `evidence` 부분을 낸다(질문에 법·기준·조문 같은 말이 있어야 인정).

### 파생 계산 (`tools.py`, `handlers.py`)

- 초과 횟수: 정상 관측 중 값 > 자료에 실린 허용기준인 30분 값의 수, 대략의 시간, 가장 긴 연속 구간. 기준값이 없는 관측은 뺀다. **법적 위반 판정이 아니다.**
- 극값 시각: 정상 관측의 최댓값(최솟값)과 그 시각.
- 차이: 이미 조회한 두 값의 차이와 변화율(같은 물질·단위만). 새 조회 없이 계산한다.
- 계산 부분은 값 부분의 굴뚝·물질·기간을 이어받고, 집계를 말하지 않은 값 부분은 계산 부분이 흡수해 불필요한 카드를 묻지 않는다.

## 6-0. 모호하면 사람에게 카드로 묻는다 (2026-11-18)

원칙(사용자 결정): **AI가 모호하거나 단정할 수 없는 부분을 마음대로 채우지 않는다.** 사람에게 카드로 물어 채우고, 모호하게 말한 사람도 카드에 답해서 원하는 조회를 얻어야 한다. 카드의 문구와 선택지는 코드가 정하며(모델이 쓰지 않음), **지금 실제로 실행할 수 있는 선택지만** 낸다. 구현: `app/agent/compound_cards.py`, 그래프 노드 `compound_judge → compound_ask(interrupt) → compound_run`.

| 모호한 경우 | 카드(kind) | 선택지 |
|---|---|---|
| 지역·묶음 말("충북", "발전소들") | `SCOPE` | 그 지역의 사업장(3곳 이하일 때) / **이 지역 안에서 순위로 보기** / 전국 순위로 보기 / 사업장 이름을 직접 말하기 / 이 부분은 빼고 진행. 물질·기간을 먼저 정한 뒤, **도구가 계산한 근거**와 함께 묻는다(아래) |
| 사업장 후보가 여럿 | `STACK_CANDIDATES` | 후보 사업장(최대 3) |
| 굴뚝 번호가 없거나 틀림, "굴뚝 전부" | `STACK_CODE` | 그 사업장의 굴뚝 번호(최대 8) |
| 기간이 없음 | `TIME` | 어제 / 오늘 현재까지 |
| 지원하지 않는 기간(지난주·새벽·지금) | `PERIOD` | 어제 / 오늘 현재까지 / 최근 24시간 |
| 물질·집계가 없음 | `POLLUTANT`, `OPERATION` | NOx / SOx / 둘 다, 평균·최댓값·최솟값 |
| 계획기가 확신하지 못한 칸(`unclear`) | 해당 칸의 카드 | 칸이 채워져 있어도 다시 묻는다 |

- 모든 카드에 "이 부분은 빼고 진행"이 있다. 카드 제목에 어느 부분인지(`[최댓값]`)를 적는다.
- 질문에 근거가 없는 값(직전 대화·모델이 지어낸 값)은 비워서 카드로 묻는다(`parse_plan`의 근거 확인).
- 지도에서 고른 굴뚝(`selectedStackId`)은 사용자가 정한 것이라 굴뚝 없는 부분에 바로 쓴다.
- 카드는 최대 6장까지 묻고(`MAX_CARDS`), 넘으면 남은 부분은 부분 상태로 알린다.
- 알려진 한계: 카드 답은 선택지만 받는다(자유 입력 없음). 지역에 사업장이 많으면 목록 대신 "전국 순위" 또는 "직접 말하기"를 쓴다. 직접 말하기는 그 부분을 `NEEDS_INPUT`으로 두고 다시 질문하게 한다(열린 결정 C6).

### 지역 평균을 하나의 값으로 답하지 않는 이유 (근거는 매번 도구가 계산한다)

"지원하지 않습니다"가 아니라 **왜 원하는 답이 아닐 수 있는지를 실제 자료로 보여 준다**(`app/agent/region.py`, `tools.region_profile`). 2026-11-10 하루치로 확인한 예:

| 지역 | 굴뚝 | NOx 값이 있는 굴뚝 | 정상 수신 | 허용기준 | 최대 / 중앙값 |
|---|---|---|---|---|---|
| 충북 | 171 | 95 | 47% | 6~270 ppm(23종) | 225 / 31 ppm |
| 전남 | 552 | 429 | 65% | 7~270 ppm(51종) | 327 / 27 ppm |
| 경기 | 762 | 305 | 33% | 10~230 ppm(36종) | 188 / 14 ppm |
| 강원 | 98 | 34 | 30% | 10~270 ppm(8종) | 222 / 80 ppm |

1. **수신 공백:** 정상 수신 슬롯이 30~65%뿐이고 나머지는 미수신·점검·기록 없음이다. 평균이 어느 굴뚝·어느 시각의 값으로 채워졌는지가 지역마다 크게 다르다.
2. **허용기준이 굴뚝마다 다르다:** 같은 값이라도 의미가 다르다(충북만 23종). 원시값의 평균은 규제 의미가 없고, 기준 대비(%)는 기준값이 없는 굴뚝이 빠진다.
3. **편차:** 최대/평균이 4~10배라 평균은 소수 굴뚝에 끌려간다.
4. **일일 요약 표로 만들면 평균의 평균이 된다.** 운영에서는 `obs.daily_stack_summary`(굴뚝·날짜별 집계)를 읽는데, 굴뚝마다 정상 수신 슬롯 수가 달라 가중 방식(굴뚝별 동일 가중 vs 슬롯 수 가중)에 따라 값이 달라진다.

그래서 지역 평균은 값으로 답하지 않고, 위 근거를 보인 뒤 **의미가 분명한 방법**을 권한다: 지역 안 순위(`region-rank`), 전국 순위, 사업장 직접 지정. 이런 질문이 반복되면 굴뚝별 분포(중앙값·기준 대비) 도구를 후보로 올린다(수신 공백 때문에 값의 신뢰도를 같이 표시).

### 자체 대화 시험 (2026-11-18)

모호하게 말하는 사용자를 흉내 내, 정답 세트 질문을 던지고 카드에 의도대로 답한 뒤 원하는 값을 얻었는지 확인했다(계획기는 Haiku가 만든 실제 계획, 하루치 실자료, Bedrock 없음). 기간·굴뚝이 확정되고 자료가 있는 138건:

- **원하는 값을 전부 얻음 108건(78%)**, 일부 4건, 하나도 못 얻음 26건. 질문당 카드 평균 1.7장(최대 6).
- 못 얻은 이유: 법령·예측·요약·화면 에이전트 없음(35 부분), 지난주 등 미지원 기간이라 빼기를 고름(27), 복합 단서를 놓쳐 단일 경로로 감(21건), 자료 없음(시험 자료가 하루치).
- 이 시험으로 찾아 고친 결함 3개: (1) 지역 말 + 굴뚝 번호("동두천 1번")를 묶음으로 오판, (2) 중앙값 같은 미지원 집계를 말해 주지 않음, (3) "기준 넘은 횟수" 같은 파생 계산이 안내 없이 평균 선택 카드로 넘어감 → 카드가 "아직 하지 않습니다"를 밝히고 대체값을 고르게 함(계획기 표시가 없어도 부분 설명(`note`)의 단서로 잡음).
- 시험 도구의 오류도 있었다(계획을 다른 질문 것으로 찾아 앞선 결과가 무효였고, 수정 뒤 다시 돌림). 남은 "원하지 않은 값" 14건 중 다수는 순위 답을 집계 정답과 비교하거나 정답 세트 부분에 굴뚝 번호가 비어 있는 시험 쪽 한계다.
- 스크립트: `D/morph-router-20261117/redteam/compound-eval-20261118/self_dialogue.py`(git 제외).

**계획기 프롬프트 비교(서브에이전트 Haiku, 같은 1,039질문):** 이전 프롬프트 대 새 프롬프트(`unclear`·`derived` 추가, 굴뚝은 `unclear` 제외, 비교는 값 부분과 계산 부분을 나눔)에서 계획 전부 맞음 67.2% → 60.7%, 자체 대화 원하는 값 전부 108 → 103건(138건 중)이다. 한 번씩만 돌린 표본이라 ±5건은 모델 변동과 구분하기 어렵다(반복 측정 필요). 새 프롬프트의 `derived` 표시는 안전 장치(파생 계산을 조용히 평균으로 바꾸지 않음)에 필요하므로 유지하고, 정확도 비교는 Bedrock Haiku 4.5로 같은 시험을 반복해 결정한다.

### 계획기 규칙 (프롬프트 + 코드, 2026-11-18~19)

모델을 바꿔 비교하기보다 **규칙을 분명히 말하는 것**이 효과가 컸다. 실패 사례에서 나온 규칙:

- **질문에 적힌 요청만 부분으로 만든다.** 근거·예측·요약·화면 부분은 질문에 그 말(법·기준·내일·예측·리포트·지도·바꿔 등)이 있을 때만 인정하고 없으면 코드가 버린다(`_AGENT_CUE`).
- **지역 이름·업종 묶음**은 `business`에 그대로 쓰고 `code`는 비운다. `code: all`은 사람이 "전부·전체·모든"이라고 말했을 때만. 모델이 지역 이름을 풀어 쓴 것(충북 → 충청북도)은 원문의 같은 지역 말이면 인정한다.
- 말하지 않은 집계는 추정하지 않는다(카드로 묻는다). 정답 세트가 추정해 채운 곳이 많아 "집계 불일치"의 상당수는 정답 쪽 추정이다.
- **앞 결과를 이어받는 말**(그 굴뚝·거기·1등)은 별도 부분 + `depends_on`(목록, 앞선 부분만). 걸러내기·"N위 안에 드나"는 순위 부분 뒤에 이어 붙인다. 직전 대화를 가리키는 말만 있으면 칸을 비운다.
- 비교·증감은 값 부분 각각 + 계산 부분(`derived`, 값 부분에 의존). 계산은 "아직 하지 않습니다"로 알린다.
- **답변 형식**(표로·3줄로·숫자만)은 부분이 아니다. 화면이 하는 일(지도 이동·굴뚝 선택·기간 바꾸기·그래프)만 `ui`.
- 위험한 요청(`blocked`)과 범위 밖 요청(`out_of_scope`)을 구분하고 예를 프롬프트에 둔다.

효과(로컬 Haiku, 같은 질문): 해로운 부분 표시 5/9 → 9/9, 공격 세트 전부 맞음 33% → 44%, 약한 유형 110건 부분 재현율 66% → 74%. 묶음마다 10건 안팎이라 방향만 본다.

## 6-1. 가드의 위치와 범위 (2026-11-18)

- **가드는 데이터 전용이 아니라 맨 앞단 공통이다.** 그래프의 첫 노드라서 단일·복합·다른 에이전트 요청 모두 여기를 지난다. 에이전트별 방어(데이터: 읽기 전용 도구·숫자 대조, 근거: 출처 표시)는 각 에이전트 경계에 따로 둔다.
- 가드는 **확실한 패턴만** 막는다(짧은 말·흔한 동사를 막으면 정상 질문이 거절된다). 이번에 데이터 변조·삭제 구어체(고쳐·날려·덮어써·비워), 설정 변경(기준치·검증 로직), 안전장치 해제(관리자 모드·제약 없는 AI), 내부 정보·비밀·계정 요구, 보고서 수치 조작을 추가했다.
- 측정(정답 세트에서 위험한 요청 84건): 막은 비율 19% → **68%**, 오차단은 정상 복합 0/921, 단일 질문 0/1043. 남은 놓침은 맥락이 필요한 은근한 조작("그냥 0으로 맞춰서 다시", "튀는 값은 빼고 계산")이다. 정규식에 억지로 넣으면 정상 질문을 막으므로 **계획기가 해당 부분을 `blocked`로 표시**하게 둔다.
- 이 에이전트에는 쓰기 도구가 없어서(조회만) 가드를 통과한 "고쳐놔"가 실제 변경으로 이어지지는 않는다. 그래도 해로운 부분을 조용히 무시하지 않고 **"변경·삭제는 할 수 없습니다"라고 알린다**(투명성).
- 범위 밖 요청(법률 상담, 하드웨어 수리, 개인정보 상담, 다른 나라 사업)은 가드가 아니라 라우터·계획기가 "지원하지 않음"으로 알린다. 정답 세트 x6 묶음의 `blocked` 라벨은 `out_of_scope`가 맞다.

## 6-2. 분류기 원인 분석과 라우터·계획기 수정 (2026-11-19)

질문: 분류가 틀리는 것은 "기능 위주로 나눠 보내는 구조" 때문인가, "말을 못 알아들어서"인가?

**실험.** 같은 요청 57개를 5가지 말투(원문·구어·오타/자모·긴 사연·암시 압축)로 바꾼 285문장을 만들어 라우터와 계획기(로컬 Haiku)에 넣었다.

| 측정 | 말투가 바뀌면 | 뜻 |
|---|---|---|
| 계획기 LLM의 원래 출력(코드 검증 전) | 전부 맞음 70~74%로 거의 그대로 | 모델은 말을 알아듣는다 |
| 같은 출력을 코드 단서 검사에 통과시킨 뒤 | 오타 문장만 39%로 추락 | 코드의 정규식이 오타를 못 읽어 값을 지웠다 |
| 라우터(복합 판별) | 같은 요청이 말투에 따라 복합/단일로 뒤바뀜 22/57, 위험한 복합 놓침 17.8% | 정규식이 "복합의 표면 단서"를 나열하는 구조의 한계 |

**결론.** 말을 못 알아듣는 쪽은 LLM이 아니라 **정규식 단서 검사**(라우터 게이트, 계획 검증의 근거 확인, 추출기)다. 구조 문제와 표면 문제가 같이 있었다.
- 표면: 오타·자모 흩어짐·이모지(`평ㄱ균`, `최댓갑`, `펴균`)에 단서가 깨진다.
- 구조: 복합을 "단서 낱말이 있다"로 알아내려면 요청 종류마다 단서를 끝없이 늘려야 한다.

**수정.**
1. `app/agent/fold.py`의 `fold()`: 단서 검사 전에 흩어진 자모·이모지·늘임표를 정리하고, 핵심 낱말(긴 것만)을 자모 한 글자 차이까지 바로잡는다. 짧은 낱말은 `언제`→`어제` 같은 오교정이 나서 표로만 고친다. 원문은 바꾸지 않는다(이름 찾기·사용자 표시는 원문).
2. 라우터는 "복합 단서가 있나"에서 **"아는 말로 설명되지 않는 낱말이 남나"**를 함께 본다(`unexplained_words`). 사업장·지역 이름과 단일 흐름이 아는 말(기간·집계·물질·요청 말투)을 빼고 낱말이 남으면 단일로 믿지 않고 계획기로 보낸다. 판단이 모호하면 안전한 쪽(계획기)으로 간다.
3. 계획 검증의 집계 단서에 `낮은/높은` 등을 더해, 순위 질문의 최소/최대가 지워지지 않게 한다.

**결과(같은 시험 세트).**
- 위험한 복합 992건 중 라우터가 놓친 것: 17.8% → **0.8%**.
- 같은 요청이 말투로 뒤바뀐 수: 22/57 → **4/57**.
- 대가: 단일 901건 중 계획기로 가는 비율 2.8% → **15.5%**(호출이 늘지만 결과는 같은 단일 한 부분).
- 계획기 코드 검증 후 전부 맞음: 말투별 63~74%로 평준화(오타 39% → 67%).

**남은 것.** 복합에서 한 굴뚝 이름을 두 번 말하는 문형("A사 …이랑 B사 …")은 일부 놓친다(0.8%). 계획기 채점의 남은 오차는 정답 라벨의 사업장 표기·후속 부분 유형 같은 채점 문제와, 앞 부분 기간 이어받기다.

## 6-3. 관문 대규모 시험과 보정 (2026-11-19)

원칙: **정규식은 "확실히 아는 말로만 이루어진 질문"만 단일로 통과시킨다. 모르는 낱말이 남거나 구조가 의심스러우면 LLM(계획기)으로 보낸다.** 시험 세트 7,906문장(종류 19가지, 단일·후속 단답·복합·공격·범위 밖·페르소나)으로 관문을 시험했다. 시험 도구와 문장은 git에서 제외된 `D/morph-router-20261117/redteam/compound-eval-20261118/gate10k/`에 둔다(`gate_eval.py`).

| 정답 종류 | 문장 수 | 단일 경로로 샌 것 | 비고 |
|---|---|---|---|
| 복합(둘 이상·다른 기능·연쇄·계산) | 2,263 | 8 (0.35%) | 나머지는 계획기·전용 경로 |
| 위험(주입·변조·비밀) | 967 | 0 | 가드 454, 계획기 511 |
| 단일 | 2,778 | 69%가 단일 | 30%는 계획기(비용) |
| 후속 단답 | 1,120 | 40%가 단일 | 59%는 계획기 |

보정 전(같은 세트): 복합·위험이 단일로 샌 것 185건(주로 영어 주입 112, "평균 및 결측 이유" 같은 둘째 조회). 보정 후 20건(대부분 "굴뚝", "3번?" 같은 모호한 입력이나 같은 집계 두 물질).

**바꾼 것**
- 영어·한자 낱말도 "설명되지 않은 말"로 센다(영어 주입 문장이 단일로 새던 구멍). 알려진 영문 낱말은 nox·sox·avg·mean·max·min·sum뿐이다.
- 값 요청에 결측 이유·순위·기준 시각이 함께 오면 복합으로 본다. 특정 굴뚝의 "전국 순위"도 복합이다(단일 흐름은 그 굴뚝의 순위를 못 내고 값만 답했다).
- 기간이 `N시간`으로 둘, `전일`/`금일`, 같은 물질을 두 번 말함, 번호 나열(`23, 24, 25번`), 미지원 집계(중앙값 등)를 단서로 더했다.
- 전용 경로(법령·요약·굴뚝 전부)는 다른 요청·위험한 말이 섞이면 타지 않는다(`other_reasons`). 이전에는 "보고서 만들어줘"가 어떤 말이 섞여도 요약 경로로 갔다.
- 버그: `굴뚝 2026`의 날짜를 굴뚝 번호로 읽어 단일 질문을 복합으로 보던 것, `주식회사`가 "주식"으로 읽히던 것, `시각 언제`(기준 시각 질문)가 계산 요청으로 읽히던 것.

**알려진 한계**
- 단일 흐름이 확신하고 틀린 답은 28건(시험 단일·후속 3,898건 중)이다. 대부분 사업장 이름 인식 문제(같은 이름 사업장 중 번호가 없는 쪽을 고름)와 후속 질문의 슬롯 이어받기다. 번호가 없는 사업장으로 가면 카드로 되묻는다. 313 이름 인식 쪽 과제다.
- 영어로 묻는 질문은 모두 계획기로 간다(단일 흐름이 영어를 못 읽는다).
- 후속 단답의 59%가 계획기로 간다(그·걔·말고 같은 이어받기 말). 안전한 쪽이라 지금은 두고, 계획기의 후속 처리 시험을 따로 한다.
