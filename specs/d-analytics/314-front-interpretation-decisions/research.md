## D2 — 규칙 코드의 작은 수정 3건

승인이 필요한 코드 변경이다(규칙은 D의 작업 코드이며 Spec Kit 설치 파일이 아니다).

1. **`㈜` 이름 매칭**: 분석기가 질문을 NFKC로 정규화(`analyzer.py` 128행)하는데 카탈로그 이름은 정규화하지 않아 `㈜` 이름 굴뚝(약 75%)이 전부 못 읽힌다. 카탈로그 이름을 같은 방식으로 정규화하면 정식 이름 읽기 24%→100%(600건 표본). 법인 표기를 생략한 입력은 별도 이름 검색이 필요(313).
2. **어휘 추가**(`lexicon.py`의 어휘 파일만 고치고 문장 패턴을 늘리지 않는다는 원칙대로): 시간 — "지난 N시간"(약 27건 실패), 날짜 표기 "11월 N일"·"N일"·"N/N"·"YYYY.MM.DD"(약 26건), 오타 "어재". 집계 — max·avg·average·맥스, 오타 "평교"·"최댓갑", 구어 "제일 높은 거". 물질 — "엔옥스"·"에스옥스"·"질소"·"황"·"NOx 말고 SOx"(부정 대체).
3. **자신 없으면 LLM에 넘김**: 도메인 신호가 없는 짧은 말을 OUT_OF_SCOPE로 단정하지 않는다(955건 중 127건을 범위 밖으로 처리해 36%만 맞음. SMALLTALK·UNSUPPORTED·후속 조각이 섞임). "바꿔줘"·"수정 전/없이/말고"·"삭제 말고"·"정지 신호 떴던 건 상관없음" 같은 말에서 위험 동사 때문에 정상 질문을 차단하는 오탐을 줄이고(955건에서 18건), 차단을 놓친 4건("메일로 쏴줘", "비번", 전화번호·주소)의 안전 어휘를 보강한다.

**권장**: 적용. 효과: 규칙이 스스로 결정하는 데이터 질문 15.6% → 26.4%, 결정한 것의 정확도 74.7% → 80.6%(이름 검색 포함). 위험 오류는 1건으로 그대로. 변경은 어휘·정규화·분기 보수화이며 구조를 바꾸지 않는다. 적용 뒤 같은 세트로 회귀를 잰다.

## D10 — 화면에서 선택한 굴뚝을 서버 요청에 싣는 경로

**현황**: 규칙 코드에는 `selectedStack`·`selectedSite`·`allowedStackIds` 맥락의 자리가 있다(`flow.py` 176·218·238행). 서버(`session.py` 70행)는 `{"authorized": True, "siteIds": 전체, "allowedStackIds": 전체 굴뚝}`만 넘긴다. 분리 프런트엔드의 `agent-chat.js`는 선택 굴뚝이나 로그인 사용자를 요청에 싣지 않는다. 313의 FR-002(선택 우선순위)·FR-010이 이 경로에 의존한다. `allowedStackIds`는 접근 제한이 아니라 서버가 아는 전체 굴뚝이다(2026-11-18 사용자 정정: 모든 굴뚝은 누구나 조회할 수 있다).

**선택지**: (a) 요청 계약에 `selectedStackId`·`favoriteStackIds`를 추가 / (b) 서버가 로그인 정보(311의 Cognito)에서 즐겨찾기를 읽음 / (c) 지금처럼 맥락 없음.
**권장**: (a)+(b) 조합. 화면 선택은 프런트가 보내고 즐겨찾기는 서버가 로그인 정보로 읽는다. 질문 문장 안의 문구로 선택을 만들지 않는다. 담당: D 프런트·서버, 311 로그인 연결 후. 미측정: 후보 우선순위 효과.

## D4 — 복합 질문의 우선순위(부분 답변 vs 허용 조합)

합의 5가 이미 "풀리는 부분은 불가능한 부분 때문에 막지 않는다(부분 답변 허용)"를 정했다. 시험에서 충돌한 곳은 분류 지침 문구다: "허용 목록에 없는 조합이거나 여러 일을 한꺼번에 요구하면 CLARIFY"가 PARTIAL(가능한 부분이 있는 복합 질문)보다 앞서 적용됐다.
- 근거: 정답 PARTIAL 65건 중 모델이 맞춘 것 45건(69.2%). PARTIAL→CLARIFY 20건(31%). 20건 중에는 "값 조회 + 실시간 값", "평균 + 굴뚝 순위"처럼 둘 다 data 에이전트 일인데 "한꺼번에"라고 되묻는 경우도 있다.
**선택지**: (a) 부분 답변 먼저, 허용 조합 규칙은 "가능한 부분이 둘 이상일 때만" 적용 / (b) 허용 조합 규칙 먼저 / (c) 질문마다 묻기.
**권장**: (a). 합의 5의 구현일 뿐 새 결정이 아니다. 지침 문구를 고치고 PARTIAL 65건 세트로 회귀를 잰다(고친 뒤 재시험은 아직 하지 않았다).

## D5 — 에이전트 배분 출력 형식

**근거**: 자유 목록 방식(A) 에이전트 집합 정확도 96.8%(717/741). 에이전트별 작업 메뉴 id 방식(M)은 id 형식을 정리한 뒤 93.3%(691/741), 에이전트가 실제로 실행되는 질문만 보면 A 97.7% 대 M 96.4%로 이득이 없다. M의 195회 id 형식 어긋남은 내 프롬프트 예시(`data.1`)와 메뉴 id(`data.tms_observations.1`)가 달랐던 시험 오류이며, 엄격 채점은 73.1%였다(방식의 결과로 쓰지 않는다). 오류가 몰리는 곳: "경보 울릴지"(data vs prediction), "센서를 추가하면 예측이…"(evidence vs prediction), 대상 없는 "다른 굴뚝으로 바꿔줘"(data vs ui). prediction을 필요 없이 부른 것 10건(정밀도 89.6%).
**선택지**: (a) 에이전트 단위 enum(강제 tool_use, 자산 등록부에서 뽑은 허용값) / (b) 작업 메뉴 id / (c) 자유 문자열.
**권장**: (a). 작업 메뉴는 각 에이전트 안쪽의 계획기가 쓴다. 경계 규칙을 자산 등록부에 명시한다: "경보 발생 현황"은 data, "경보 울릴지(미래)"는 prediction, 가정 질문은 evidence(한계 카드).
