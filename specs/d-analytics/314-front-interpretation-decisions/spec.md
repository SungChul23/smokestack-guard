# 기능 명세: 앞단 해석 구조와 열린 결정

**기능 번호**: 314 · **담당**: D 분석·화면·RAG
**작성일**: 2026-11-18(KST) · **상태**: 초안 — **결정 대기. 사용자가 각 결정을 확정하기 전에는 구현하지 않는다.**
**브랜치**: 만들지 않았다. 사람이 관리한다. 코드·설정·인프라를 바꾸지 않았다.
**입력**: 2026-11-17~18 대화, 멘토 문서(사용자 전달, 저장소로 확인되지 않은 부분 포함), 로컬 시험 결과([research.md](research.md))

## 이 문서의 역할

질문 하나가 들어와서 어떤 도구·에이전트로 가는지를 정하는 "앞단 해석"에는 아직 결정되지 않은 흐름이 많다. 이 문서는 (1) 결정이 필요한 항목과 서로의 의존 순서를 한곳에 모으고, (2) 각 항목의 선택지·근거·권장안을 적고, (3) 결정이 나면 이어질 작업을 미리 나눈다. 결정은 사용자(필요하면 담당 A·C·E와 멘토)가 한다. 이 문서의 권장안은 제안이며 확정이 아니다.

## 왜 지금 필요한가

- 12/7 주에 에이전트를 조립하고 12/11에 동결하며 12/17에 발표한다. 구현 위치·앞단 구조가 정해지지 않으면 조립이 시작되지 않는다.
- 이번 세션에서 만든 Python 서버·형태소 라우터·Bedrock 연결은 기존 spec(301~312)이 다루는 **브라우저 JavaScript 라우터**와 다른 경로이고, 어떤 spec에도 없다. 303은 "신규 서버·LLM·SQL은 추가하지 않는다"고 명시한다.
- 2026-11-18의 시험(분류 955건, 데이터 질문 정답 짝 1,043건)이 몇 가지 결정의 근거를 줬다.

## 사용자 시나리오와 검증

### US1 — 결정자가 근거와 함께 한눈에 결정한다 (P1)

사용자는 아침에 이 문서만 보고 열린 결정 각각에 "채택/수정/보류"를 정한다.

**독립 검증**: 결정 항목마다 질문·선택지·근거 수치·권장·영향·결정자가 있고, 결정 순서가 의존 관계와 맞는지 읽어 본다.

1. 모든 결정은 한 줄 질문과 선택지 2~4개, 권장 하나, 근거(수치 또는 코드 위치)를 가진다.
2. 결정 간 의존이 표로 보인다(D3 → D1 → …).
3. 근거가 없는 항목은 "미측정"으로 표시한다.

### US2 — 결정 뒤 같은 계약으로 구현이 이어진다 (P1)

결정이 나면 [tasks.md](tasks.md)의 조건부 작업이 활성화되고, 이미 정한 합의(분류→분기, 모델은 SQL을 쓰지 않음, 카드 문구는 코드가 정함)와 어긋나지 않는다.

**독립 검증**: 각 결정의 채택안이 기존 합의·spec 301~313과 충돌하는 곳을 표로 확인한다.

### US3 — 기존 합의를 바꾸는 제안은 숨기지 않는다 (P1)

기존에 합의한 틀과 다른 제안이 이 문서에 있으면 "틀을 바꾼다"고 명시하고 결정 항목으로 올린다.

**독립 검증**: 합의 목록(아래)과 각 결정을 대조해 충돌 표시가 있는지 본다.

## 이미 합의된 틀 (변경하려면 결정 항목으로 올린다)

1. 맨 앞에서 저렴한 LLM이 분류하고 에이전트로 분기한다. 에이전트가 서로를 자유롭게 부르는 구조는 아니다.
2. **모델은 SQL을 직접 쓰지 않는다.** 조건만 고르고 도구가 산식 등록부의 정의대로 질의를 만든다.
3. 차단·숫자 대조·서버 검증 같은 결정적 안전장치는 앞단과 경계에 둔다.
4. 자산 등록부가 "일을 보낼지 말지"를 정한다. 에이전트는 데이터·근거·예측·리포트 4종, 화면 조작은 에이전트가 아닌 도구다.
5. **복합 질문**: 부분으로 나누고 가능 여부를 한꺼번에 판정한다. 불가능한 부분 때문에 가능한 부분을 막지 않는다(부분 답변 허용). 카드는 의존 순서대로, 카드마다 "이 부분은 빼고 진행"을 둔다. 처음 허용 조합은 데이터+근거, 예측+근거, 데이터+화면이다.
6. **카드 문구와 선택지는 코드·등록부가 정하고 모델이 쓰지 않는다.** 카드는 선택지를 코드가 아는 칸(데이터 칸, 문서 조건)에만 쓴다.
7. 위치 분포·항목 추가 질문은 사용자가 든 예시일 뿐 채택된 자산이 아니다.

## 사용자가 알려 준 사실 (2026-11-18)

1. **배포 현황:** 프런트는 S3 버킷 `smokestack-tms-web-952900391026`에, 데이터는 RDS에, API는 EC2에 있다. 로그인을 앞단으로 옮겨 사이트 접속 자체를 막는 방안을 팀이 보고 있다. 로그인 식별자는 개인 즐겨찾기와 에이전트 대화 저장의 기준이다(굴뚝 조회를 제한하는 권한이 아니다). → D3(서버 정본)·D10·D13에 영향.
2. **멘토 기술:** 강제가 아니라 공부 겸 권장이다. 쓰는 이유와 측정 근거를 남기는 선에서 선택한다.
3. **질문 기록:** 받을 때 개인정보를 마스킹하거나 지우고 저장하는 방향이다. 실제로 개인정보가 들어올 일은 없지만, 시험에서 일부러 넣어 본다. → D13.
4. **LLM 모델:** 고정하지 않았다. 잘 나오고 저렴한 것으로 간다. 용도별로 다른 모델을 쓴다. → D11.
5. **정확도:** 사람 평가도 받아 완성한다. 사람 평가는 나중에 시험 창구에서 한다.
8. **관측·평가: LangSmith를 쓴다 (2026-11-18).** 개발·평가 단계에서 켜고(평가 세트 비교, 사람 평가 대기열), 운영(시연)은 전송 전 마스킹을 넣은 뒤 켤지 정한다. CloudWatch 구조화 로그가 기본이고 LangSmith는 보조다. 요금제·보존·자체 호스팅 가능 여부는 미확인.
7. **오케스트레이션 구현: LangGraph를 쓴다 (2026-11-18).** 에이전트 서버는 `services/dashboard-agent/`(A의 인프라, LangChain·Bedrock 전제)에 둔다. 흐름은 명시적 그래프로 정하고 모델이 다음 단계를 자유롭게 고르지 않는다. → D3·D1 구현 방식에 영향.
6. **굴뚝 부르기:** id → 100% 정확한 이름 → 법인 표기 없이 → 지역 이름만 잘라서 부르기 순으로 단계를 나누고, 잘라도 유일한 결과면 붙이고 아니면 카드로 묻는다. → [313](../313-stack-target-resolution/spec.md) 정의 4.

## 요구사항

- **FR-001** 이 문서의 모든 결정은 질문·선택지·근거·권장·영향·결정자를 가져야 한다(research.md).
- **FR-002** 결정이 나기 전까지 해당 결정이 막는 구현은 시작하지 않는다. 결정이 나면 같은 번호의 tasks를 활성화한다.
- **FR-003** 기존 합의와 어긋나는 제안은 "합의 충돌" 열에 표시한다. 표시 없이 합의를 바꾸지 않는다.
- **FR-004** 결정 결과는 이 문서의 상태와 tasks.md의 체크 표시, 관련 spec(303·313 등)의 갱신으로 기록한다.
- **FR-005** 근거가 없는 항목은 "미측정"으로 쓰고 임의로 채우지 않는다.

## 성공 기준

- **SC-001** 12/7 주 조립 시작 전에 D3·D1·D10이 확정된다.
- **SC-002** 확정된 결정마다 구현 작업이 tasks.md에서 활성화되고 관련 spec이 갱신된다.
- **SC-003** 기존 합의와 어긋난 채 구현된 항목이 없다(합의 충돌 열이 모두 해소).

## 가정

- 2026-11-18 시험은 사용자 Claude 계정의 Haiku 5.5(하위 에이전트)로 했고, 운영에서 쓸 Bedrock 모델(Haiku 4.5·Nova)과 다르다. Bedrock Haiku 5.5는 이 계정에서 아직 호출할 수 없다.
- 시험 질문은 LLM이 만들었다(정답을 만든 모델과 푸는 모델이 같은 계열). 실제 사용자 표현으로 다시 확인하기 전까지는 상한에 가깝다.
- 멘토의 구두 설명이 섞인 내용은 저장소로 확인되지 않은 것으로 표시한다.

## 멘토에게 확인할 질문 (D15, 사용자 전달용)

1. 에이전트 종류는 몇 개까지 구현해야 하고, 각각 얼마나 깊어야 하나(데이터·근거 2종 + 리포트·예측까지 4종이면 충분한가).
2. "센서를 추가한다면?" 같은 TMS 밖 가정 질문은 한계 카드로 안내하는 것으로 충분한가.
3. 맨 앞 분류를 LLM 하나로 하는 것을 기대하는가, 규칙+LLM 혼합도 인정되는가.
4. 에이전트 목록·범위를 언제까지 동결해야 하나.
