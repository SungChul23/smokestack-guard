# 구현 계획: 앞단 해석 구조 (조건부)

**기능**: 314 · **날짜**: 2026-11-18 · **명세**: [spec.md](spec.md) · **근거**: [research.md](research.md)
**상태**: 초안. 이 계획은 권장안(D3=A, D1=(b), D2 적용, D4=(a), D5=(a), D6=(a), D7=(b), D8=코드 고정)이 채택된다는 조건에서 쓴 것이다. 결정이 다르면 해당 단계를 고쳐 쓴다.

## 요약

맨 앞에서 LLM이 질문에서 칸을 뽑고(강제 tool_use의 enum), 코드가 필요 칸·빠진 칸·분기를 판정하고, 형태소 규칙이 확정 분기에서 LLM의 선택을 검증한다. 어긋나거나 자신 없으면 확정하지 않고 카드로 보낸다. 굴뚝 대상은 [313](../313-stack-target-resolution/spec.md)의 검색 모듈이 정한다. 카드 문구와 선택지는 코드가 정한다. 안전 차단·숫자 대조·서버 검증은 앞단과 경계에 그대로 둔다.

## 기술 문맥

| 항목 | 가정 |
|---|---|
| 정본 | Python 서버(`agent_server`). JS 라우터(301~312)는 이식 대상 목록으로 관리 |
| LLM | Bedrock Converse + 강제 tool_use. 운영 후보 Haiku 4.5(`global.`), Nova Lite(`apac.`). 시험은 temperature 0 단건 호출 |
| 출력 | verdict(7종) + agents(enum, 에이전트 단위) + 칸(stack 언급·물질·시간·집계·지표·patch) + 사유 한 문장 |
| 판정 | 빠진 칸·기대 분기는 코드가 칸에서 계산(`slot_common.expected`를 운영 코드로 재작성). 모델이 쓰는 건 칸 값뿐 |
| 검증 | 형태소 규칙의 확정 분기(READY·FOLLOWUP·UNSUPPORTED)와 LLM 결과를 대조. 불일치는 카드 |
| 안전 | 규칙 기반 차단·단발성이 LLM보다 먼저. 위험 동사 오탐은 D2로 줄인다 |
| 평가 | 분류 955·데이터 질문 1,043 세트를 회귀로 고정(D12). 모델·지침을 바꿀 때마다 재측정 |

## 원칙 점검 (constitution 0.1.0)

| 원칙 | 판단 |
|---|---|
| I 수집 연속성 | 해당 없음. 수집·원본·스케줄을 건드리지 않는다. |
| II 비밀값 | 새 비밀값 없음. Bedrock은 IAM 역할로 호출한다. 질문·로그에 개인정보가 들어올 수 있어 기록 전 마스킹 정책이 필요하다(D13). |
| III Terraform·적용은 사람이 | 서버 배포(EC2·Lambda 등)와 Bedrock 호출 권한은 담당 A가 Terraform으로 만든다. 에이전트는 plan까지만 한다. 권한은 사용 모델(Haiku 4.5·Nova Lite·Titan v2)의 InvokeModel로 한정해 plan에 적는다. 서울 리전 밖 호출은 가드레일이 막는다. |
| IV 데이터 계약 우선 | 요청 계약에 선택 굴뚝·즐겨찾기(D10)를 추가한다. 공식 키는 C가 정한다. 계약에 없는 필드를 읽지 않는다. |
| V 같은 조건의 정직한 비교 | 방식 비교는 같은 세트·같은 지표로 한다. 세트의 한계(LLM이 만든 질문, 같은 계열 모델)를 명세와 조사에 적었다. D11에서 다른 모델·사람이 쓴 질문으로 보강한다. |
| VI 설명 가능한 결과 | 해석 결과(칸, 분기, 규칙 검증 일치 여부, 카드 선택 경로)를 요청 기록에 남긴다. |

위반 없음. 복잡도 추적이 필요한 새 의존성은 이 계획 자체에는 없다(313에 numpy 선택 의존성).

## 비용 영향

LLM 호출: 질문당 1회(분류+칸 뽑기를 한 번에). 시험 규모(1,043건) 기준 Haiku 4.5로 몇 달러 이하로 예상(미측정). 서버 상시 비용은 D3 구현 위치와 A의 배포 결정에 따른다(API는 이미 EC2에 있고 데이터는 RDS, 프런트는 S3다. 2026-11-18 사용자 확인. 이 서버에 올릴지는 D3에서 정한다).

## 단계

1. **결정**: D3 → D1 → D10 → D2·D4~D8·D9 (spec의 순서도). 병렬로 D11~D15 요청(A·E·멘토).
2. **재시험(D11)**: Bedrock 모델로 분류·칸 뽑기 재측정. D1 확정 근거를 보강한다.
3. **계약 확정**: 요청·응답 계약(분류 출력, 선택 맥락, 카드)을 307과 맞춰 contracts에 쓴다.
4. **규칙 수정(D2)**: 어휘·정규화·보수화 적용, 회귀 측정.
5. **앞단 구현**: 칸 뽑기 → 판정 → 검증 → 카드. 313 검색 모듈과 연결.
6. **통합·평가 편입(D12)**: 세트를 `tests/`로 옮기고 CI(또는 수동 명령)로 회귀를 돈다.
