# 기능 명세: 법령 문서 질문의 요약 답변

**Feature Branch**: 기존 브랜치 유지 (사람 관리)
**Created**: 2026-11-19
**Status**: 로컬 구현·단위 검증 완료. 실제 모델(Haiku) 시험은 시험 재료만 준비함 (`results.md` 참고)
**Input**: 재영(D)과 합의: "굴뚝이 초과했거나 초과할 것 같을 때 어떻게 되나/어떻게 해야 하나를 물으면, 환경·굴뚝 규제 문서를 찾아 **요약해서** 보여 준다. 원문은 너무 길다. 관련 규정이 없으면 없다고 말한다(자료 부족 / 서비스 범위 밖). 이해가 안 되면 되묻는다."

## 배경

서비스가 다루는 대상은 굴뚝이 배출하는 오염물질(NOx·SOx)과 각 굴뚝의 지정 기준(ppm) 준수다. 지금 근거 에이전트(`evidence.py`)는 조문 14개와 공식 안내 8조각을 글자 겹침으로 검색해 **원문 문장을 그대로 잘라** 보여 준다. 11/19 시험(문서 질문 300개)에서 드러난 문제:

- 문서에 있는 질문(108개) 중 맞는 조문을 낸 것이 34%. 질문의 핵심어 절반 이상이 문서에 없으면 후보를 버리는 방어가 "받나요", "보관해" 같은 서술어를 핵심어로 세어 정상 질문을 버렸다.
- 모호한 질문(59개)의 31%가 조문을 냈다("어떻게 해?" → 자가측정 조문).
- 문서에 없는 질문과 범위 밖 질문이 같은 문구("찾지 못했습니다")로 답한다.
- 요약이 없다.

## 사용자 시나리오

### US1 — 초과 시 조치를 요약으로 안내 (P1)
"초과하면 어떤 조치를 받나요?" → 관련 조문(개선명령·조업정지 등)을 쉬운 말로 3~6문장으로 요약하고, 문장마다 근거 조문을 단다. 특정 시설의 위반·처분을 단정하지 않는다.
독립 검사: 요약의 조문 번호·숫자가 후보 조문 원문에 모두 있고, 검증을 통과한다.

### US2 — 그 굴뚝의 기준·측정값을 함께 (P1)
굴뚝이 정해진 질문("한솔제지 1번 NOx 초과했는데 어떻게 돼?")은 법령 요약 뒤에 그 굴뚝의 지정 기준 ppm과 최근 24시간 측정값을 코드가 붙인다. 모델은 이 숫자를 만들지 않는다. 기준값이 자료에 없으면 "자료에 없음"으로 표시한다.

### US3 — 없을 때 이유를 구분해 안내 (P1)
- 자료 부족: 보관 문서에 해당 규정이 없음(초과부과금 금액, 별표 수치 등)
- 서비스 범위 밖: NOx·SOx 배출 규제와 무관(먼지·암모니아 기준, 법률 상담 등)
- 되묻기: 어떤 상황인지 알 수 없음("어떻게 해?", "초과됐어요")

### US4 — 조합 질문과 후속 (P2)
"어제 NOx 평균 알려주고 초과하면 어떻게 돼?"처럼 데이터 부분과 문서 부분이 함께 오면, 문서 부분이 같은 질문의 굴뚝을 받아 기준·측정값을 붙인다. 후속("그럼 조업정지는?")은 직전 조회의 굴뚝을 이어받을 수 있다.

### US5 — 예측은 분리 (P3)
"ML 예측 결과 설명 요약기"로 정의하되 예측 결과의 형식이 정해지지 않았으므로 이번에는 "예측 결과 연결 준비 중" 안내만 유지한다. 공용 요약기(`summarizer.py`)는 예측 설명에도 쓸 수 있게 입력을 일반화한다.

## 요구사항

- FR-001: 검색은 조문 후보를 최대 5개까지 관대하게 모은다. 질문의 낱말이 문서에 없다는 이유로 후보를 버리지 않는다(요약기가 판단한다). 요약기가 없을 때(원문 발췌 모드)는 기존 방어를 유지한다.
- FR-002: 요약기는 후보 조문(id·제목·원문)과 선택적 굴뚝 사실을 입력으로 받아 `{answerable, reason, summary[{text, chunk_ids}], caveats, clarify}`를 낸다. 모델은 조문 번호·숫자·기간·금액을 지어내지 않는다.
- FR-003: 코드가 요약을 검증한다. 후보에 없는 chunk_id, 후보 원문(또는 굴뚝 사실)에 없는 조문 번호·숫자, 단정 표현("반드시", "위반입니다", "처분을 받게 됩니다" 등)이 있으면 요약을 버리고 **원문 발췌로 되돌리며** notice에 이유를 적는다.
- FR-004: 요약기 호출 실패·답 없음·형식 오류도 원문 발췌로 되돌린다. 답을 지어내지 않는다.
- FR-005: 굴뚝 사실(지정 기준, 최근 24시간 최댓값·최근값, 기준 초과 횟수)은 데이터 도구로 읽어 코드가 문장으로 붙인다. 기준값이 없으면 없다고 표시한다.
- FR-006: 계획기가 나눈 evidence 부분은 같은 부분의 굴뚝, 같은 계획의 데이터 부분 굴뚝, 직전 조회(`follows_last`)의 굴뚝 순으로 굴뚝을 받는다. 굴뚝을 정하지 못하면 일반 규정만 안내하고 그렇다고 표시한다(카드로 되묻지 않는다).
- FR-007: 응답 형식(`Part`, `Evidence`)은 바꾸지 않는다. 요약은 `Part.answer`, 근거는 `Part.evidence`, 이유 구분은 `Part.notice`와 `status`(DONE / UNAVAILABLE / NEEDS_INPUT)로 낸다.
- FR-008: 개발은 로컬 에이전트 클라이언트(Haiku)로 한다. Bedrock은 운영 클라이언트를 같은 인터페이스로 주입할 때만 쓴다.
- FR-009: 문서를 임의로 지어내 추가하지 않는다. 부족한 문서 목록은 `results.md`에 적는다.

## 경계와 가정
- 요약기가 한국어 숫자 표기("삼십 일")를 쓰면 숫자 대조가 못 잡는다. 후보 원문의 표기를 그대로 쓰도록 지시하고, 한계로 둔다.
- 요약 모델과 시험 문장이 모두 Haiku라 운영 모델과 다를 수 있다.
- 지금 문서는 조문 14개와 안내 8조각이다. 별표 8(업종별 허용기준 수치), 초과부과금, 과태료·벌칙은 없다.

## 성공 기준
- SC-001: 단위 시험 전체 통과(기존 297개 유지).
- SC-002: 검증기가 지어낸 조문 번호·숫자·후보 밖 chunk_id·단정 표현을 모두 걸러 원문 발췌로 되돌린다(단위 시험).
- SC-003: 문서에 있는 질문 108개에서 맞는 조문이 후보 5개 안에 드는 비율을 측정한다(요약 모델 없이 검색만).
- SC-004: 조합 질문에서 굴뚝·기준·측정값 연결이 의도대로 붙는지 결정적 시험으로 확인한다.
- SC-005 (미측정): 실제 모델의 answerable/reason 정확도, 환각 검출률, 조합 분해 정확도. 시험 재료를 준비하고 실행은 이후로 둔다.
