## 배경

한국환경공단 CleanSYS 공개 API는 과거 데이터를 다시 주지 않는다. 호출을 놓치면 그 측정값은 영구히 사라진다(헌법 I). 그래서 B는 10분마다 API 전체 스냅샷을 받아 **원문 그대로** Bronze에 보존한다.

A의 001은 같은 일을 AWS Lambda + EventBridge로 구현한다. 이 spec은 B가 `k-tms-bronze`에서 만든 **Airflow DAG 방식**을 다룬다. 두 방식은 같은 원본 경로 규칙을 쓰지만, 이 방식에는 001에 없는 **확정 표지**(manifest, `_SUCCESS`)와 **업로드 검증**이 있다. 확정 표지는 "이 실행 폴더는 믿어도 된다"는 신호이며, 이후 단계(Silver, 합성 데이터 적재 검증)가 완결된 스냅샷만 읽게 해 준다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 10분마다 스냅샷이 원문 그대로 보존된다 (Priority: P1)

운영 담당자(B, A)는 API 응답 원문이 가공 없이 시간대별 실행 폴더에 저장되기를 원한다. 이후 어떤 단계가 문제를 일으켜도 원문에서 다시 만들 수 있어야 한다.

**Why this priority**: 놓친 데이터는 되돌릴 수 없다. 원문 보존이 없으면 이후 모든 단계가 의미가 없다.

**Independent Test**: DAG를 한 번 실행해, 실행 시각 폴더에 원문(gzip)과 메타 파일이 생기고 원문을 풀어 해시를 계산하면 메타에 적힌 해시와 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 정상 응답을 받았을 때, **When** 한 번 실행하면, **Then** `ingest_date=<UTC 날짜>/hour=<UTC 시>/run_ts=<UTC 실행 시각>/` 폴더에 원문 압축 파일과 메타 파일이 생긴다.
2. **Given** 응답 본문이 저장되었을 때, **Then** 원문은 한 글자도 바뀌지 않고, 메타에는 요청 시각, 저장 시각, 응답 코드, 소요 시간, 시도 횟수, 원문·압축 크기, 원문 SHA-256이 기록된다.
3. **Given** API가 일시 오류(429, 5xx)나 연결 오류를 낼 때, **Then** 짧은 대기 후 최대 3회까지 다시 호출하고, 모두 실패하면 그 실행은 실패로 끝나며 원문은 저장되지 않는다.

---

### User Story 2 - 검증을 통과한 폴더에만 확정 표지가 붙는다 (Priority: P1)

Silver 담당(C)과 합성 데이터 검증은 완결된 실행 폴더만 읽고 싶다. 확정 표지가 있는 폴더는 원문과 메타가 온전하고 응답 점검을 통과했음을 보장해야 한다.

**Why this priority**: 반쯤 저장된 폴더를 Silver가 읽으면 조용한 데이터 오염이 된다. 표지가 그 경계다.

**Independent Test**: 정상 응답과 점검 실패 응답을 각각 흘려, 정상일 때만 manifest와 `_SUCCESS`가 생기는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 응답 점검(결과 코드 `"0"`, 전체 건수 = 실제 항목 수)을 통과했을 때, **When** 업로드한 파일을 다시 읽어 해시가 일치하면, **Then** 폴더에 `manifest.json`과 빈 `_SUCCESS` 파일이 생긴다.
2. **Given** 응답 점검이 실패했을 때, **Then** manifest와 `_SUCCESS`는 만들지 않고 실행은 실패로 끝난다. 이때 원문과 메타는 증거로 남는다.
3. **Given** 업로드 후 다시 읽은 해시가 올리기 전과 다를 때, **Then** 실행은 실패하고 확정 표지는 만들지 않는다.
4. **Given** manifest가 있을 때, **Then** 파일 목록(이름·크기·해시), 원문 해시, 확정 시각을 볼 수 있다.

---

### User Story 3 - 전날 슬롯 누락률 리포트가 날짜별로 남는다 (Priority: P2)

B는 "누락 1% 이하" 목표를 근거로 보고하려고 한다. 전날 하루(한국 시각) 동안 원본에 들어오지 못한 슬롯과 호출 횟수를 매일 리포트로 받고 싶다.

**Why this priority**: 수집이 정상이어도 API가 같은 값을 계속 주면 슬롯이 비는 조용한 공백이 생긴다. 이를 사람이 알아챌 장치다. 기능은 수집(P1) 없이는 의미가 없어 P2다.

**Independent Test**: 알려진 누락이 있는 날짜를 지정해 실행하고, 리포트의 누락 슬롯 목록이 실제와 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 매일 정해진 시각이 되었을 때, **When** DAG가 실행되면, **Then** 전날(한국 시각 기준) 하루의 리포트가 `reports/missing_rate/date=YYYY-MM-DD/report.json`에 저장된다.
2. **Given** 리포트를 열었을 때, **Then** 기대 슬롯(30분 단위 48개)과 누락 슬롯 수·목록, 기대 호출(10분 단위 144회)과 누락 호출 수·목록, 점검 실패·메타 없음·원문 없음 폴더 수, 생성 시각이 있다.
3. **Given** 누락 슬롯이 하나라도 있을 때, **Then** 리포트는 저장되고 DAG 실행은 실패로 표시되어 운영 담당자가 알 수 있다.
4. **Given** 과거 날짜를 놓쳤을 때, **Then** DAG의 과거 실행 채우기로 그날 리포트를 다시 만들 수 있다.

### Edge Cases

- **API 반영 지연**: 한국 시각 전날 마지막 슬롯(23:30)은 다음 날 새벽에야 API에 나타날 수 있다. 리포트 실행 시각이 이 지연보다 늦어야 한다.
- **한국 날짜와 저장 날짜의 차이**: 원본은 UTC 날짜로 저장되므로 한국 하루를 계산하려면 UTC 이틀치 폴더를 읽는다.
- **동시 실행**: 같은 DAG의 이전 실행이 끝나지 않았으면 새 실행을 시작하지 않는다.
- **전체 실행 시간 초과**: 실행 한 번이 8분을 넘으면 실패로 처리한다(10분 주기 안에 끝나야 한다).
- **이전 실행의 임시 파일**: 실패한 실행이 남긴 임시 파일이 다음 실행에 섞이지 않아야 한다(실행 시각별로 분리).
- **같은 응답이 반복되는 경우**: 이 방식은 응답이 같아도 매번 저장한다. 001(Lambda)은 해시가 같으면 저장하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 10분마다 공개 API 전체 스냅샷을 호출한다. 응답 원문은 가공하지 않고 gzip으로 압축해 저장한다.
- **FR-002**: 저장 경로는 `tms_cleansys/ingest_date=YYYY-MM-DD/hour=HH/run_ts=YYYYMMDDTHHMMSSZ/`(UTC)이며, 원문은 `snapshot.json.gz`, 메타는 `snapshot.meta.json`이다. 001과 같은 규칙이다.
- **FR-003**: 메타에는 요청 시각, 저장 시각, 응답 코드, 소요 시간, 시도 횟수, 원문·압축 크기, 원문 SHA-256, 원문 경로, 응답 점검 결과를 기록한다.
- **FR-004**: API 호출은 일시 오류(429, 500, 502, 503, 504)와 연결 오류에서 최대 3회까지 재시도한다(대기 2초, 5초). 다른 HTTP 오류는 즉시 실패한다.
- **FR-005**: 응답 점검은 JSON 구조가 예상과 같고 결과 코드가 `"0"`이며 전체 건수와 실제 항목 수가 같은지 확인한다. 실패한 응답도 원문과 메타는 증거로 남긴다.
- **FR-006**: 수집은 임시 보관(버퍼) → 업로드 후 해시 검증 → 확정의 세 단계로 나눈다. 업로드한 객체를 다시 읽어 올리기 전 해시와 같음을 확인한다.
- **FR-007**: 응답 점검과 업로드 검증을 모두 통과한 실행 폴더에만 `manifest.json`과 `_SUCCESS`를 만든다. 둘은 이후 단계가 "완결된 폴더"를 판별하는 표지다.
- **FR-008**: manifest에는 manifest 버전, 파일 목록(이름·크기·해시), 원문 해시, 확정 시각을 기록한다. [NEEDS CLARIFICATION: 현재 코드의 원문 해시 키 이름이 `ras_sha256`이라 오타로 보인다(`raw_sha256`). 이름을 계약에 어떻게 정할지, 이미 만들어진 manifest가 있다면 어떻게 할지 C와 합의해야 한다.]
- **FR-009**: 같은 DAG는 동시에 하나만 실행하고, 실행 전체는 8분, 각 작업은 5분을 넘기지 않으며, 작업은 실패 시 최대 2회 다시 시도한다(1분 간격).
- **FR-010**: 임시 보관 폴더는 실행 시각별로 분리하고, 업로드가 끝나면 지운다.
- **FR-011**: 매일 전날(한국 시각) 슬롯 누락률 리포트를 만든다. 대상은 30분 단위 48개 슬롯이며, 정상 점검을 통과한 폴더 안의 가장 최신 `mesure_dt`를 모아 비교한다.
- **FR-012**: 리포트는 `reports/missing_rate/date=YYYY-MM-DD/report.json`에 저장하며, 누락 슬롯 수와 목록, 누락 호출 수와 목록, 점검 실패·메타 없음·원문 없음 건수를 담는다.
- **FR-013**: 누락 슬롯이 있으면 리포트를 저장한 뒤 DAG 실행을 실패로 표시한다.
- **FR-014**: 원본 객체를 삭제하거나 다른 내용으로 덮어쓰지 않는다(헌법 I). 실패한 실행은 확정 표지를 만들지 않을 뿐 폴더를 지우지 않는다.
- **FR-015**: API 키는 환경 변수로만 받고 코드·로그·저장 파일에 쓰지 않는다(헌법 II). 로그에는 건수, 점검 결과, 저장 경로, 소요 시간 같은 요약만 남긴다.

### Key Entities *(include if feature involves data)*

- **실행 폴더(Run folder)**: 한 번의 호출 결과를 담는 폴더. 원문, 메타, (확정 시) manifest·`_SUCCESS`를 가진다.
- **원문(Snapshot)**: 응답 본문을 가공하지 않고 압축한 파일.
- **메타(Meta)**: 호출 이력과 응답 점검 결과.
- **확정 표지(Commit marker)**: manifest와 `_SUCCESS`. 있으면 "원문·메타가 온전하고 점검을 통과했다"는 뜻이다.
- **누락 리포트(Missing-rate report)**: 한국 시각 하루 기준 슬롯·호출 누락 집계.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 정상 실행의 모든 폴더에 원문, 메타, manifest, `_SUCCESS`가 모두 있고, 원문을 풀어 계산한 해시가 메타·manifest의 해시와 같다.
- **SC-002**: 응답 점검 실패 또는 업로드 검증 실패를 일으킨 실행의 폴더에는 `_SUCCESS`가 없다.
- **SC-003**: 하루 144회 호출 중 누락률이 1% 이하(슬롯 기준 누락 48개 중 1개 이하)이다. 이 값은 목표이며 달성 여부는 리포트로 확인한다.
- **SC-004**: 전날 리포트가 매일 자동으로 저장되고, 누락 슬롯 목록이 실제 폴더 내용과 같다.
- **SC-005**: 이후 단계(Silver 등)가 `_SUCCESS`가 있는 폴더만 골라 읽을 수 있다.

## Assumptions

- 실행 환경은 로컬(Docker Compose의 Airflow + MinIO)이며, AWS로 옮길 때 연결 정보만 바뀐다(`aws_default` 연결). 실제 AWS 계정 운영 경로는 A의 001(Lambda)이다.
- 현재 두 방식(001 Lambda, 이 DAG)이 **같은 원본 경로 규칙**을 쓰므로 같은 버킷에 동시에 쓰면 폴더가 섞일 수 있다. [NEEDS CLARIFICATION: 운영에서 Bronze 원본의 기준(source of truth)은 어느 쪽인가? DAG는 로컬 보조·검증용인지, 001과 함께 쓰는지, 아니면 001을 대체하는지 A·B가 정해야 한다.]
- 이 DAG의 슬롯 누락률 리포트는 A의 002(Lambda)와 기능이 겹친다. [NEEDS CLARIFICATION: 002와 이 DAG 중 어느 쪽을 운영 리포트로 쓸지, 중복이면 어느 한쪽을 정리할지 A·B가 정해야 한다.]
- API 키는 `.env`(커밋 금지)에서 읽고, 저장소에는 `.env.example`만 둔다.
- 로컬 실행 산출물(로그, 임시 파일, 응답 샘플)은 커밋하지 않는다(`k_tms_pipeline/.gitignore`).
- 확정 표지에 대한 데이터 계약(C)은 아직 문서로 정리되어 있지 않다. 이후 Silver가 `_SUCCESS`를 입력 조건으로 쓰면 계약으로 올려야 한다.
- Kafka 발행과 Spark → Bronze 적재는 이 spec 범위 밖이다. Bronze Table은 아직 만들지 않았고, 현재 Bronze는 원문 보존 형태(Raw)뿐이다. 합성 데이터 경로는 합성 데이터 생성기 spec(이슈 #29)에서 다룬다.
