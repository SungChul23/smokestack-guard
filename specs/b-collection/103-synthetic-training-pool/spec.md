# Feature Specification: K-TMS 학습용 합성 데이터 (일 단위 생성 + Kafka → Spark → Bronze 적재)

**Feature Branch**: `50-b-k-tms-학습용-합성-데이터-풀-생성-및-kafkasparkbronze-적재` (`29-k-tms-synthetic` 기준)

**Created**: 2026-11-16 · **Revised**: 2026-11-16 (일 단위 생성·backfill로 범위 변경)

**Status**: Draft

**Input**: User description: "K-TMS 실측처럼 합성 데이터를 매일 Bronze에 적재하고, Silver → ML-ready로 정제해 모델 학습에 쓴다. 생성기는 데이터를 계속 만들어 쌓고, 얼마나 쓸지는 ML 담당자가 정한다. 하루 단위로 독립 생성하며 10/30부터 어제까지는 backfill(하루치씩 배치)하고, **지금부터는 실측처럼 30분 슬롯마다 하나씩 자기 `run_ts` 시각에 올라가게(방출) 한다.** 생성량의 시작값은 그날 실측 양성과 1:1이다. Kafka로 발행하고 Spark가 학습용 합성 전용 Bronze 폴더에 원문 스냅샷 파일로 적재하며, 실측 수집기는 건드리지 않는다."

**관련 이슈**: #50 · **선행/관련**: #29, [102-synthetic-generator](../102-synthetic-generator/spec.md), [101-ktms-bronze-dag](../101-ktms-bronze-dag/spec.md)

## 배경

실측 K-TMS에서 사전 경고 라벨(`label-v1`)의 양성(현재 90% 미만인데 30분 또는 60분 뒤 90% 이상)은 매우 드물고, 일부 모양의 사건은 개수가 매우 적다. 이 spec은 **실측과 같은 모양의 합성 K-TMS 데이터를 매일 Bronze에 적재**해서, Silver → ML-ready를 거쳐 모델 학습에 쓸 수 있게 한다.

**원칙**: 생성기는 데이터를 **만들어 쌓고 태그를 남기는 것**까지만 책임진다. 학습에 **얼마나, 어떤 모양을** 쓸지는 ML 담당자(E)가 정한다. 생성량을 정하는 숫자(1:1 등)는 생성기의 규칙이 아니라 **시작값**이다.

**실측 현황** (분석 시점 2026-10-30 ~ 11-12 수집분, Athena `ktms_flat`, `label-v1`, 같은 측정은 가장 늦은 스냅샷 한 줄만 사용):

| | 양성 | 음성 | 양성 비율 |
|---|---|---|---|
| NOX | 5,374 | 1,029,915 | 0.519% |
| SOX | 1,439 | 477,742 | 0.300% |
| 합산 | 6,813 | 1,507,657 | 0.45% |

- 하루 NOX 약 12만 행, 하루 양성 약 350~460개(재료 기간 일평균 NOX 약 400, SOX 약 100). SOX 하루 양성은 10/30의 22개에서 11/12의 150개 안팎으로 늘어나는 추세다.
- 양성이 있는 NOX 굴뚝은 530개, 양성의 약 80%가 평소 수준이 높은(상위 99%값 90% 이상) 굴뚝에서 나온다.
- 실측 사건(90% 이상 행을 60분 재진입 기준으로 묶음)을 모양으로 나누면 아래와 같다. "직전 단서" 사건은 직전 30·60분에 유효한 90% 미만 값이 있는 사건으로, 양성 행이 생길 수 있는 사건이다.

| 모양 | NOX 사건 | NOX 직전 단서 사건 | SOX 사건 | SOX 직전 단서 사건 |
|---|---|---|---|---|
| OTHER (근접·중간 진입) | 2,402 | 1,690 | 385 | 330 |
| SPIKE | 663 | 663 | 196 | 196 |
| EXCEED | 511 | 113 | 122 | 90 |
| PLATEAU | 150 | 136 | 55 | 53 |
| OVER | 89 | 76 | 16 | 16 |
| GRADUAL (=S-02) | 52 | 52 | 14 | 14 |

**합성이 풀 수 있는 문제는 희귀한 모양의 양성 개수 부족**이다. 흔한 모양(OTHER, SPIKE)도 함께 만든다. 아래는 합성으로 풀 수 없다.

- **양성 비율**: 합성으로 양성 비율을 크게 올리는 것은 비현실적이다(1%를 만들려면 NOX는 합성 양성이 실측과 비슷한 수, SOX는 2.4배 필요). 비율은 학습 단계의 가중치·음성 언더샘플링·임계값 조정으로 맞춘다(담당 E).
- **짧은 기간과 소수 굴뚝에 몰린 양성, SOX의 시간 추세**: 실측이 더 쌓여야 풀린다. 한계로 명시한다.

**상태 단계 기준**: 70% 미만 정상, 70~79% 주의, 80~89% 경고, 90~99% 위험, 100% 이상 초과. 라벨 양성 기준 90%는 위험 단계의 시작이다.

**참조 통계와 누출**: 합성의 곡선은 실측 굴뚝의 통계(평균, 변동, 자기상관)를 빌려 만든다. 이 통계는 **고정된 버전**(현재 `ref-1030-1110`, 실측 2026-10-30 ~ 11-10)을 쓰며 합성 데이터의 날짜와는 독립이다. E의 K-TMS 외부 검증이 같은 기간(현재 10/31 ~ 11/10)을 쓰면 통계를 통해 검증 정보가 학습으로 새어 들 수 있으므로 기간을 E와 맞춘다(열린 질문 참조).

이 spec은 102(평가·시연용, 이슈 #29)와 별개다. 102의 생성기 코드(`k_tms_synthetic/`)에서 필요한 모듈을 새 폴더(`k_tms_synthetic_train/`)로 복사해 쓰고, **학습용 합성 데이터의 일 단위 생성(backfill 포함)**과 그것을 **Kafka → Spark → Bronze로 적재하는 경로**를 다룬다. 실측 수집기(`tms_cleansys/`, Lambda)는 건드리지 않는다.

합성과 실측은 **저장 경로**(학습용 합성 전용 폴더)와 **`SYN-` 접두어 굴뚝 코드**로 구분한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 하루 단위로 합성 데이터를 생성한다 (backfill 포함) (Priority: P1)

수집·Bronze 담당(B)은 날짜를 지정하면 그날의 합성 스냅샷 전체(슬롯마다 1개, 하루 48개)를 만들고, 10/30부터 오늘까지는 날짜별로 한꺼번에 만들고(backfill), 이후에는 매일 하루치를 만들고 싶다.

**Why this priority**: 합성 데이터가 실측처럼 매일 쌓여야 Silver·ML-ready로 흘러가 모델이 쓸 수 있다.

**Independent Test**: 날짜 하나를 지정해 생성하고, 같은 날짜를 두 번 만들었을 때 결과가 바이트 단위로 같으며, 날짜가 서로 다른 두 날을 순서와 무관하게 만들어도 결과가 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 날짜를 지정했을 때, **Then** 그날의 슬롯(30분 간격 48개)마다 스냅샷이 하나씩 만들어지고, 스냅샷은 그날 활성인 합성 굴뚝의 행을 합쳐 담는다.
2. **Given** 자정을 걸치는 에피소드가 있을 때, **Then** 에피소드는 (시작 날짜, 번호)에서 정해지는 seed로 통째로 만들어지므로, 저장된 상태 없이 전날 시작한 에피소드의 오늘 부분을 seed만으로 다시 만들 수 있다. 그래서 어떤 날짜든 전날 결과를 읽지 않고 독립적으로 만들 수 있다.
3. **Given** 같은 날짜를 같은 설정으로 두 번 생성했을 때, **Then** 산출물이 바이트 단위로 같다.
4. **Given** 날짜 범위(예: 10/30 ~ 어제)를 지정했을 때, **Then** 날짜마다 독립적으로 만들어지고, 날짜를 만드는 순서가 결과에 영향을 주지 않는다.

### User Story 2 - 합성 스냅샷이 Kafka → Spark → Bronze로 적재된다 (Priority: P1)

수집·Bronze 담당(B)은 합성 생성기가 스냅샷을 Kafka로 발행하고, Spark가 이를 읽어 Bronze의 학습용 합성 전용 폴더에 실측과 같은 원문 스냅샷 파일 구조로 적재하는 것을 확인하고 싶다. 과거 날짜는 하루치씩 한꺼번에, **지금부터는 실측처럼 30분 슬롯마다 하나씩 도착 시각에 맞춰** 쌓이기를 원한다.

**Why this priority**: 계획서의 Kafka → Spark → Bronze 경로를 합성 데이터로 먼저 검증할 수 있고, 실측 수집을 건드리지 않아 수집 공백 위험이 없다.

**Independent Test**: 이미 검증된 102의 평가용 에피소드 16개를 재료로 발행·적재하고, 결과를 파일로 직접 쓴 결과와 비교한다(학습용 생성기가 없어도 파이프라인만 검증). 검증용 별도 폴더에 적재하고 학습용 폴더는 사용하지 않는다.

**Acceptance Scenarios**:

1. **Given** 스냅샷 N개를 발행했을 때, **Then** Bronze 학습용 합성 폴더에 `ingest_date=/hour=/run_ts=` 폴더 N개가 생기고 각각 `snapshot.json.gz`, `snapshot.meta.json`, `manifest.json`, `_SUCCESS`를 가진다.
2. **Given** 같은 토픽을 두 번 처리했을 때, **Then** 결과가 같다(멱등).
3. **Given** Spark 작업을 중간에 중단했다가 재시작했을 때, **Then** 빠짐도 중복도 없이 이어진다.
4. **Given** 같은 스냅샷을 파일 모드로 직접 만든 결과와 Kafka 경로로 만든 결과를 비교했을 때, **Then** 파일이 바이트 단위로 같다.
5. **Given** 저장 도중 실패했을 때, **Then** `_SUCCESS`는 데이터 저장과 해시 검증이 끝난 뒤에만 생긴다.
6. **Given** 오늘 하루치가 만들어져 있을 때, **When** `release`를 실행하면, **Then** `run_ts`가 현재 시각(UTC) 이전이고 아직 올리지 않은 스냅샷만 발행되고, 현재 시각 이후의 스냅샷은 발행되지 않는다.
7. **Given** `release`를 10분마다 실행할 때, **Then** 각 스냅샷은 자기 `run_ts`(측정 시각 + 70분) 이후 첫 실행에서 Bronze에 나타나, 실측처럼 시간에 따라 슬롯마다 하나씩 쌓인다.
8. **Given** `release`를 같은 시각에 여러 번 실행하거나 실행을 건너뛴 뒤 다시 실행했을 때, **Then** 밀린 스냅샷이 한꺼번에 올라가고 Bronze 결과(경로와 내용)가 같다(멱등).

### User Story 3 - ML 담당자가 태그로 골라 쓴다 (Priority: P1)

모델 담당(E)은 쌓인 합성 데이터에서 날짜, 성분(NOX, SOX), 모양(SPIKE, EXCEED, PLATEAU, OVER, GRADUAL, OTHER), 양성 건수를 기준으로 어떤 에피소드를 얼마나 학습에 쓸지 직접 고르고 싶다.

**Why this priority**: 합성 양과 모양 비중의 최종 결정은 E의 몫이다. 생성기는 선택할 수 있는 정보를 제공하는 것이 전부다.

**Independent Test**: `manifest.jsonl`만으로 (날짜 × 성분 × 모양)별 에피소드 수와 양성 수를 집계할 수 있고, 일부 에피소드만 골라내도 그 에피소드의 행이 완전한지 확인한다.

**Acceptance Scenarios**:

1. **Given** 생성이 끝났을 때, **Then** 모든 에피소드가 날짜·성분·모양·참조 굴뚝·합성 굴뚝 코드·행 수·참조 통계 버전을 `manifest.jsonl`에 가진다(라벨 건수는 Silver·ML-ready 연결 후 추가한다).
2. **Given** E가 일부 에피소드를 골랐을 때, **Then** 골라낸 에피소드의 모든 행은 합성 굴뚝 코드(`SYN-…`)로 구분되어 다른 에피소드 없이 독립적으로 쓸 수 있다.
3. **Given** 합성 데이터가 실측과 같은 날짜에 들어 있을 때, **Then** `SYN-` 굴뚝 코드와 저장 경로로 합성만 정확히 걸러낼 수 있다(검증·평가에서 제외하기 위해).

---

### User Story 4 - 생성 결과를 점검한다 (Priority: P2)

검수자는 생성된 합성 데이터가 규칙을 지켰는지(구조, 날짜, 합성 굴뚝 코드, 라벨 건수, 모양) 자동으로 확인하고 싶다.

**Why this priority**: 이 데이터는 모델 학습에 쓰이므로 구조·라벨·모양의 오류는 학습 결과를 오염시킨다.

**Independent Test**: 일부러 규칙을 어긴 출력(합성 굴뚝 코드가 실측과 겹침, 에피소드가 자정을 넘음, 라벨 건수 불일치, 모양 판정 불일치)을 만들어 각각 걸리는지 확인한다.

**Acceptance Scenarios**:

1. **Given** `SYN-` 굴뚝 코드가 실측 굴뚝 코드와 같을 때, **Then** 불일치로 표시한다.
2. **Given** 하루치 스냅샷의 측정 시각이 지정한 날짜(KST)가 아니거나 슬롯이 48개가 아닐 때, **Then** 불일치로 표시한다.
3. **(후속: Silver·ML-ready 연결 후)** **Given** `label.py`(`label-v1`)로 다시 센 양성·음성·제외 건수가 `manifest.jsonl`의 값과 다를 때, **Then** 불일치로 표시한다.
4. **Given** 생성한 곡선이 `classify_shape`로 판정했을 때 의도한 모양과 다를 때, **Then** 불일치로 표시한다.
5. **Given** 102의 구조·필드·해시·경로·격자·형식 검사는, **Then** 학습용 폴더에도 그대로 적용된다.

### User Story 5 - 모양 생성 방법을 단계적으로 높인다 (Priority: P3)

개발자는 1단계(규칙 기반 + 범위 무작위화)로 먼저 만들고, E의 비교 실험에서 합성이 도움이 된다고 확인되면 모양 구간을 실측 템플릿 증강(사건이 많은 모양)이나 실측 파라미터 기반 생성(중간)으로 바꾸고 싶다.

**Why this priority**: 합성이 학습에 도움이 되는지 모르는 상태에서 템플릿·파라미터 체계를 먼저 만들면 비용이 낭비될 수 있다.

**Independent Test**: 1단계로 만든 데이터로 E가 "합성 없음 / 합성 포함"을 비교하는 실험을 마친 뒤 2단계 도입 여부를 결정한다. 모양 구간을 만드는 부분만 교체 가능한 구조인지(`trajectory.inject`는 궤적 목록만 받는다) 확인한다.

**Acceptance Scenarios**:

1. **Given** 1단계 설정일 때, **Then** 같은 모양에서도 에피소드마다 궤적이 범위 안에서 달라지고 모두 모양 판정 규칙을 통과한다.
2. **Given** 모양 구간 생성 방법을 바꿀 때, **Then** 계획, 시각표, 스냅샷 만들기, 쓰기, 점검, Kafka 이후 단계는 바뀌지 않는다.

---

### Edge Cases

- **같은 날짜를 다시 만들 때**: 같은 설정·seed면 같은 결과이고, 이미 적재된 경로에는 같은 내용이 덮어써진다. 설정(생성량, 통계 버전)이 바뀌면 `generator_version`과 `stats_version`을 바꾸고 manifest에 남긴다.
- **backfill의 부분 일**: 수집 첫날(10/30)은 일부 시간만 실측이 있으나, 합성은 완전한 하루로 만든다(합성에는 수집 공백이 없다).
- **자정을 걸치는 에피소드**: 에피소드를 하루 안에 가두면 시작이 낮으로 치우쳐 합성 양성이 밤에 거의 생기지 않고, E의 시간대 피처(`hour_sin`, `hour_cos`)로 모델이 "합성 = 낮"을 배울 수 있다. 그래서 자정을 걸치는 에피소드를 허용하고, 하루를 만들 때 **전날 시작해 오늘로 이어지는 에피소드도 seed로 다시 만들어** 그날 슬롯에 넣는다. 에피소드가 하루 이상 걸치지는 않는다(길이가 하루 미만).
- **방출 실행이 멈췄다 재개될 때**: 밀린 스냅샷(`run_ts`가 지금 이전)을 다음 실행에서 한꺼번에 올린다. 그 사이 도착 시각은 실측과 달라지지만 경로와 내용은 같다.
- **방출 시작 시점의 오늘**: 방출을 처음 시작하는 날은 이미 지난 슬롯이 있으므로 첫 실행에서 한꺼번에 올라가고 이후 슬롯부터 하나씩 올라간다.
- **backfill 첫날**: 첫날(10/30)에는 전날(10/29) 시작 에피소드도 seed로 만들어 넣는다. 첫날 앞쪽 슬롯이 비지 않게 하기 위해서다.
- **참조 굴뚝 후보가 부족할 때**: 조건을 완화하는 대신 가능한 만큼만 만들고 부족 수를 보고한다.
- **SOX GRADUAL(14건)·OVER(16건)**: 모양의 실측 사건이 적어 정보의 한계가 있다. 같은 14건의 변형을 많이 만들어도 새 정보가 늘지 않으므로 많이 만들어 두더라도 선택은 E가 한다.
- **Kafka 중복 전달 / 같은 `run_ts`에 다른 내용**: 같은 내용이면 덮어쓰고, 다른 내용이면 오류로 멈춘다.
- **Spark 중단 후 재시작**: 체크포인트에서 이어간다. 한 스냅샷의 파일 일부만 저장된 상태는 `_SUCCESS`가 없으므로 미완성으로 구분된다.
- **합성이 검증·평가 데이터에 섞일 위험**: 합성은 실측과 같은 날짜에 들어간다. ML-ready에서 시간 기준으로 분할하면 합성이 검증·평가 쪽에 섞일 수 있으므로 E가 `SYN-` 굴뚝 코드로 제외해야 한다(열린 질문 참조).
- **Kafka 메시지 크기**: 스냅샷 원문이 1MB(Kafka 기본 한도)를 넘지 않게 한 스냅샷에 담는 합성 굴뚝 수를 정한다.
- **스냅샷 구조(2026-11-05 실측으로 확인됨: 모든 (굴뚝, 측정 시각) 154,842건이 스냅샷 한 개에만 나타남)**: 실측은 하루 약 50개 스냅샷(슬롯당 1개)이다. 학습용은 처음부터 실측 구조에 맞춘다(102는 10분마다 같은 내용을 3번 반복하므로 따르지 않는다).

## Requirements *(mandatory)*

### Functional Requirements

**데이터 구성**

- **FR-001**: 합성 데이터는 성분(NOX, SOX) × 모양(SPIKE, EXCEED, PLATEAU, OVER, GRADUAL, OTHER)별 에피소드로 구성하고, 성분별로 따로 만든다(NOX·SOX 합산하지 않는다). 합성 굴뚝은 단일 성분이며 측정하지 않는 성분 필드는 `None`이다.
- **FR-002**: 모양은 실측 사건 정의로 판정한다. 사건은 기준대비율 90% 이상 행을 60분 재진입 기준으로 묶은 것이다.
  - EXCEED: 100% 이상 3칸 이상
  - PLATEAU: 90% 이상 4칸 이상, 최고 100% 미만, 진입 2회 이하
  - OVER: 90% 경계를 3번 이상 넘어 진입
  - SPIKE: 90% 이상 1~2칸, 사건 시작 30분 전이 70% 미만
  - GRADUAL: 시작 직전 120·90·60·30분 전 값이 엄격히 증가, 30분 전 80% 이상, 120분 전 70% 미만
  - OTHER: 위에 해당하지 않는 나머지
  - 판정은 **EXCEED → PLATEAU → OVER → SPIKE → GRADUAL → OTHER 순서로 먼저 맞는 것**을 쓴다. GRADUAL은 시작 직전 120·90·60·30분 전 값이 모두 유효해야 한다.
- **FR-003**: 새 모양은 (실측에서 비중이 크고, 기존 모양과 다르며, E의 모양별 재현율이 낮을 때) 세 조건을 모두 만족할 때만 추가한다.
- **FR-004**: 합성 에피소드는 합성 양성 외에 음성 행을 포함한다. 에피소드 길이는 앞 구간(warmup, 최소 6칸. E의 피처가 최대 6칸을 봄), 모양 구간, 복귀 구간으로 정하며 설정 가능해야 한다. 합성 음성 수는 이 길이에서 나오고 manifest에 기록한다.
- **FR-005**: 합성에는 결함(S-05~S-08: 문자열, 깨진 데이터, 중복·충돌, 지연·누락)을 넣지 않는다. 값은 항상 숫자 문자열이다.

**일 단위 생성과 생성량**

- **FR-006**: 생성은 **날짜 하나를 지정하는 명령**과 **날짜 범위를 지정하는 backfill 명령**을 제공한다. backfill은 날짜마다 독립 실행이다.
- **FR-007**: 하루를 만들 때 필요한 값은 모두 **seed와 설정에서 결정적으로 다시 만들 수 있어야** 한다. 에피소드는 (시작 날짜, 성분, 모양, 번호)에서 정해지는 seed로 통째로 만들어지며, 자정을 걸치는 에피소드는 전날 시작분을 seed로 다시 만들어 그날 슬롯에 넣는다. 그래서 전날 상태를 저장하거나 읽지 않고도 날짜별로 독립 생성되고, 날짜를 만드는 순서가 결과에 영향을 주지 않는다. 에피소드 길이는 하루 미만이다.
- **FR-008**: 하루 생성량은 설정의 **(성분 × 모양)별 하루 에피소드 수**로 정한다. 시작값은 성분별로 그날 합성 양성이 실측 일평균 양성(재료 기간 NOX 약 400, SOX 약 100)과 같도록(1:1) 정하고, 실측에 부족한 모양(GRADUAL, OVER 등)은 실측 모양 비중보다 많이 넣는다. 계산 근거(사건당 양성 약 1.85, 모양별 비중)는 plan에 적는다. 이 숫자는 **권고 시작값**이며 학습에서 얼마나 쓸지는 E가 정한다.
- **FR-009**: 합성 에피소드의 참조 굴뚝은 실측에서 그 모양이 나온 굴뚝 유형과 맞추도록 설정 가능해야 한다(양성의 약 80%가 상위 99%값 90% 이상 굴뚝에서 나옴). 1단계는 102의 참조 선택(`stats.py`)을 재사용한다.
- **FR-010**: 하루를 만들 때 seed는 설정 seed와 날짜에서 결정적으로 정한다(같은 날짜는 항상 같은 결과).

**곡선 생성**

- **FR-011**: 1단계는 규칙 기반 + 범위 무작위화로 만든다. 배경과 복귀 구간은 AR(1)(`episode.py`)이고, 모양 구간은 고정 숫자 대신 설정한 범위에서 뽑은 궤적을 `trajectory.inject`로 끼운다. 궤적의 모든 값이 해당 모양 판정 규칙(FR-002)을 통과해야 한다.
- **FR-012**: 2단계(E의 비교 실험에서 합성이 도움이 된다고 확인된 뒤)에서는 모양 구간 생성만 바꿀 수 있어야 한다. 사건이 많은 모양은 실측 템플릿 증강, 중간은 실측 파라미터 기반, 아주 적은 모양은 규칙 기반을 유지한다. 모양 구간을 만드는 부분 외의 단계는 바뀌지 않는다.
- **FR-013**: 참조 통계는 **고정된 버전**(현재 `ref-1030-1110`)을 쓴다. 통계를 다시 뽑으면 통계 버전을 올리고 manifest에 남긴다. 합성 데이터의 날짜와 통계의 기간은 독립이다.

**스냅샷과 적재**

- **FR-014**: 학습용은 실측 구조(슬롯마다 스냅샷 1개, 하루 48개)에 맞춘다. 여러 에피소드를 같은 슬롯의 스냅샷에 합쳐 담되, 항목의 굴뚝 코드로 에피소드를 추적할 수 있게 한다. 한 스냅샷의 크기는 Kafka 메시지 한도 안이어야 한다.
- **FR-015**: 합성 스냅샷의 `run_ts`는 **측정 시각(KST를 UTC로 바꾼 값) + 70분**이다(실측의 94.9%가 70~79분 뒤에 처음 나타남). 지연은 넣지 않는다.
- **FR-016**: 스냅샷 항목은 실측과 같은 18개 필드(문자열·`None`)이며 합성을 표시하는 필드를 넣지 않는다. 합성 여부는 저장 경로와 `SYN-` 굴뚝 코드로만 구분한다.
- **FR-017**: 합성 생성기가 스냅샷을 Kafka 토픽으로 발행한다. 메시지 하나는 스냅샷 하나(API 응답 원문 JSON)이고 키는 `run_ts`이다. 메시지는 원문만 담는다. 발행은 두 방식이다. (가) **배치**: 과거 날짜(backfill)는 하루치(48개)를 한꺼번에 올린다. (나) **방출(release)**: 지금부터의 데이터는 실측처럼 각 스냅샷을 자기 `run_ts` 시각에 맞춰 하나씩 올린다. 두 방식의 Bronze 결과(경로와 내용)는 같고, 저장소 객체의 수정 시각만 다르다(방출은 실제 도착 시각과 같다).
- **FR-018**: Spark(Structured Streaming 또는 일괄 처리)가 토픽을 읽어 Bronze의 학습용 합성 전용 폴더(임시 이름 `tms_synthetic_train/`, 계약 문서에서 확정)에 원문 스냅샷 파일 구조로 저장한다: `<학습용 합성 폴더>/ingest_date=/hour=/run_ts=/`에 `snapshot.json.gz`, `snapshot.meta.json`, `manifest.json`, `_SUCCESS`. `snapshot.meta.json`과 `manifest.json`은 Spark 쪽에서 원문과 `run_ts`로부터 **결정적으로** 계산한다(저장 시각 등 시각 필드도 처리 시각이 아니라 `run_ts`에서 유도).
- **FR-019**: 저장 경로는 메시지의 `run_ts`로만 정해 중복 전달에도 같은 경로에 같은 내용이 덮어써지게 한다(멱등). `run_ts`는 Spark가 처리하는 시각이 아니라 메시지에 든 시뮬레이션 시각이다.
- **FR-020**: `_SUCCESS`는 데이터 파일 저장과 해시 검증이 끝난 뒤에만 쓴다. 저장되는 파일 이름은 실측과 같다. 저장 방법은 plan에서 정한다.
- **FR-021**: 실측 수집기와 실측 경로(`tms_cleansys/`)는 건드리지 않는다. 학습용 합성 폴더를 Silver·ML-ready가 읽도록 하는 변경은 C의 영역이며, 합성이 ML에 쓰이려면 필요하므로 **이 spec의 선행·동시 협의 과제**로 둔다(열린 질문 참조).
- **FR-022**: 비밀값(저장소 계정 등)은 환경 변수로만 받고 코드·설정·커밋에 쓰지 않는다.
- **FR-023**: 전체 경로(발행, Kafka, Spark, 저장소)는 외부 계정 없이 로컬에서 재현할 수 있어야 한다. AWS 리소스(MSK, Glue 실행)는 이 spec에서 만들지 않는다. 실행 환경과 도구 버전은 plan에서 정한다.

**점검과 기록**

- **FR-024**: 점검(`validate`)은 102의 검사(구조, 필드, 해시, 경로, 격자, 형식, 응답, 쌍)를 학습용 폴더 이름만 바꿔 재사용한다.
- **FR-025**: 세트 점검을 추가한다: 하루치 스냅샷이 지정한 날짜의 슬롯 48개인지, 자정을 걸치는 에피소드의 앞뒤가 날짜별 생성에서 같은 곡선으로 이어지는지, `SYN-` 코드가 실측과 겹치지 않는지, (라벨 건수가 `manifest.jsonl`과 일치하는지는 Silver·ML-ready 연결 후 추가), 곡선이 의도한 모양으로 판정되는지.
- **FR-026**: (후속: Silver·ML-ready 연결 후 추가. ML-ready 결과와 대조해서 만든다.) `label.py`는 `label-v1` 규칙(반올림 없이 90% 기준, 현재 90% 이상이거나 미래 값을 모르면 제외)으로 양성·음성·제외 건수를 센다. 라벨은 Bronze에 넣지 않는다(manifest 태그로만 남긴다).
- **FR-027**: `manifest.jsonl`은 에피소드마다 날짜, 성분, 모양, 참조 굴뚝, 합성 굴뚝 코드, `seed`, 첫·마지막 측정 시각, 스냅샷 수, 행 수, 통계 버전, 생성기 버전을 가진다(라벨 건수와 합성 음성 수는 `label.py`가 생긴 뒤에 추가한다). 하루 단위로 파일을 나눠 쌓는다.

**방출 (지금부터의 데이터)**

- **FR-028**: `release` 명령은 `run_ts`가 현재 시각(UTC) 이전이고 아직 올리지 않은 스냅샷만 Kafka로 발행한다. 현재 시각 이후의 스냅샷은 올리지 않는다. 현재 시각은 시험을 위해 인자로 바꿀 수 있다.
- **FR-029**: `release`는 **멱등**이다. 몇 번을 실행해도, 실행을 건너뛰었다 다시 실행해도(밀린 스냅샷을 한꺼번에 올림) Bronze 결과가 같다. 올린 기록을 별도 상태로 두지 않고 경로와 내용의 결정성(FR-019)에 의존한다.
- **FR-030**: `release`는 오늘과 내일 하루치가 없으면 먼저 생성한다(날짜별 결정적 생성이라 비용이 작다). backfill은 어제까지, 방출은 오늘부터 담당한다.
- **FR-031**: 실행 주기는 실측 수집기와 같은 10분을 권장한다. 스케줄러 구성은 이 spec의 범위가 아니며, 실행 명령과 주기를 문서로 제공한다.

### Key Entities *(include if feature involves data)*

- **합성 에피소드(학습용)**: 한 모양의 사건 하나와 그 앞뒤 구간(하루 안). 참조 굴뚝 한 곳의 통계로 만든 합성 굴뚝(`SYN-…`)에 대응한다.
- **모양(shape)**: 실측 사건의 형태 분류(SPIKE, EXCEED, PLATEAU, OVER, GRADUAL, OTHER). 정의는 FR-002.
- **하루 생성량 설정**: (성분 × 모양)별 하루 에피소드 수. 시작값은 1:1(FR-008).
- **합성 스냅샷 메시지**: Kafka 메시지. 키 `run_ts`, 값은 응답 원문 JSON.
- **학습용 합성 Bronze 폴더**: 실측과 같은 파일 구조(`ingest_date=/hour=/run_ts=/`)의 합성 전용 저장 위치(임시 이름 `tms_synthetic_train/`).
- **`manifest.jsonl`**: 날짜별 에피소드 정보(모델 입력 아님, ML 담당자의 선택과 점검용).
- **참조 통계 버전**: 합성 곡선의 재료인 실측 통계(`data/ref_stats.csv`, 현재 `ref-1030-1110`).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 날짜 하나를 같은 설정으로 두 번 생성한 산출물이 바이트 단위로 같고, 두 날짜를 어떤 순서로 만들어도 결과가 같다.
- **SC-002**: 날짜별로 **시작하는** (성분 × 모양)별 에피소드 수가 설정과 같고, 합성 양성이 하루의 모든 시간대(24시간)에 걸쳐 분포한다(특정 시간대에 몰리지 않는다).
- **SC-003**: 하루 스냅샷이 슬롯당 1개(하루 48개)이고, 같은 (굴뚝, 측정 시각)이 한 번만 나타나며, 각 스냅샷의 원문 크기가 Kafka 메시지 한도 안이다.
- **SC-004**: `manifest.jsonl`만으로 (날짜 × 성분 × 모양)별 에피소드와 양성 수를 집계할 수 있고, 골라낸 에피소드는 다른 에피소드 없이 독립적으로 쓸 수 있다.
- **SC-005**: Kafka → Spark → Bronze 경로로 만든 폴더가 같은 스냅샷을 파일로 직접 만든 폴더와 바이트 단위로 같다(시각 필드는 `run_ts`에서 결정적으로 유도하므로 가능하다).
- **SC-006**: 같은 토픽을 두 번 처리해도, Spark를 중간에 중단하고 재시작해도 결과가 같다.
- **SC-007**: 합성 굴뚝 코드가 실측과 겹치지 않고, `SYN-` 코드와 저장 경로로 합성만 정확히 걸러낼 수 있다.
- **SC-008**: (후속) `label.py`로 다시 센 라벨 건수가 `manifest.jsonl`과 모두 일치한다.
- **SC-009**: 모든 합성 궤적이 해당 모양 판정 규칙(FR-002)을 통과한다.
- **SC-010**: 결함(문자열, 깨진 데이터, 중복·충돌, 지연·누락)이 합성 데이터에 0건이다.
- **SC-011**: backfill 범위(10/30 ~ 어제)가 날짜별로 모두 생성되어 Bronze 학습용 폴더에 적재된다.
- **SC-012**: `release`를 반복·건너뛰며 실행해도 Bronze 결과가 같고, 각 스냅샷은 자기 `run_ts` 이후 첫 실행에서 올라가며 그 이전에는 올라가지 않는다. 10분마다 실행하면 지연은 10분 이내이다.

## Assumptions

- 참조 통계는 실측 2026-10-30 ~ 11-10(고정 버전 `ref-1030-1110`)에서 뽑는다. 합성의 날짜는 통계 기간과 독립이며, backfill 범위는 10/30부터 어제까지, 이후는 매일 하루씩이다.
- E 자료(401 spec, 주간 보고 11/12) 기준: 현재 모델은 대만 CEMS로 학습하고 K-TMS는 외부 검증에 쓰며, 물질별 모델(NOX·SOX 분리), XGBoost 분류·회귀와 Random Forest 회귀, 시간 순서 분할, 피처는 최대 150분 lag와 3시간 이동통계(최소 6칸 이전 값)를 쓴다. 합성 K-TMS는 이후 학습 보강으로 쓰일 예정이며 그 시나리오는 E가 정한다.
- 실측 통계와 일별 양성 수는 Athena `ktms_flat`에서 `label-v1`로 뽑는다(양성 정의: 현재 90% 미만, t+30 또는 t+60이 90% 이상, 반올림 없음).
- 합성은 결함 없이 숫자 값만 쓰고, 모델은 합성 포함 여부를 비교 실험으로 검증한다(E).
- 102의 코드(`plan`, `stats`, `episode`, `scenarios/trajectory`, `snapshot`, `schedule`, `writer`)를 새 폴더 `k_tms_synthetic_train/`로 복사해 쓰고(`validate`는 이후 복사), 스냅샷 구조(하루 48개, 한 스냅샷에 여러 굴뚝)에 맞추는 수정은 이 spec에서 한다. 102의 평가용 생성 결과는 바꾸지 않는다.
- 이 spec은 현재 구조(Bronze = 원문 스냅샷)를 따르며 Bronze Table은 만들지 않는다.
- 가중치, 언더샘플링, 임계값 조정, 모델 학습은 범위 밖이며 E가 한다.
- 하루 생성량(1:1), 모양별 비중은 시작값이고 E의 실험으로 조정한다.
- 실측의 도착은 30분 슬롯이 갱신될 때(측정 시각 + 약 70분)이고 수집기는 10분마다 실행된다. 합성 방출도 같은 규칙(`run_ts` = 측정 시각 + 70분, 10분 주기 실행)을 따른다.

## 범위 밖

- 실측 수집 Lambda와 스케줄 변경, 실측 데이터 변형·삭제
- Silver·ML-ready 변환(피처·라벨 컬럼 생성), 모델 학습·평가, 가중치·언더샘플링 설정, 모양별 재현율 평가(C·E 영역). 이 spec의 산출물은 **Bronze 형태의 원문 스냅샷**까지다.
- **스케줄러 구축·운영**(cron, Windows 작업 스케줄러, Airflow 등): 이 spec은 주기 실행에 안전한 `release` 명령(멱등)과 실행 방법 문서까지 만들고, 스케줄러를 구성하는 것은 후속으로 둔다.
- 슬롯마다 굴뚝 상태를 이어서 만드는 실시간 스트림(상태를 이어받는 생성기)
- NOX와 SOX가 동시에 상승하는 변형(상관이 약해 보류)
- 결함 시나리오(S-05~S-08)를 학습용에 포함
- AWS 배포(MSK, Glue 실행), Bronze Table
- 평가용 합성(102)

## 열린 질문 (진행 전 확인 필요)

- **[NEEDS CLARIFICATION] C**: 학습용 합성 Bronze 폴더를 Silver·ML-ready가 읽도록 할 수 있는가(현재 Silver의 읽기 경로는 `tms_cleansys/`로 고정)? 합성이 ML에 쓰이려면 필요한 핵심 경로다.
- **[NEEDS CLARIFICATION] E**: (1) 합성이 실측과 같은 날짜로 ML-ready에 들어오므로, 검증·평가 데이터에서 `SYN-` 굴뚝 코드를 **제외**해 줄 수 있는가? (2) K-TMS 외부 검증 기간이 참조 통계 기간(10/30~11/10)과 겹쳐 누출이 생기지 않도록, 외부 검증을 11/11 이후 데이터로 바꿀 수 있는가? 외부 검증이 굴뚝 기준으로 나뉜다면 합성의 참조 굴뚝을 학습 굴뚝으로 제한해야 한다.
- **확정(E 자료로 확인)**: 피처가 이전 값을 최대 6칸(3시간) 보므로 에피소드의 앞 구간(warmup)은 6칸 이상으로 한다. E는 물질별(NOX·SOX) 모델을 따로 학습하므로 데이터는 성분별로 만든다.
- **참고(E 영역, 이 spec의 결정 사항이 아님)**: 합성을 얼마나, 어떤 모양을 쓸지(합성 없음 / 일부 / 1:1), 클래스 가중치·언더샘플링, 모양별 재현율 보고는 E가 정한다. 이 spec은 쓸 수 있는 데이터와 태그를 제공하는 것까지만 책임진다.
- **확인됨(사실, 2026-11-05)**: 실측 스냅샷 구조. 같은 (굴뚝, 측정 시각)은 스냅샷 한 개에만 나타나고, 수집 시각(`run_ts`)은 측정 시각(UTC로 바꾼 값)보다 94.9%가 70~79분 뒤이며 나머지는 30분 단위(100·130·160분 뒤)로 늦다. 학습용 합성은 지연 없이 측정 시각 + 70분으로 한다.
