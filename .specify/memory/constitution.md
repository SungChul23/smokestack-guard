# smokestack-guard Constitution

이 문서는 모든 기능의 spec·plan이 지켜야 하는 원칙이다. `/speckit-plan`은 이 원칙을 관문(Constitution Check)으로 쓴다.
구체적인 작업 규칙(Terraform 버전, 경로, 금지 명령 등)은 저장소 루트 `AGENTS.md`에 있다.

## Core Principles

### I. 수집 연속성 (협상 불가)

공개 API는 과거 데이터를 다시 주지 않는다. 놓친 데이터는 영구 손실이다.

- 수집 스케줄을 끄거나, 주기를 바꾸거나, 수집을 멈출 수 있는 변경은 plan에 **수집 공백 위험과 복구 방법**을 반드시 적고, 담당 B의 확인을 받는다.
- 원본(Bronze)은 추가만 한다. 원본 객체를 삭제·덮어쓰는 코드나 수명 주기 규칙은 팀 확인 없이 만들지 않는다.
- 매 실행은 성공 여부와 관계없이 흔적(실행 시각)을 남겨 "갱신 없음"과 "수집 중단"을 구분할 수 있어야 한다.

### II. 비밀값 비공개 (협상 불가)

저장소는 Public이다.

- API 키·액세스 키·비밀번호·개인 이메일은 코드, 설정, spec 문서, 커밋, 로그 어디에도 쓰지 않는다.
- 비밀값은 SSM Parameter Store SecureString에 사람이 직접 넣고, 코드와 Terraform은 **이름**만 참조한다.

### III. 코드로 만들고, 적용은 사람이

모두가 같은 환경에서 재현할 수 있어야 한다.

- AWS 리소스는 Terraform으로만 만든다. 콘솔에서 만든 리소스는 임시 검증용이며 반드시 코드로 옮긴다.
- AI 에이전트는 `plan`까지만 실행한다. `apply`·`destroy`는 사람이 결과를 확인하고 실행한다.
- IAM 권한은 기능에 필요한 최소 범위로 준다. plan에 부여하는 권한 목록과 이유를 적는다.

### IV. 데이터 계약 우선

모든 단계는 같은 약속(계약)으로 데이터를 읽고 쓴다.

- 단계 사이(Bronze → Silver → 분석·판정)를 오가는 데이터의 스키마·의미·단위는 계약 문서로 먼저 정한다.
- 계약을 바꾸는 변경은 담당 C의 리뷰를 받고, 영향받는 담당에게 PR로 알린다.
- 계약에 없는 필드를 읽거나 쓰지 않는다.

### V. 같은 조건의 정직한 비교

규칙과 모델의 성능은 같은 조건에서만 비교한다.

- 규칙(`rules.yaml`)과 모델은 같은 데이터 기간, 같은 평가 지표, 같은 기준선으로 비교하고, 그 조건을 spec에 적는다.
- 규칙과 모델은 버전으로 관리하며, 모델 배포는 2인 확인 후 진행한다.

### VI. 설명 가능한 결과

화면에 보이는 숫자와 경고는 근거를 따라갈 수 있어야 한다.

- 대시보드 수치는 수작업 기준선과 대조할 수 있어야 한다.
- 경고와 판정에는 어떤 규칙·모델·데이터로 나왔는지 출처를 남긴다.

## 운영 제약

- AWS 팀 계정 `952900391026`, 리전 `ap-northeast-2`. 루트 사용자로 작업하지 않는다.
- 새 리소스를 추가하는 plan에는 예상 비용 영향을 한 줄 이상 적는다. (A가 주간 비용 점검에서 확인한다.)
- 외부 패키지는 필요한 이유를 plan에 적는다. 수집 Lambda는 표준 라이브러리와 boto3만 쓴다.

## 작업 절차

- 새 기능, 새 스택, 계약 변경은 Spec Kit(`specify → plan → tasks → implement`)을 거친다. 작은 수정은 예외다.
- spec 번호는 담당별 대역(A 001–100, B 101–200, C 201–300, D 301–400, E 401–500)에서만 쓴다.
- 모든 변경은 PR과 1명 이상의 승인을 거쳐 `main`에 들어간다. 리뷰어는 spec과 이 원칙 위반 여부를 먼저 본다.

## Governance

- 이 원칙은 다른 작업 관행보다 우선한다. `AGENTS.md`와 충돌하면 이 문서가 우선하고, `AGENTS.md`를 고친다.
- 개정은 PR로 하고, 담당 A의 승인과 팀 공지를 거친다.
- 버전: 원칙 삭제·재정의는 MAJOR, 원칙·섹션 추가는 MINOR, 문구 정리는 PATCH.
- plan의 Constitution Check에서 위반이 있으면 plan의 Complexity Tracking 표에 이유를 적고 리뷰에서 승인받는다.
